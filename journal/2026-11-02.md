## What the M16 device incident changed

- **CCI fix (revision 15).** `cci_reset()` uses master 0's `irq_complete`, but `init_completion()` ran only for available child nodes. The `m15-safe` DTB enables CCI1 master 1 without master 0, so probe could call `reinit_completion()` on a zeroed completion and fault before any sensor probe. This is the leading hypothesis for the reported DIE and matches `i2c_qcom_cci(+)` in the warning's module list. The fix initializes every master completion after allocation, before the IRQ and reset.
- **Audio.** No audio bug found; the speaker UCM overlay is userspace. The D26 speaker path staying enabled in `m15-safe` was kept for the single-variable device test; turning it off and a camera gate remain documented fallbacks.
- **GPU/display vblank loop.** No kernel patch justified by the available fragment. The source review shows a failed firmware load does not by itself fail `msm_open()`, so removing the initramfs GPU firmware is not established to remove the loop; the recommended device diagnostic is `drm_client_lib.active=` (and separately `drm_kms_helper.fbdev_emulation=0`) on the affected entry. The firmware rollback was preserved as `image/evidence/2026-11-01-gpu-firmware-initramfs-rollback.patch`, unmerged.
- **Automatic brightness (D27).** Removed: the image ships and locks `ambient-enabled=false`; L0 checks it. The ALS remains diagnostic-only. Evidence in `hardware/sensors/evidence/2026-11-01-auto-brightness-removed.md`: the Windows WinRT inventory reports `LightSensor: PRESENT`, the board config defines a TCS3430 and Windows ships `sensorsalsdriver`; the sensor is real, the automatic response is what was removed.

## Speaker ABI resolved to EUNSUPPORTED; debug entry stabilized

- **DSP error decoded.** The status 3 returned by `APM_CMD_REGISTER_MODULE_EVENTS` is `ADSP_EUNSUPPORTED` (`sources/linux/sound/soc/qcom/qdsp6/q6dsp-errno.h:14`). A byte scan of the Surface ADSP firmware `out/firmware-root/lib/firmware/qcom/x1e80100/microsoft/Denali/qcadsp8380.mbn` finds the SP module table entries `0x070010e2` (SP), `0x070010e3` (SP VI) and `0x070010e4` (CPS router) at file offsets 0x12c6030/0x12c6020/0x12c6010, but **no occurrence of the reference diagnostics event ID `0x0800138c`**; the Windows audio miniport `qcaudminiport8380.sys` contains neither the event ID nor the module IDs. The Surface firmware supports the SP modules but not the reference SP diagnostics event, so patch 0014's fatal registration turned every WSA playback prepare into `-22`.
- **Patch 0020 (candidate).** `hardware/audio-speakers/patches/0020-ASoC-qcom-handle-unsupported-SP-diagnostics-safely.patch` maps that rejection to `-EOPNOTSUPP`, allows graph preparation to continue, and latches a guard fault so the speakers stay muted (fail-closed). Other errors stay fatal; a transport EOPNOTSUPP is kept distinct. Checkpatch `--strict` clean. Audible playback still needs device evidence that the DSP SP module and VI/CPS protection are active; the muted retest must capture the registration response and guard state.
- **Debug entry stabilization (image).** The automatic GPU two-step (`sp11.gpu_diag=1` on line 1) and the automatic CDSP restart (`sp11-cdsp-experiment.service`, `sp11.entry=debug`) were the two self-resetting diagnostic agents active only on the debug entry; the GMU/HFI start returned 0 and no oops/reset reason was logged. The image now keeps the GPU-enabled `m15` DTB on debug but starts neither agent: the two-step needs `sp11.gpu_diag=1` added in GRUB, and the CDSP experiment needs the `sp11/cdsp-experiment` marker on the boot medium (the `sp11/disable-cdsp-experiment` marker still overrides). Safe remains the default, GPU-off, microphone-only.
- **GPU firmware provenance.** The Windows `qcdx8380` package contains the Microsoft zap shader (`qcdxkmsuc8380.mbn`, staged from DriverStore) but not `gen70500_sqe.fw`/`gen70500_gmu.bin`; those come from linux-firmware. The zap-shader node is present and enabled in the m15 DTB and no zap load error is logged, so the reset is not explained by a missing zap.
- **Revision 17 build** (camera RGB-only DT exclusion + audio 0019 diagnostics + audio 0020 best-effort). The revision-16 build was cancelled after the audio ABI was decoded so a single build carries both fixes. Image scripts extended to accept revision 17; the Spectra module will be rebuilt with vermagic 17.

## Reference delivery analysis (D28/D29)

- **Audio:** the reference ships the upstream public topology `X1E80100-Microsoft-Surface-Pro-11-tplg.bin` (linux-msm/audioreach-topology `993a17dc…`) and alsa-ucm-conf 1.2.16.1 + PR 847, with volume limits and no hardware protection; its feature table reports speakers and microphone working. Topology facts: playback `S16_LE` 48 kHz 2 channels (WSA RX0 and both DP links), capture 48 kHz 1-2 channels for the 2-DMIC VA array. Our closed-loop SP path is the cause of the `-22`: `APM_CMD_REGISTER_MODULE_EVENTS` returns `ADSP_EUNSUPPORTED`, the firmware has the SP module table (`0x070010e2/e3/e4`) but not the reference event ID (`0x0800138c`), and the Windows miniport never sends that command.
- **Selection contract:** the kernel requests `qcom/<driver_name>/<card->name>-tplg.bin` (`topology.c:1415-1429`) with `card->name` = sound model. Default variants keep the public model; the spk experiment gets `…-CL` and the private closed-loop topology under that name. No userspace selector, no race with probe.
- **Patch 0022 (audio):** reads `/chosen/sp11,speaker-policy` and the parsed graph: unreadable policy → refuse; SP module present → closed loop; no SP + `d26-open-loop-v1` → open loop (skips the SP loader and closed-loop requirements, keeps PA/RX/MIX caps 6/81, fault and `sp11.nospk`); anything else → refuse. Mic and DP registration survive a refusal. checkpatch clean; needs integration and the muted device test.
- **GPU:** no firmware gap (the reference uses the same linux-firmware SQE/GMU and the WOA zap; the Windows qcdx package has no SQE/GMU). The reference DT reserves no-map `gpu-prr@81f00000` (64 KiB) and `pld-gmu@81f36000` (4 KiB) that our v7.3/M15 DT omits; candidate patch 0002 adds exactly those, with EFI-map/`/proc/iomem` comparison and rejection criteria. GMU/OPP/speed-bin/GPUCC/cooling match the reference; the diagnostic agents are now opt-in.
- **Cameras:** the reference explicitly has no camera support. Our stack is ahead; the upstream Surface-tested C-PHY work uses a standalone PHY architecture different from our legacy integrated CSIPHY patches (a migration set, not a cherry-pick), and the ST VD55G0 driver exists outside the pinned base. The RGB-only DT fix is the next device test; the IR driver will be considered only from the Windows/upstream data if required. REA of the Windows camera binaries is prepared but blocked for Codex workers by the `never` approval policy; the orchestrator can run it.
