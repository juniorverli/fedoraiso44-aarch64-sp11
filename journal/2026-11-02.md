## What the M16 device incident changed

- **CCI fix (revision 15).** `cci_reset()` uses master 0's `irq_complete`, but `init_completion()` ran only for available child nodes. The `m15-safe` DTB enables CCI1 master 1 without master 0, so probe could call `reinit_completion()` on a zeroed completion and fault before any sensor probe. This is the leading hypothesis for the reported DIE and matches `i2c_qcom_cci(+)` in the warning's module list. The fix initializes every master completion after allocation, before the IRQ and reset.
- **Audio.** No audio bug found; the speaker UCM overlay is userspace. The D26 speaker path staying enabled in `m15-safe` was kept for the single-variable device test; turning it off and a camera gate remain documented fallbacks.
- **GPU/display vblank loop.** No kernel patch justified by the available fragment. The source review shows a failed firmware load does not by itself fail `msm_open()`, so removing the initramfs GPU firmware is not established to remove the loop; the recommended device diagnostic is `drm_client_lib.active=` (and separately `drm_kms_helper.fbdev_emulation=0`) on the affected entry. The firmware rollback was preserved as `image/evidence/2026-11-01-gpu-firmware-initramfs-rollback.patch`, unmerged.
- **Automatic brightness (D27).** Removed: the image ships and locks `ambient-enabled=false`; L0 checks it. The ALS remains diagnostic-only. Evidence in `hardware/sensors/evidence/2026-11-01-auto-brightness-removed.md`: the Windows WinRT inventory reports `LightSensor: PRESENT`, the board config defines a TCS3430 and Windows ships `sensorsalsdriver`; the sensor is real, the automatic response is what was removed.

## M16 device boot: component findings

The operator returned three boots from the revision-15 ISO (`out/device-logs/m16-20261102/`): safe `9e275ce6…` (complete), debug `9ea9dbde…` (incomplete, the GPU diagnostic boot) and spectra `0d54e0fc…`.

- **CCI fix confirmed.** The safe boot reaches the camera stack with no DIE: CCI/ISP probe, OV13858 loads three modes from its blob, IMX681 binds. The `msm_dpu` vblank WARN is no longer the reported failure on safe.
- **Cameras not usable yet.** Both RGB sensors bind but the media graph has zero sensor links and `cam -l` finds no camera; `/dev/video0…15` exist but no `/dev/v4l-subdev*`. The cameras worker's strongest hypothesis is that CAMSS waits for the described IR sensor (VD55G0, no driver) before completing registration. It prepared an RGB-only DT exclusion (`hardware/cameras/dtb-variants/x1-microsoft-denali-camera-no-ir.dtsi`) and corrected the rear-only diagnostic variant. TPG entity warnings are not shown to cause the missing links. Privacy LED, C-PHY streaming and tuning remain unverified.
- **Audio playback `-22`.** The DSP rejects `APM_CMD_REGISTER_MODULE_EVENTS` (`0x0100100e`) — the shared-memory watermark event registration in `audioreach_shmem_register_event()`, whose module instance is `graph->shm_iid` — and the error propagates through media-format setup as `-22` on `WSA_CODEC_DMA_RX_0`. The topology declares stereo/48 kHz/S16_LE; the actual negotiated RX parameters and the ADSP's rejection reason are not logged. A diagnostic patch (0019) and the SH_MEM lead are with the worker.
- **Microphone.** The safe boot applied the D26 speaker UCM overlay; selecting Mic then also runs WSA initialization, and the speaker path fails as above. The mic route itself is present in the live UCM (Mic on PCM 1, DMIC0/1, AIF1 capture switches). Image now keeps safe microphone-only.
- **CDSP blocked.** `fastrpcglink-apps-dsp` and `IPCRTR` endpoint creation time out in the GLINK OPEN_ACK handshake (`-110`/`-12`); channel names and the normal `c1-00078` pair match, the alternate pair is not shown selected. The ADSP FastRPC/QRTR path works and the SSC service appeared on QRTR, so sensors do not depend on this CDSP failure. No speculative fix.
- **GPU.** GMU firmware and HFI start return 0 (twice), step 1 writes on the GMU, step 2 renders and samples; the reset follows the last durable log with no oops or reset reason. The debug entry is a self-resetting diagnostic, not a usable session. Safe without the GPU is software-rendered (Vulkan llvmpipe), which explains the stutter. The image now boots safe by default and keeps debug selectable; GPU stability is unresolved.
- **Sensors.** The hexagonrpcd seccomp filter-add warnings do not stop the daemon; it ran and served ADSP file requests, then stopped at shutdown. The first instance rejected an input larger than 256 bytes, exited and restarted; the effect on SSC data is unknown. Installer/collector fixes are merged.
- **Bluetooth and Wi-Fi look up on safe:** `hci0: QCA setup on UART is completed` with the AOSP extensions and RFCOMM; ath12k adds its interface and updates the regulatory rules.
