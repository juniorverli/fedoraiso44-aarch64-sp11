## M16 device incident (2026-11-01, evening): DIE in safe and vblank loop

- **Reported by the operator, photographed screen, not a captured log:** real Surface Pro 11, M16 private ISO, kernel `7.3.0-65.sp11.14.fc44`. A DIE (taint `D`) before 46.66 s whose trace tail is a kworker; at 47.72 s a WARN at `drm_vblank.c:1329`, `msm_dpu ae01000.display-controller: vblank wait timed out on crtc 0`, from `drm_fb_helper_damage_work`, which the operator reports repeating. The WARN module list includes `i2c_qcom_cci(+)`, `camcc_x1e80100`, `msm`, `panel_edp`. The first oops header, fault address and full trace are unavailable. M15.1 logs have no vblank warning, no CCI load and no oops.
- **Cameras worker (Codex Terra 6.1 high), concrete defect:** `cci_reset()` always uses `/soc@0/cci@…` master 0 (`sources/linux/drivers/i2c/busses/i2c-qcom-cci.c:271-282`), but `init_completion()` runs only for available child nodes (`:562`). The `m15-safe` DTB enables CCI1 master 1 (`cci1_i2c1`) without master 0, so probe calls `reinit_completion()` and waits on a zeroed completion, which can fault before any sensor probe. The running module was not inspected; attribution to the DIE remains a hypothesis until the oops PC is captured. Evidence: `hardware/cameras/evidence/2026-11-01-m16-safe-camera-die.md`; recovery gate `hardware/cameras/m16-safe-camera-gate.diff`; fix patch `hardware/cameras/patches/0021-i2c-qcom-cci-initialize-every-master-completion.patch` (checkpatch --strict clean, applies to v7.3). Worker branch `worker/cameras` commits `cd5c04c`, `b542b8a`.
- **Audio worker (Codex Terra 6.1 high):** no specific audio bug found; the UCM overlay is userspace and cannot execute in the kernel. It recommends keeping the D26 speaker path out of the fallback (`m15-safe`): replace the D26/DP/closed-loop includes with `x1-microsoft-denali-audio-mics.dtsi` (microphones + DP, speakers off), per S1/D26. Evidence: `hardware/audio-speakers/evidence/2026-11-01-m16-safe-audio-die.md`; branch `worker/audio-speakers` commit `6b1d510`.
- **GPU worker (Codex Terra 6.1 high):** the timeout proves the vblank count did not advance, not that the CRTC was software-inactive; the atomic fbdev finder already checks activity, so no kernel patch is justified from this log. A failed firmware load does not make `msm_open()` fail, so removing the M16 initramfs GPU firmware is not established to remove the loop. Recommended first diagnostic: boot the affected entry with `drm_client_lib.active=` (empty) to bypass the in-kernel client, separately test `drm_kms_helper.fbdev_emulation=0`, and capture the full first oops. Evidence: `hardware/gpu/evidence/2026-11-01-m16-vblank-loop.md`.
