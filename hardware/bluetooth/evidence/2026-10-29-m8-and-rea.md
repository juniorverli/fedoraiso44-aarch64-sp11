## M8: established failure and ordering

**Verified:** `extra-bluetooth.txt:2-23` reports zero normal management indexes, one unconfigured hci0, and `public-address` as its only supported/missing configuration option. The explicit-index output prints an inconsistent index label; use the unindexed enumeration and option fields as evidence, not that label as a second controller. `:35-38` reports Bluetooth soft/hard unblocked. `:48-52` records the helper's failed result and exit 1.

**Verified:** `dmesg.txt:2145-2215` records WCN7850 setup, requests for `qca/hmtbtfw20.tlv` and `qca/hmtnv20.bin`, the firmware build string and completed UART setup. `journal.txt:66325-66428` records bluetoothd 5.87 starting and management interface 1.23 initializing. At `:72049` the helper detects the missing option; at `:74076` it reports no valid operator file on the boot ESP. The operator confirms the file was not supplied. This establishes the missing-address gap; the absence of a file is expected input, not a firmware download failure.

The component capture was taken during shutdown: bluetoothd is already inactive and `bluetoothctl` aborts after failing to obtain its D-Bus connection (`extra-bluetooth.txt:25-46`). Those observations do not establish a session-time daemon failure. Preserve the earlier startup journal and request the next capture during the session.

**Verified source design:** the helper is pulled in by `sys-subsystem-bluetooth-devices-hci0.device`, binds to that device, and runs after device creation and `local-fs.target`, with normal systemd service dependencies and a 90-second timeout. It polls the management configuration because device creation precedes completed firmware setup. It neither requires nor orders after bluetoothd; management sockets work without it. Setting the address queues controller configuration (`sources/linux/net/bluetooth/mgmt.c:8412-8422`); the core subsequently publishes an index-added event (`net/bluetooth/hci_sync.c:5749-5760`), allowing a running BlueZ daemon to discover it. No new BlueZ ordering dependency is needed.

M9 changes an absent explicit file or unavailable/invalid boot-ESP source into exit 0 with a clear `controller remains unconfigured; skipped` journal line and provisioning guidance for the boot ESP. Invalid existing explicit files, failed management queries/commands, unexpected missing options and failed readiness verification remain errors. The service description no longer reads as an unconditional address promise. This is a soft skip, not Bluetooth functional success. No fallback address or firmware write is introduced.

## REA: DPP backend and Linux access limits

`QcSOCPartition.sys` lists 867 procedures (`ev_22834756f8a41958b6eb14cb68792fcb77bcb24639b35c8c424f64200b814662`). The shared storage path has a read/write selector: the traced read path supplies zero (`0x140024088`, `ev_89795d64eb2ee6f6ba97ca9037fb50499bd4a41df53e06550b31fafe1fde14d2`; `0x140052e00`, `ev_1f433f9bc0f780d6e518a47fd61dec0c6bc1419ecb827b9e3579b30489ba6efe`). Partition discovery opens disk paths, requests partition layouts, and constructs `\Device\Harddisk%u\Partition%u` for matching entries (`0x14004d368`, `ev_3a39845170279f76697f9b2b4b94f102e5feb69f4691d44ebf164afe23c85ce3`; `0x14002bb10`, `ev_1f12b9adebd5904d1f1eec9dea79a084a4da27d350d253b57bf0a787bc783e83`). The private Windows GPT capture in `sar-phase2-readonly.txt:18` onward contains no DPP-type partition. That bounds the captured disks; it does not exclude firmware-owned storage or prove the DPP item absent.

**Verified Linux source:** v7.3 `hci_qca` has no DPP consumer. Address-property lookup is in `sources/linux/net/bluetooth/hci_sync.c:3746-3763`; the unconfigured flag is set at `:5320`. Native management address setting is already supported by `sources/linux/net/bluetooth/mgmt.c:8376`, `drivers/bluetooth/hci_qca.c:2078`, and `drivers/bluetooth/btqca.c:1005`. The existing QSEECOM client registers UEFI variable operations (`drivers/firmware/qcom/qcom_qseecom_uefisecapp.c:794-800`), and M8 `dmesg.txt:551-553` confirms that registration. Neither fact identifies a Bluetooth address variable.

The upstream [October 14 UEFI-NVMEM RFC](https://patchew.org/linux/20261014-b4-nvmem-efivar-v1-0-187c85f65018%40oss.qualcomm.com/) proposes an operator-provisioned `MacAddresses` variable; its illustrative consumers are not a discovery method for an existing Surface factory variable. Writing such a variable is outside S3 and unnecessary here. The [QCA NVMEM series](https://lore.kernel.org/all/20261015-block-as-nvmem-v11-6-f890ac74f87d@oss.qualcomm.com/) is relevant only after a real readable backing store/cell is established. No matching DPP/UEFI source was found in the local Linux source or the upstream search; this is a bounded investigation, not proof none exists.

**Conclusion / Inference:** a read-only automatic Linux source is not established. Porting a Windows storage backend or fabricating a UEFI variable name would exceed the evidence. Keep the private post-write operator file for M9; request only metadata and registry presence evidence in the next planned test. Do not derive an address from Wi-Fi, UUIDs or serials, write UEFI/DPP, or mount Windows to recover it.
