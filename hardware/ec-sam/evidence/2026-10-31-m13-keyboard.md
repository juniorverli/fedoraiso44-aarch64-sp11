## Unknown

- Which request (event disable, display-off, D0-exit), if any, fails at shutdown, or whether the Windows driver simply cannot recover from a D0-exit that Linux sent after its own session.
- Whether a full Windows shutdown before the Linux session (no hybrid hiberfile) changes the outcome.
- Whether Windows is frozen by the EC state or by the cover (detach/re-attach result is not recorded).
- Whether `ResetSystem` versus PSCI changes the outcome.

## Which SAM mode first: `silent`

Order: **`silent`, then `clean`, then `quiet`**.

Why `silent` first:

1. It is the only mode that touches the EC with nothing at all, so it cuts the hypothesis space in one cycle: if the keyboard still freezes, no SAM shutdown request (default, quiet or clean all send a subset of what default sends) is the cause and the next work is the Windows boot type, the cover and the reset path; the two other builds are not needed. If it works, a request is the poison and `quiet` then isolates events-off from display-off and D0-exit.
2. The other two modes are only informative when they succeed: `clean` and `quiet` failing would not exclude the shutdown requests (the failing request may be one they still send). `silent` failing excludes them.
3. It carries no extra risk: it sends nothing, so the EC state at the next boot is what a hard loss of the host would leave, and probe sends D0-entry and display-on again (`core.c`, probe).
4. `clean` is the second best chance to become the fix (it is default plus an orderly client removal) but its benefit over default cannot be measured while the failure point stays invisible (V4).

## Experiment design (one cold cycle per mode; changes versus the previous note)

1. **Use `systemctl poweroff`, and record which of reboot or poweroff the operator uses.** M13 ended with `Reboot` (V3). Do the first `silent` cycle with poweroff, then repeat once with reboot if it passes.
2. **Control (zero code):** once, end the Linux session with a long power-button hold (no `device_shutdown()` at all) and boot Windows. If the keyboard still freezes, the SAM shutdown path is not the cause and Linux's earlier session state is. If it works, the shutdown path matters.
3. **Remove the hybrid hand-off from Windows:** before each Linux session, in Windows run `shutdown /s /full /t 0` (full shutdown, no hiberfile resume), or once `powercfg /h off` (reversible: `powercfg /h on`). After the Linux session record the boot type in Windows: `Get-WinEvent -FilterHashtable @{ProviderName='Microsoft-Windows-Kernel-Boot';Id=27} -MaxEvents 1` (0 full, 1 Fast Startup, 2 resume from hibernate). This tests I4 with Windows tools only.
4. **Make the failure observable** (image owner request; no kernel code): add `printk.always_kmsg_dump=1` and, if `efi_pstore` is built, check `/sys/fs/pstore` on the next boot; otherwise a serial/netconsole path would be needed. Grade: Hypothesis (needs `CONFIG_PSTORE`/`EFI_VARS_PSTORE` in `kernel/config`; unknown whether this unit's UEFI variable store (qseecom `uefisecapp`) accepts the dump).
5. **Kernel-level options that need no patch (command line only), after `silent`:**
   - `reboot=warm`: selects `EFI_RESET_WARM` in `ResetSystem` (V7). Hypothesis that a warm reset leaves the EC session intact; low value, costs one cycle.
   - `efi=noruntime`: forces the PSCI `SYSTEM_RESET` path instead of UEFI `ResetSystem` (V6) and removes efivarfs for that boot; tests whether the Microsoft reset handler matters. Hypothesis, 1 cycle; run it only if `silent` fails.
   Both leave `surface_aggregator.shutdown_mode` at the mode chosen, so combine only one change per cycle.
6. The Windows Fast Startup hand-off and UEFI runtime services cannot be changed from the kernel: the first is Windows state (item 3), the second is read-only firmware (item 5).

Entries needed from the image owner (already specified in `2026-10-30-windows-transition.md` section 5): `SAM shutdown quiet`, `clean`, `silent` exist in the M13 menu. Add `printk.always_kmsg_dump=1` to them and record `sp11.entry` in the collector.
