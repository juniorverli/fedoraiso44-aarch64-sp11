## 2. Corrections to the M10 evidence

- M10 I1 is wrong. It said the CDSP read our VERSION_ACK before opening channels. F1 and F2 show the CDSP read only VERSION. Its own VERSION_ACK and OPENs are the response to that single message, written in one burst; it then stopped reading. The doorbell and mailbox ids are still not wrong (the first signal was seen), but only one signal ever got through.
- M10 section 4 item 2 named events `smp2p_*:*` and `rproc_qcom_event`. The SMP2P events are real, but their trace system is `qcom_smp2p`, and 7.3 has no remoteproc trace event at all.

## 3. Cause decision

Hypothesis C2 (CDSP does not wake or stalls) is supported: C1 (waiting for a Windows SMP2P step) would show the CDSP reading our messages and staying silent, and F1 shows the opposite. C3 (crash) is excluded by F4. The CDSP never reads the second doorbell, and it has been counted as asleep since boot (F6).

New hypothesis C4, Inference only: the Microsoft-signed CDSP firmware does not hold its own NSP/MXC votes through RPMh after `handover`, and relies on a vote that Windows keeps (ACPI NSP0 is a PEP-managed device, F9). Linux releases cx, mxc and nsp when the handover IRQ arrives (F5), so the NSP core idles or power-collapses a few milliseconds after the first message. Support: the stall starts 2 to 4 ms after boot, `nsp` is off, the CDSP accumulates sleep time with no count. Against: the same driver works for upstream CDSP firmware on other X1E devices, and the time of the handover IRQ against the first VERSION is not recorded (the smp2p trace failed). Grade: Inference, not Verified. No fix is established.

Windows bring-up (REA, `qcsubsys8380.sys` SHA-256 `4ce9bc81...a995be`, matches `sources/binary-catalog.tsv`, one binary open, closed; Ghidra 12.1.4, language was `auto-from-header` arm64, not forced: R-S1 stays open):

- Verified: function at `0x1400d6ab0` (evidence id of the string xref `ev_9d4be5c1`) is the SMP2P channel init. It registers the SubsystemToApps context (entry `slave-kernel`) and then the AppsToSubsystem context (`master-kernel`), each with a 1 s wait, reads the first `slave-kernel` value, and treats bit 0 set as an error state. Errors it formats: `Registration of ... failed`, `Reading SMP2P message failed`.
- Verified: function at `0x140019c80` (evidence `ev_20501c0d`) only formats crash reasons (`watch dog bite`, `[HLOS] Failure in the SMP2P monitor thread`, SMEM failure reason). Not a bring-up step.
- Verified: function at `0x1400a4a80` (evidence `ev_a569eb8f`) waits on two events with indirect calls for the two contexts. The bit writes and the QB/DS bits are behind indirect calls (`_guard_check_icall`) that this pass did not resolve.
- Unknown: which bit values Windows writes into `master-kernel`; what the QB_RDY, PWR_CLK_RDY and ERR_HDL_RDY event names map to on the wire; the NSP, MXC and CX votes Windows holds after start; any wake or doorbell step. The decompiled bodies are mostly trace-call boilerplate; the next pass needs the indirect-call targets (the SMP2P interface table passed to the registration helper `FUN_14000dd08`) and the PEP side (not in `qcsubsys8380`).
- `DS_RDY`/`DS_ACK` and `DEEP_SLEEP_ACK` belong to deep sleep (modern standby) in the state and event names. Inference only.

## 4. Decision: diagnostic patch 0003, not a fix

`patches/0003-remoteproc-qcom_q6v5_pas-add-keep_proxy_pds-diagnostic.patch`: new read-only module parameter `qcom_q6v5_pas.keep_proxy_pds` (default off). When set, the handover IRQ logs `handover: proxy power domains kept` and leaves the proxy power domains (cx, mxc, nsp for the CDSP; lcx, lmx for the ADSP) enabled until `rproc stop`, where they are released. Off, it only adds one `dev_info` line (`... released`). This decides C4: with the parameter set, a CDSP that then acks OPEN confirms C4, and the fix becomes a DT/driver rule for this SKU. If the CDSP still stalls, C4 is excluded.

Checks: `git apply --check` clean on v7.3 and on v7.3 plus the full current `kernel/series`; `checkpatch --strict` reports only the intentional missing `Signed-off-by`. Not built, not run. The parameter works from the kernel command line (`qcom_q6v5_pas.keep_proxy_pds=1`) because the driver loads from the initramfs.

`pd_ignore_unused` and `clk_ignore_unused` do not help: they stop the late cleanup of unused domains and clocks, but the proxy release is an explicit disable in `qcom_pas_handover()`.

## 5. Trace names in 7.3 (item B)

Found by grep of `TRACE_SYSTEM` and `TRACE_EVENT` in the v7.3 tree:

| System | Events | Where |
|:--|:--|:--|
| `qcom_smp2p` | `smp2p_ssr_ack`, `smp2p_negotiate`, `smp2p_notify_in`, `smp2p_update_bits` | `drivers/soc/qcom/trace-smp2p.h`; `smp2p` is a module here (`lsmod`) |
| `qcom_glink` | `qcom_glink_cmd_*` | `drivers/rpmsg/qcom_glink_trace.h`; already working in M10 |
| `qcom_aoss` | `aoss_send`, `aoss_send_done` (the CDSP `load_state` QMP vote) | `drivers/soc/qcom/trace-aoss.h`; module `qcom_aoss` |
| `rpmh` | `rpmh_send_msg`, `rpmh_tx_done` (NSP and MX rail votes) | `drivers/soc/qcom/trace-rpmh.h` |
| `power` | `power_domain_target` (genpd performance state) | `include/trace/events/power.h` |

No `remoteproc` or `rproc_qcom` event exists in 7.3. `smp2p:*` and `remoteproc:*` can never work. Tracing config: Fedora RPM config provides tracing (M10 `qcom_glink` events were recorded); `kernel/config/*.config` states no tracing symbol, so the L0 check should assert `CONFIG_TRACING` and `CONFIG_EVENT_TRACING` in the final config (request R-K5).

Corrected string (modules by `:mod:` so that tracing starts at module load; built-in systems by name):

`trace_event=:mod:qcom_glink,:mod:smp2p,:mod:qcom_aoss,rpmh:rpmh_send_msg,power:power_domain_target trace_buf_size=16M`

`rpmh_send_msg` can be frequent: the collector records only a count of it. If the buffer overruns, drop `rpmh:` first and keep `qcom_glink` and `smp2p`. Unproven: that `:mod:smp2p` is accepted for module `smp2p` (the same syntax worked for `qcom_glink`); check `Failed to enable trace event` in dmesg of the next boot.

Collector: added a section to `collector/dsp-subsystems.sh` (read only): enable state of the four systems, `smp2p_*` lines, `aoss_send`, genpd lines for nsp, mxc, cx, an `rpmh_send_msg` count, the patch 0003 handover line and the genpd summary rows for nsp, mxc, cx.
