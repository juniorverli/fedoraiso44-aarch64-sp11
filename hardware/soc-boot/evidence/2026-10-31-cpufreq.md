## Verified (Linux 7.3 source)

- `drivers/cpufreq/scmi-cpufreq.c:481-485`: the driver's only match is `{ SCMI_PROTOCOL_PERF, "cpufreq" }` through `MODULE_DEVICE_TABLE(scmi, ...)`.
- `drivers/firmware/arm_scmi/bus.c:53-190`: an SCMI device named `cpufreq` is created only after a driver *registers* that id table (`scmi_protocol_device_request`). The DT does not name it, and nothing in `arm_scmi` calls `request_module` for it (only vendor protocols, `driver.c:50,280-284`).
- `scmi-cpufreq.c:441-452`: probe needs `scmi_dev_used_by_cpus()`, satisfied by the CPUs' `perf` power-domain pointing at `protocol@13`.
- The 10 remaining CPUs keep `power-domains`/`power-domain-names`/`#cooling-cells` (patch 0001 removes only cpu7/cpu11 nodes). The DT is not at fault.

## Inference: root cause

`scmi-cpufreq` is a module, its device appears only when the module registers, and the alias the kernel emits (`scmi:13:cpufreq`) never exists before that, so udev cannot autoload it. Nothing loads it explicitly. This is a chicken-and-egg: `arm-scmi` and `scmi-perf-domain` (built in) work, `scmi_cpufreq` never runs. Reasoning rests on: module present and not loaded; no DT, protocol or deferral error; `bus.c` request model; no modules-load entry. Not proven by a manual `modprobe` (not run).

Ruled out: SCMI node missing or disabled (present, Using mailbox transport); transport or protocol config (built in, handshake OK); missing performance-domains (10 present); deferral (no cpufreq line in `devices_deferred`, `dmesg` or journal); missing module (present in squashfs).

## Fix (minimal, no kernel patch, no DT patch)

1. Image owner (no kernel build): add `image/overlay/etc/modules-load.d/sp11-cpufreq.conf` with the single line `scmi_cpufreq`, and extend L0 to check the file and the module. Needs a new ISO only. The module is in the squashfs (late); the initramfs does not need it.
2. Optional later, kernel owner: `CONFIG_ARM_SCMI_CPUFREQ=y` in `sp11.config` makes it independent of userspace, but needs a full kernel build; not required.
3. Safety wrapper (below) is part of the image change, not a separate build.

Expected after the fix: `scmi-cpufreq` registers `cpufreq: policyN` for three clusters (4 + 3 + 3 CPUs), `scaling_governor=schedutil`, and two new cooling devices appear only after a DT cooling-map exists (see below). Unknown: whether registration succeeds on this firmware (fast channels, rate limit, OPP table); a failure would print `scmi_cpufreq_probe: registering cpufreq failed` or `No OPPs for this device`.

## Safety (S6)

- Today CPUs run at a firmware-chosen, unknown frequency (Unknown; `/proc/cpuinfo` has no MHz). `schedutil` can raise a CPU to the SCMI maximum under load, which may be higher than that frequency. Registering cpufreq therefore can raise sustained power, even though it saves power at idle.
- Thermal today: CPU zones have one `critical` 115 C and no passive trip or cooling-map (`hamoa.dtsi` thermal zones); Windows throttles from 104.85 C. With cpufreq registered, `CONFIG_CPU_FREQ_THERMAL=y` creates a `cpufreq-N` cooling device per policy, but `step_wise` does nothing until a passive trip and `cooling-maps` exist. Registering cpufreq does not by itself lower or raise any limit.
- Conservative default for the first boot (proposal, image owner): load the module from an opt-in unit enabled only by a GRUB entry or `sp11.cpufreq=1`, record `scaling_available_frequencies`, set governor `schedutil` and cap `scaling_max_freq` to a mid-range level taken from `scaling_available_frequencies`, never `performance` or `ondemand`. Run the existing thermal sampler (85 C abort ceiling) and log temperatures. Default-on only after the stress run passes.
- Trips (proposal, soc-boot patch 0002 after the first boot proves registration): add `passive` at 104000 mC or lower on the `cpu*` and `cpuss*` zones with `cooling-maps` to the three clusters' cpufreq (cpus already have `#cooling-cells = <2>`), and lower `critical` from 115000 to 114000 mC or lower. Never raise any trip. Not written now: a passive trip without a registered driver does nothing, and the mapping of zones to sensors is Inference (power-thermal dossier).
