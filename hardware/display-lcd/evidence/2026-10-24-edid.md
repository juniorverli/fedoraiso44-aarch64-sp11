# LGD077B EDID and DisplayID decode

Input: `sources/windows/live-inventory/panel/edid-LGD077B.bin`, 384 bytes,
SHA-256 `37b722fa103c8ecd8fd14356c0fdad153f9d6b6699dbe7c7b9b4c66f1d3d9e62`.
Its catalog row classifies it as data, with no Ghidra language. No disassembly
was used. All offsets below are absolute file offsets. Private identification
fields are deliberately omitted.

Reproduction: run `python3 hardware/display-lcd/tools/decode-static.py` from
the project root. Independently decoded with Fedora 44 `v4l-utils-1.32.0-3.fc44`
(`edid-decode 1.32.0`); private full output stays in
`out/rea/display-lcd/edid-decode.txt`. This second decoder is a local check,
not the independent runtime cross-check required by protocol §5.1.

## Q4: link budget

**Inference**, using the Verified clock above and the 8b/10b link capacities
represented in `sources/linux/arch/arm64/boot/dts/qcom/x1-microsoft-denali.dtsi:922`:

| RGB depth | Stream rate (clock × bits per pixel) | Four-lane requirement |
|:--|--:|:--|
| 8 bpc | 17.164824 Gbit/s | Fits nominal HBR2 payload 17.28 Gbit/s, with little margin |
| 10 bpc | 21.456030 Gbit/s | Exceeds HBR2; fits HBR3 payload 25.92 Gbit/s |

Both refresh modes have the same stream clock and therefore the same nominal
bandwidth requirement. Whether the panel advertises four HBR3 lanes, which
bpc MSM actually chooses, and whether training succeeds remain **TBD** pending
DPCD and device logs. This arithmetic alone does not establish a working link.
