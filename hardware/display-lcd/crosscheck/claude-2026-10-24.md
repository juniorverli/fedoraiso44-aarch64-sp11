## 3. How the blobs were decoded (no disassembly)

`qcdxkmext8380_DEN*.bin` are catalogued as data and were decoded by structure only (script kept outside git).

- File header, 0x34 bytes: `34 00 00 00`, `70 70 80 80`, `01`, `0a`, `0c`, then the string `8380_DEN_EXT`.
- Section table at 0x34, 12 bytes per entry (4-byte tag, u32 offset, u32 size): `ENGS`, `G0MD`, `G7MD`, `G8MD`, `G9MD`, `GKMD`, `GLMD`, `GMMD`, `GPMD`, `PMCL`. In BLOB-IDP they start at `0xac, 0xb37, 0x5de1, 0xfa32, 0x19683, 0x234f6, 0x2d369, 0x371a6, 0x40fe3, 0x4103e`; the last ends at `0x4a7b2` = file size. Verified.
- Each section starts with `AeoB`, u32 section size, u32 count, then records. A record is `u16 type, u16 payload length, payload` with no padding. Type 0 = little-endian integer (always 8 bytes here), 1 = NUL-terminated string, 2 = 16-byte GUID, 3 = node containing records. In `PMCL` a pair of stray zero bytes follows each `'*'` string.
- `G0MD`, `G7MD`..`GMMD` are the file form of the DSDT methods of the same name in `Scope (\_SB.PEP0)` (`DSDT:23105` `G0MD`, `23155` `G7MD`, `23405` `GMMD`); `GPMD` is `METHOD_LIST` (`DM0G`..`DMMG`), the same list as `PREL` in the DSDT (around `DSDT:4865`). Each method returns a `DEVICE 0x82 "\_SB.GPU0"` description, which the PEP (`qcpep8380.sys`) executes. The DSDT versions are `IDP1` (`DSDT:4898`) and `IDP2` (`DSDT:13929`), selected by `TBID` in `G0MD` (`TBID == 0` returns `IDP2`; 5, 7, 8, 0xB, 0xD, 0xF, 0x10 return `IDP1`; anything else returns a one-byte empty buffer).
- Live registry shows the GPU uses `AcpiBaseFile = qcdxkmbase8380.bin` and `AcpiExtFile = ...\surface_dxext_8380.inf_arm64_69910c8aa1a39011\qcdxkmext8380_DENidp.bin` (`GCK`, lines `AcpiBaseFile`/`AcpiExtFile`).

## 5. Q1: backlight

### 5.1 What the Windows data shows

BLOB-IDP, section `G0MD`, `DEVICE \_SB.GPU0`, component 0, `FSTATE 1`. The `EXIT` node (`0x11b8`) is the power-up list and the `ENTER` node (`0xbc0`) the power-down list: the power-up list carries the real rail votes (`LDO2_J` 1 256 000 µV and `LDO3_J` 880 000 µV, `0x1437`, `0x14c1`) and the enabling clock and footswitch values; the power-down list carries zero votes. The power-up list has the same content as the DSDT `IDP1` `FSTATE 0 EXIT` list (`DSDT:4898-5233`), except that the blob moved the MDP clock and bus lines into its `PSTATE_SET` nodes. Verified (records), Inference (which list is which direction, from the votes).

### 5.2 Reading the PMIC GPIO records

- Record meaning (Inference): fields are `pmic index, gpio index (0-based), out buffer, voltage source, source/function, drive, ...`. PMIC index = SPMI USID: index 0 is `pmk8550` (`hamoa-pmics.dtsi:199`, `reg = <0x0 ...>`), index 3 is `pmc8380_3` (`hamoa-pmics.dtsi:492-494`). GPIO index is 0-based.
- Evidence for the 0-based GPIO index (Inference, three independent matches): `(3,7)` and `(3,5)` are used in the DSDT for `\_SB.PCI3` (`DSDT:41116`, `41132`, `41700`, `41716`, `45677`, `45693`, `46239`, `46255`), and `sources/linux/arch/arm64/boot/dts/qcom/hamoa-iot-evk.dts:285` and `:299` use `pmc8380_3_gpios 6` (`VREG_PCIE_3P3`) and `pmc8380_3_gpios 8` (`VREG_PCIE_3P3_AUX`), that is index 5 and 7 plus one. The three display records land on `pmc8380_3` gpio10 (`hamoa-iot-evk.dts:232-247`, `vreg_edp_bl`, "VBL9"), `pmc8380_3` gpio4 (`hamoa-iot-evk.dts:22-30`, `enable-gpios`, and `x1-microsoft-denali.dtsi:902,1009-1015`) and `pmk8550` gpio5 `func3` (`hamoa-iot-evk.dts:1184-1189`, `x1e78100-lenovo-thinkpad-t14s.dts:51-56`, `x1e80100-microsoft-romulus.dtsi:1213-1217`). With a 1-based index they would be gpio9, gpio3 and pmk8550 gpio4, which match none of the pins the reference boards use for these three functions.
- Function field (Inference): the `source` field is 4 for the PMK8550 pin; Linux's function index for `func3` is 4 (`pinctrl-spmi-gpio.c:129-133`: normal 0, paired 1, func1 2, func2 3, func3 4). The value `0x0A` used for the two plain GPIOs (and `0` in two other DSDT records for the same PMIC GPIO pairs) is not decoded (TBD).
- TLMM records (Inference): layout `gpio, value, function index, direction, pull, drive`. GPIO 70 power-up `(1, 0, 1, 3, 7)` = output high, function 0 (gpio), drive code 7 = 16 mA, matching `x1-microsoft-denali.dtsi:1127-1132` (`edp_reg_en`, function `gpio`, `drive-strength = <16>`) and `vreg_edp_3p3` on `tlmm 70` (`x1-microsoft-denali.dtsi:128-141`). GPIO 119 power-up `(1, 1, 0, 0, 0)` = function index 1, input, no pull; `pinctrl-x1e80100.c:1686` shows function index 1 of pin 119 is `edp0_hot`, matching `hamoa.dtsi:6110-6114` (`edp0_hpd_default`). The pull code `3` for GPIO 70 does not match the `bias-disable` of the Linux DT; not resolved.

### 5.3 Method: PMIC PWM, not DPCD/AUX (Inference)

Evidence in favour of PMIC PWM for this unit:

1. The IDP blob (LCD SKU) powers a backlight supply `(3,9)`, a backlight enable `(3,3)` and muxes `pmk8550` gpio5 to `func3`. The CRD/OLED variants enable only `(3,3)`. Same pattern as the Linux reference LCD boards (`hamoa-iot-evk.dts:22-30`, `1143-1155`, `1184-1189`).
2. `PMCL` of the IDP blob has a software brightness power-state set `INTERNAL_BRIGHTNESS_POWER` / `BRIGHTNESS_CONTROL` with 4 p-states (`0x42236`, string at `0x4227b`); the CRD blob has none.
3. `SDHD` brightness code is OLED-only (strings "OLED TCON Controlled Brightness (V1/V2/V3) ... DBV", file offset `0x74328`), and the LCD TCON resources are different I2C addresses (`SSDT:1807`, `LCD0`: 0x3E, 0x44, 0x39). So the TCON does not set LCD brightness.
4. The reference LCD panel config in the DSDT (`ROM0` = `PCG1`) says `BacklightType 1`, `BacklightPmicControlType 4`, `BacklightPmicId 0`, `BacklightPmicPWMSizeinBits 12`, `BacklightPMICPWMFrequency 200`; the OLED one (`ROM1`) says `BacklightType 5` and no PMIC keys. `QCDXKM` knows the key names, including `BacklightAuxPWMSizeinBits` (file offsets `0x30f811` `BacklightType`, `0x30f856` `BacklightPmicControlType`, `0x30f9af` `BacklightPmicPWMFrequency`, `0x30fac3` `BacklightAuxPWMSizeinBits`), so the driver supports both PMIC and AUX; the type value for AUX is not decoded here.

Not excluded: that the LGD panel also advertises DPCD brightness (AUX) and that Windows could use it. No DPCD capture of this panel exists in `sources/`. The panel's DPCD `0x701`/`0x702` (and eDP 1.5 luminance registers) on the vanilla Linux boot would answer it. Also TBD: whether Windows reaches the `ROM0` template at all for this unit (depends on `TBID`, `DSDT:54799-54860`); the `INF` brightness override (`600000`) equals the `ROM0` range `0 600000 100 2`, which supports it but does not prove it. Grade: Inference (pins and sequence Verified).
