# M15.1 sensor startup logs (2026-11-01)

Worker: sensors. Sources are the read-only log snapshots `/mnt/c/sp11-logs-1/e6e73008-a91c-402d-9a6c-90d41becd4f2/` and `/mnt/c/sp11-logs-1/bddcee3c-89d3-4472-9cfc-fe27e34545c3/`; both were short debug boots (about 53 s and 100 s) and ended with orderly shutdown. No sensor raw values are copied here.

## Findings

- **Verified from journal:** each `journal.txt.gz` contains 665 `hexagonrpcd` lines matching `Could not open /persist/sensors/registry...`; 332 specifically address `/persist/sensors/registry/registry/...`. Representative requests include `sns_reg_version`, `parsed_file_list.csv`, `fstempfile`, JSON property files, `sns_reg_config`, `sns_secure_database.bin`, and `color_calibration.bin`. The daemon starts when `/dev/fastrpc-adsp` appears; ADSP is running and QRTR reports the sensor-core service. There is one clean early daemon exit/restart in the collected boot summaries; this alone does not establish a cause.
- **Verified path mismatch:** the installed `sns_reg.conf` contains `output=/persist/sensors/registry/registry`. The package's systemd root is `/usr/share/qcom/x1e80100/Microsoft/Surface-Pro-11`; its `sensors/registry` entry is a symlink to `/var/lib/hexagonrpcd/registry`. The collector sees 296 files in that parent directory, including generated seed names, while `sns_reg_config` and `parsed_file_list.csv` are absent and the secure database is only 71 bytes. This package layout puts the seed files in the parent, one directory above the configured JSON-registry output. The configuration explicitly requires a nested `registry/` directory.
- **Verified from hexagonrpc source and local write patch:** `hexagonfs_mapped.c` resolves mapped components with Linux `openat(2)`; the patched `mapped_openat()` passes the requested `O_*` flags to `openat`, which follows the filesystem symlink. `hexagonfs_openat_flags()` applies create/write flags only to the final path component. The `fopen_with_env` handler reports `Could not open <path>: <strerror>` for all open failures and does not include the requested mode in this diagnostic. Thus an ENOENT during an initial read is expected for absent state, and the journal line alone cannot tell whether an attempt to create `fstempfile` failed. The configured nested registry files are nevertheless unavailable at the path where the seed was installed.
- **Verified generator naming mismatch:** the pinned `sscregistrygen` source `tools/sscregistrygen.c` composes registry child filenames from the group name and dotted JSON key; it does not include the source JSON filename. The staged seed includes `ak0991x_0_platform.config`, while the ADSP journal requests `8380_crd_ak991x_display.json.ak0991x_0_platform.config`. Therefore the 293 generated seed files are not shown to match the paths requested by this ADSP build, even after correcting their directory. The staged seed names therefore do not satisfy those exact journal reads. The installer retains its existing seed default; both seeded and ADSP self-generation paths still require device evidence, and generated seed acceptance is unverified.
- **Verified permissions:** upstream `sscregistrygen` creates files with mode 0644. The previous installer changed staged seeds to 0640, but the private build ran as uid/gid 1000 while the image service account is 983:984; M15.1's collected rootfs confirms this mismatch. With 0640, the service could not read a staged file owned by the builder. The installer now uses 0644 for seed files, granting read access but no group/world write. The registry directory is included in the unit's nested `StateDirectory`, which is intended to be service-writable; ADSP-created files are written as the daemon. Whether the ADSP attempts to update seeded files remains unknown.
- **Inference, high confidence:** the installer's seed destination is wrong for `sns_reg.conf`; this explains at least the repeated ENOENTs for JSON entries and leaves the registry configuration unavailable to consumers. Generated seed names also disagree with requested names, making the seed route unsuitable absent a source for the expected naming scheme. The logs do not establish that every `fstempfile` ENOENT was a failed write or that this issue caused the daemon exit.
- **Unknown:** whether nested-registry correction alone makes the ADSP initialize sensors. Logs do not show `monitor-sensor` ALS/accelerometer output. `iio-sensor-proxy` owns its D-Bus name and reports zero mount matrices (falls back to identity); that does not prove it has working sensor data. These boots do not show a light reading sequence, so the reported slow auto-brightness transition has no timing evidence yet.

## Correction and safety

`sns_reg.conf` and the vendor package are read-only inputs. `sp11-sensors-install-private.sh` now installs the seed under the configured output directory `/var/lib/hexagonrpcd/registry/registry`. It retains the existing seed default. Seed filename compatibility with the ADSP parser remains unverified; the alternate empty/self-generation mode remains available for a later controlled device test. Seed files use 0644 (read-only to service users); the nested directory is included in `StateDirectory` for runtime writes. The parent remains available for separate ADSP state files; existing contents are not migrated, removed, or overwritten. Collector and read-only test output now distinguish nested registry contents from parent state files. A temporary-root install test produced 293 nested seed files at 0644 and preserved parent and nested marker files across a second install. No on-device registry or ADSP action was performed.
