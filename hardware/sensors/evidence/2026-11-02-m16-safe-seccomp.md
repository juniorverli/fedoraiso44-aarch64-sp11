# M16 safe boot: seccomp and SSC

Input: read-only `out/device-logs/m16-20261102/9e275ce6-2064-46f7-a153-b569a6f1b1a4/`, `journal.txt.gz` (monotonic seconds) and `extra-sensors.txt.gz`; kernel 7.3.0-65.sp11.15. No device actions were performed.

## Findings and grades

- **Verified:** systemd's pre-exec child emitted, among other repeated lines, `[   42.037746] localhost-live (hexagonrpcd)[7419]: hexagonrpcd-sensors.service: Failed to add filter for mkdir: Numerical argument out of domain`, followed by the same message for `mknod`, `open`, `creat` and `chmod`. It continued to `[   42.051974] localhost-live (hexagonrpcd)[7419]: hexagonrpcd-sensors.service: Executing: /usr/bin/hexagonrpcd -f /dev/fastrpc-adsp -d adsp -s -R /usr/share/qcom/x1e80100/Microsoft/Surface-Pro-11`. The earlier instance likewise executed and processed ADSP file requests. This is filter rule addition in systemd/libseccomp, not a daemon error or evidence of a kernel BPF rejection. The image has systemd 259.10 and libseccomp 2.6.1. These warnings do not show the entire filter failed or prove what rules loaded; the exact unsupported architecture/rule mapping is **TBD**. Architecture-specific syscall rewriting is a plausible explanation, not proven with the installed versions. Systemd's [seccomp implementation](https://github.com/systemd/systemd/blob/v259/src/shared/seccomp-util.c) and [libseccomp API](https://github.com/seccomp/libseccomp/blob/v2.6.1/src/api.c) describe filter construction. No weakening of sandbox directives is justified.
- **Verified:** `[   36.715095] localhost-live hexagonrpcd[4649]: Large (>256B) input buffers aren't implemented`, then `[   36.717121] localhost-live systemd[1]: hexagonrpcd-sensors.service: Main process exited, code=exited, status=0/SUCCESS (success)` and at 41.967561 a restart was scheduled. Pinned hexagonrpc 0.5.0 `hexagonrpcd/listener.c`, `return_for_next_invoke`, rejects `inbufs_len > 256`, before decoding; it does not implement retrieval of the rest. This explains the first listener's exit; its effect on SSC data and what specific call was interrupted are **TBD**. The process exit status does not imply listener success. Do not merely increase the buffer or replay `next2`: continuation protocol and limits must be established first.
- **Verified:** `[  190.415199] localhost-live systemd[1]: hexagonrpcd-sensors.service: Main process exited, code=killed, status=15/TERM (success)` follows shutdown jobs, including `Stopping dracut-shutdown.service` and `Stopping iio-sensor-proxy.service`. It is not evidence that the filter warnings killed the service. The collector ran during/after shutdown: proxy inactive and `Waiting for iio-sensor-proxy to appear`; it cannot establish whether data was available earlier. **TBD:** live accelerometer, orientation and light events.
- **Verified:** `[   36.276234] localhost-live seed-private-sensor-registry[2870]: seed-private-sensor-registry: installed 293 private seeds for the service`; on restart it reports `existing registry preserved`. The image's `image/component-inputs/private-sensors/hexagonrpcd-sensors-private-seeds.conf` targets `/var/lib/hexagonrpcd/registry/registry`; its helper installs new files 0640 owned hexagonrpcd:fastrpc. The old collector did not enumerate that child's actual ownership or count, so the on-device metadata is **TBD**, not proven by the install message. It reported parent state including `sns_secure_database.bin`, owned hexagonrpcd:fastrpc, and `color_calibration.bin`. The daemon also reports `Could not open /persist/sensors/registry/registry/8380_crd_lsm6dsv_display.json.lsm6dsv_0_platform.config: No such file or directory` and repeated `fstempfile` ENOENT. The open mode and seed-name compatibility remain unknown; ENOENT alone does not prove failed creation or failed sensor initialization.
- **Verified:** collector shows `crw-rw----. 1 root fastrpc ... /dev/fastrpc-adsp`, ADSP running and QRTR `400 1 0 5 20 Snapdragon Sensor Core service`. The local rule assigns group fastrpc and mode 0660, and the service uses that group. This establishes node metadata, not successful access to every operation. The SSC accel udev rule and proxy ordering are packaged; the capture does not record the effective udev property or live proxy data. Four proxy `Mount matrix provided by firmware is all 0, falling back to identity matrix!` messages do not identify SSC and cannot establish correct orientation.
