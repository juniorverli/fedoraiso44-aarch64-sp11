## PHY integration skeleton if a front-only failure is demonstrated

Reference `phy/` is coupled to a jglathe-only generic-PHY refactor; copying its files, DT or module parameters into v7.3 will not integrate. First obtain sensor-identified front vs rear and GPU-only A/B, active clocks and IRQs. If evidence isolates legacy C-PHY, kernel/sources owners should pin and review the posted C-PHY/generic-PHY series identified in `2026-11-02-upstream-windows-gap.md`, reconcile dependencies and attribution, and build these distinct reviewable commits (skeleton, not tested patches):

1. **Bindings/API:** define and review generic PHY C-PHY configuration (trio count/map, symbol-rate units and settle), ownership and separate X1E80100 provider schema; preserve old CAMSS bindings/DT ABI. Do not repurpose D-PHY semantics or global force flags. Confirm exact upstream API version, clock/PM and error unwinds.
2. **Provider infrastructure/D-PHY:** introduce dependency-compatible generic CSI2 PHY core with matching Kconfig/Makefile, clocks, regulators, domains, reset, IRQ, runtime PM and lifecycle. Backport only required interfaces. Make legacy and generic PHY exclusive owners of every MMIO window/IRQ/clock; no duplicate `devm_ioremap_resource` or double PM vote. Validate rear D-PHY first against rev23.
3. **C-PHY hardware:** review independently sourced GPL-2.0 2.1.2 table provenance and each offset/order, active-trio clock gating, reset assert/release, barriers, delays, bounded failure handling and rate/settle mapping; use actual DT endpoint and explicit provider mode. Differentially audit 0009 all-trio writes and reference register sequence without copying tables blindly. Keep debug parameters and sweeps out of production; no device MMIO when clocks off.
4. **CAMSS consumer:** bridge media graph lane mapping and selected link frequency to generic PHY; acquire/init/configure/power and unwind correctly under streaming/refcounts; retain 0007/0008/0010 where applicable, remove overlapping legacy 0009/0023 code only after equivalent PM/clock and header behavior is demonstrated. Avoid simultaneously driving both providers.
5. **DT:** split CSIPHY windows, interrupts, clocks and top domain from CAMSS to individual enabled provider nodes, connect named `phys`; preserve physical csiphy2/front, csiphy1/rear, front C-PHY trio 0 and sensor privacy LED graph. Handle actual provider numbering, clocks/voltages and bindings from pinned SoC documentation, not hardcoded reference phandles. Keep IR absent and flash/illuminator off. Run `dtbs_check`, inspect effective graph and validate no overlapping resources.
6. **Validation:** build full integration with BTF and W=1/checkpatch; test PM fault/unwind, repeated starts/stops, rear D-PHY and front C-PHY in matched boots with LED, active clocks, SOF/EOF and IRQ/error counters, data layout and reset-resilient logs. Cross-check safety values before promotion. Reference's userspace `force_cphy`, runtime sweeps, hardcoded DT and Windows data are not an upstream integration.

**Decision:** plan a standalone-PHY port as a contingency, but rev24 does not yet have evidence to require it or to claim that 0024/0025/line length fix a reset. First isolate the failure with unmodified rev23 control. If a front-only hang lands inside legacy PHY programming, prioritize a narrowly audited legacy fix or the clean standalone port; if SOF/drop or VFE violations appear with stable clocks, stage the respective receiver patch separately. If GPU-only resets, continue GPU/PM investigation. The working reference strengthens front-PHY investigation but differs in kernel, sensor timing, API and tuning.

## Front sensor and private-data request

The rev22 manifest (`out/firmware-private/cameras/MANIFEST.json`, front SHA-256 `095823de119975b778b536dd9eef4b535a2780e4ccbffb1d6e8490c33e0d52f5`; installed full hash still TBD) has four RGGB10 modes 3840x2640, 3840x2160, 3520x2640 and 3660x2440, all HTS 6752, VTS 3554, pixel-rate field 548570000, link frequency 1200000000, one trio. `0016` reports a derived line clock `pixel_rate * 1000 / 762` (~719.91 MHz), an inference requiring measurement; baseline calculated fps ~30.0. It reports HBLANK 2912 for 3840 and VBLANK 914/1394 for the respective heights. The sensor's timing register is loaded from the private mode ops while 0016 advertises HTS from blob metadata; both must agree. Reference's 7552→8704 was for its 3844x2640 alternative table/PLL; its Windows-mode 3840x2160 path is distinct, and its own dossier says the Windows PLL did not lock with its AFE setup. It does not establish that our HTS 6752 is wrong. The reference mode and our 3840x2160 selection are not interchangeable.

**Request to kernel/image:** preserve baseline blob; once stable front receive shows line loss/overflow and timing is measured, prepare one private, separately named test blob from the exact current front blob with only 3840x2160 mode line-length register *and its HTS metadata* changed together from 6752 to 8704, leaving VTS 3554, pixel-rate field, PLL, C-PHY clocks, Bayer, all other modes and tuning unchanged. At the current inferred line clock that implies HBLANK 4864, line period ~12.09 us and ~23.27 fps, versus ~9.38 us/~30.00 fps baseline; actual line clock and FPS must be verified. Preserve mode op order, CRC, hashes and private provenance; reject if no unique verified line-length pair or if another later op overwrites it. Compare active SOF cadence, packet errors, frames/stride and loss under same scene and mode. This is a controlled experiment, **not a recommended default nor a copy of 7552→8704**, and must not be run before the reset and safety gates permit. Reconcile exposure in lines and frame interval in IPA when changing HTS; do not change VTS to hide the effect.

Gain claims conflict within the reference: README and historical `docs/dossier-en.md:65` say analogue code zero is maximum; checked-in `ccs/ccs-core.c:801-825` says measured 0 versus 960 had no effect and redirects V4L2 analogue control to digital U8.8 1–16x, while the dossier's first section reports even 15x digital had no effect in an earlier configuration. Our 0016 and `userspace/quality/libcamera-sp11-imx681-helper.patch` assume `512/(512-code)` with code 0..479 and global digital 0x020e, explicitly unverified. Do not invert, remap analogue to digital globally, or replace CCS with reference code on these conflicting assertions. Once safe, measure controlled manual gain/exposure sweeps on uniform unsaturated RAW at fixed light, record requested/reported values, measured channel response and frame delay, and independently check controls/readback without raw register pokes. The reference CCS has static limit fixes, custom control and mode logic, while ours uses private firmware ops and separate driver; cross-check actual hardware behavior before changing either.

## Userspace and LED

Reference `userspace/libcamera/BASE.txt` pins v0.7.0, while our image logged 0.7.2. Its patch changes global soft AGC target from 2.5 to **3.5** (comment incorrectly says 3.1) and allows tuning gamma/contrast/saturation defaults. Our `userspace/quality/libcamera-sp11.patch` already adds range-clamped gamma and rear black fallback; it does not implement the other two adjustments or change AGC target. Reference YAMLs include Windows-derived CCMs; our private generator already produces approximate sensor YAML/CCM. Image owner should first verify Fedora package build and IPA/helper/tuning hashes, packed RAW support and actual renderer; reproduce at fixed settings, collect RAW dark/flat/colour target, metadata and convergence. Then experiment with target 3.5 as an isolated private IPA A/B against 2.5, tracking clipping and latency, followed by measured sensor-specific AWB/CCM, gamma, black and contrast/saturation tuning; do not copy factory values into git or force global brightness as an unmeasured fix.

Reference `userspace/pipewire/sp11-camera.conf` disables `MemoryDenyWriteExecute` for a service based on its llvmpipe JIT diagnosis. Our failure is WirePlumber/llvmpipe, and it has not been established to share that protection or fault mechanism. Image owner should identify the exact crashing unit, service hardening, coredump signal/address/maps and Fedora Mesa/LLVM/PipeWire versions, verify whether a JIT execute denial occurred, and first A/B the rev23 safe-only softpipe wrapper against unchanged rev22/23 baseline. Only if verified, test a narrowly scoped service override, record security tradeoff; don't copy the drop-in blindly. Its heal unit restarts PipeWire on broad log matches and can mask failures; do not import it for reset diagnosis.

Reference `userspace/systemd/sp11-camera-led.sh` polls ISP runtime PM once per second and backgrounds timed GPIO writes, interpreting read failures as suspended; delayed transitions, runtime activity unrelated to streams, crashes, suspend and shared ownership make it insufficient to enforce our per-stream LED gate. Do not import that service, startup script or GPIO overrides; keep V4L2 core/shared LED refcount (0020) and verify actual physical mapping/on-before-or-at-stream/off-after-last stream per our safety plan. No IR or flash.
