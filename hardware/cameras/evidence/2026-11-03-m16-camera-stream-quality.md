## Brightening and image quality

- **Verified source, unknown runtime:** OV13858 has exposure, analogue and digital gain and VBLANK controls (`sources/linux/drivers/media/i2c/ov13858.c:58-76,1211-1255,1606-1619`); exposure is in lines, maximum `height + vblank - 8`, minimum 4, nominal default 1600 lines; the gain code defaults to 128. Patch 0013 also adjusts mode-dependent timing. Limits and defaults do not show whether AGC reached a limit or how long it took. Digital gain is present in the kernel; it is not evidence that SoftISP uses it. No run-time exposure, gain, frame-duration, scene luminance, or per-frame metadata is captured. `No sensor delays found ... Assuming unverified defaults` appears at 20079066 line 1837; wrong control delay could cause transient AE errors, but the timing and sign are **Hypothesis**. Distinguish gradual AGC convergence, capped exposure/gain, incorrect line-time calculation, low frame rate, missing AE feedback, and display adaptation with a fixed-lit target and per-frame data. A tuning file being selected does not prove that its algorithms ran or its coefficients are correct.
- **Verified in a local reference, installed version TBD:** `out/ref/libcamera/src/ipa/simple/algorithms/agc.cpp:68-124,128-192` (SHA-256 `90614965bf1bf05681c6d6dc925e2029a869fa3545908dfea187cd5e2b82a4b7`) adjusts exposure first and then analogue gain in bounded per-frame steps based on histogram statistics, and emits exposure/gain metadata. Invalid statistics retain the preceding values. A many-frame brightening transient is therefore plausible if that implementation is running; this reference is not established as the exact shipped IPA, and no convergence series is logged. Match the packaged source/build first; neither its step size nor the reported gradual brightening alone proves the cause.
- **Verified source — tuning is approximate, runtime unverified.** The private tuning generator `userspace/quality/build-libcamera-tuning.py:1-28,395-419` emits BlackLevel, Awb, optional Ccm and Adjust/gamma, and Agc; its conversion reduces four black channels to one, selects CCM by colour-temperature band at one lux bin, approximates a LUT with a power curve, and omits Windows lens shading, AWB reference points, denoise, sharpening, local tone mapping, HDR and AEC. `userspace/quality/libcamera-sp11.patch` provides a gamma reader and a fallback black level; the selected pathname proves neither deployed YAML content nor that the matching patched IPA/helper interpreted it. Do not publish private tuning values (S5). Verify installed package build and tuning hash privately; compare rendered patch-chart and flat-field frames with fixed conditions. Missing or approximate stages are plausible contributors, not a demonstrated cause or a quantified Windows comparison.
- **Verified defect, unquantified effect:** rear libcamera reports missing native-size, crop-bounds and crop selection targets and defaults array/active area to 4224x3136 and analogue crop to active size (20079066 lines 1828-1835,1845-1846). No `.get_selection` exists in the base OV13858 pad ops (`sources/linux/drivers/media/i2c/ov13858.c:1525-1530`); patch 0013 adds blob modes but no selection API. Crop metadata may misstate field of view, scaling and metering; the warnings alone do not prove that pixels were cropped or degraded.
- **Inference:** interpreting BGGR blob-mode RAW10 as GRBG, or using an incorrect bit depth, would seriously harm colour. Base driver reports GRBG10 (`ov13858.c:1276-1285`); Windows-derived modes report BGGR10 by patch 0013 and prior cross-check `2026-10-31-bayer-units-gain-crosscheck.md:9-39`. Actual sensor output and app mode remain unmeasured; inspect RAW and negotiated bus formats before changing Bayer order. Blob timing estimates have an identified ~9.6% discrepancy against Windows mode arithmetic in that cross-check §2, not a proven runtime frame rate; determine actual SOF cadence and exposure-line units before changing timing.
- **Inference:** absence of a bound lens/actuator driver can explain poor focus if this module requires active focus, but no focus sweep, lens position, sharpness target or PDAF test is recorded. Linux has no implemented PDAF/AF or multi-exposure HDR path here; whether these explain a particular comparison is **TBD**. Resolution, fps, motion blur, lighting and exposure need matched Windows/Linux captures before ranking causes.

Extend mode/blob metadata if needed. Add enumeration and mode-switch tests that check coordinates, Bayer parity and consistency with RAW captures; reject unsupported targets. Until geometry is established a plausible-looking full-output rectangle would conceal the defect. No hardware geometry value is ready for an independently cross-checked patch.
2. **Front enumeration proposal:** run `python3 -I hardware/cameras/userspace/build-camera-firmware.py imx681 --ccs-controls --again-range 0:479:1:0` in the image build's private staging area. It emits exposure, analogue-gain and frame-length records; the 0016 driver supplies its own gain limits and only instantiates gain/digital gain when a gain record exists. The register choices are CCS-based **Inference**, the 0–479 reciprocal gain law comes from prior Windows analysis and remains physically unverified (`2026-10-31-bayer-units-gain-crosscheck.md:120-129`); exposure/frame limits and timing also need measured validation. At boot confirm full installed hash, driver version and `v4l2-ctl -d <front-subdev> -L` shows exposure/analogue gain and bounded frame length, then `cam -l` lists both. This is the right next enumeration experiment, not proof that streaming, controls or front image quality work. No regeneration or ISO build was performed in this worker session.
3. **Userspace:** retain current tuning and helpers as a baseline; verify the packaged IPA actually contains both image patches and records per-frame AE/AWB/gamma controls, gain mapping, timings and tuning file hash.
