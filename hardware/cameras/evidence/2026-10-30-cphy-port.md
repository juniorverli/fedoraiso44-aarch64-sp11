# Cameras: C-PHY support for X1E80100 in upstream CAMSS (patches 0006 to 0010)

Date: 2026-10-30. Static work plus a cross-compile of the camss objects. No device access, no REA
call, nothing booted. The front IMX681 is the only known C-PHY user and has no driver, so no
C-PHY link can be exercised even on the device yet.

## Correction to the earlier reference note

The earlier note puts the CSID PHY-type logic in `camss-csid-gen3.c`. The X1E80100 CSIDs use
`csid_ops_680` (`camss.c` `csid_res_x1e80100`, `.hw_ops = &csid_ops_680`), so the file is
**`camss-csid-680.c`**, which already defines `CSI2_RX_CFG0_PHY_TYPE_SEL` as 24 and never uses it
(Verified: `camss-csid-680.c:105`). `camss-csid-gen3.c` serves other SoCs and was not changed.

## Inference

| Statement | Reasoning | What would change it |
|:--|:--|:--|
| Link frequency of a C-PHY sensor is `symbol rate / 2` (V4L2 defines `V4L2_CID_LINK_FREQ` as `1/(2*UI)`, and the C-PHY UI is a symbol); the symbol rate is `2 * link_freq`, the bit rate per trio `symbol rate * 2.28` | the control definition; a sensor driver that reports another convention would select the wrong rate class. The IMX681 driver does not exist yet | the IMX681 driver, and a measured clock |
| When the sensor offers only a pixel rate, `link_freq = pixel_rate * bpp / (2 * trios * 2.28)`, coded as `mul = bpp * 25`, `div = 2 * trios * 57` | the same definition; uses the 16 bits in 7 symbols ratio of C-PHY | none expected |
| CSIPHY and CSID clocks are chosen from the bit rate of a lane (`link_freq * 57/25` for C-PHY, then the existing `/ 4` rule). That is the D-PHY link frequency with the same bit rate | the D-PHY code derives both clocks from the lane bit rate; the C-PHY bit rate is the reference's `2.28 bits/symbol` | a CSID or CSIPHY clock too slow or too fast at high symbol rates |
| The settle count of the reference class tables is the right value | the reference lets user space overwrite it, but the table value is the default and matches the Windows table at 2.5 Gsym/s (0x22) and at the 500, 600, 700, 800 and 900 Msym/s bounds. The Windows table is binned slightly differently (for example 57 against 60 below 1 Gsym/s, whose provenance is a decompile that is not copied) | a link error at the affected classes |
| The reset hold and release (`0x1000` = 1, then `0x0e` and 3.048 ms) is needed even though the driver already resets the block at power-on | copied from the reference, which does it for every C-PHY start. D-PHY uses 0 and no release on this driver | a PHY that locks without it |
| The IRQ masks may stay disabled | the D-PHY path does; the reference enables them for diagnostics only | none |
| Only one of the data-lanes positions (0 to 2) per trio and no clock lane: the three trio banks are always programmed, the enable bits choose the used ones | the reference programs all three banks for any trio count | a trio that interferes when not enabled |
| `data-lanes = <0 1 2>` maps trio positions 0 to 2 to CSID lane routing 0 1 2 through the existing `csid_get_lane_assign()` | the same code serves D-PHY positions; `lane_assign` nibbles are the positions | a swapped trio on the board |

## Unknown, only hardware can confirm

1. A C-PHY link has never run: the sequence is verified against the reference text, not against a
   PHY that locks. The front IMX681 (CSIPHY index and trio count from the Windows data, 3 trios
   expected) cannot be used before its driver exists, so the first test needs that driver or a
   C-PHY capable test source.
2. Whether CSID `CFG0` bit 24 alone suffices on CSID 680 (the reference also sets lane count and
   routing, which the driver does).
3. The CSIPHY and CSID clock sufficiency at the symbol rate the IMX681 modes use.
4. The settle count at each class (the reference's per-class values, not a Windows or measured
   value) and the 3.048 ms release wait.
5. Trio polarity and line order: no register is known, so non-default values are rejected, not
   programmed. A board with a swapped trio needs a measurement.
6. The CSIPHY clock and CSID timing for the pixel-rate fallback of the link frequency (only used by
   a sensor driver without `V4L2_CID_LINK_FREQ`).
7. Whether the X1E80100 CSIPHY index used by the front camera shares the C-PHY registers: the table
   is per block, so every CSIPHY of the SoC gets the same sequence (the reference's table has no
   per-instance difference for v2.1.2, but combo mode with D-PHY on the same CSIPHY is not
   supported by this patch and not tested).

## Not done

- `camss-csid-gen3.c`, `camss-csid-gen2.c` and the 2ph CSIPHY driver are untouched; other SoCs
  reject C-PHY in the parser ("C-PHY is not supported on this SoC").
- No combo mode (D-PHY plus C-PHY on one CSIPHY), no CDR sweep, no BIST, no skew calibration of the
  D-PHY side.
- No DT node uses C-PHY: the front camera node waits for the IMX681 driver.
