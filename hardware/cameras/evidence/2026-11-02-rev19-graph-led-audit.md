## Compiled graph

Verified against the decompiled staged safe DTB `out/image-work/l0-sp11-fedora44-aarch64-kiwi-20261102T210101Z-private/s1-safe-x1p64100-microsoft-denali-m15-safe.dtb.dts`; the corresponding rev19 DTB and staged DTB have SHA-256 `0f7c340e5455a7207bbc1214c3dc7ac9f611485edb24e2e1872b53d8bf3abf26`. Rear endpoint phandle 0x11d points to CAMSS endpoint 0x114, which points back to 0x11d. Front 0x11e points to CAMSS 0x11a, which points back to 0x11e. CAMSS has only ports 1 and 2; IR has no port, and IR and CCI0 bus 0 are disabled. Both RGB buses and CAMSS are enabled; RGB sensor nodes inherit enabled status. No conclusion is made about an independently substituted runtime DTB.

`sources/linux/drivers/media/platform/qcom/camss/camss.c:4743` and patch 0010 parse *each CAMSS-local endpoint*, add its remote endpoint to the async notifier, and assign `vep.base.port` as the CSIPHY array index. `csiphy_res_x1e80100` at `camss.c:4190` is ordered 0, 1, 2, 4; ports 1 and 2 thus select CSIPHY1 and CSIPHY2. Both indices are valid. On a successful match, bound assigns the PHY; complete creates immutable enabled sensor-source-to-CSIPHY-sink links and registers subdev nodes (`camss.c:5167-5220`). Notifier completion requires all connections and child notifiers, and may fail for other runtime errors. A sensor I2C driver bound alone is insufficient proof.

`video-interfaces.yaml:87,159` defines bus 1 as C-PHY, 4 as D-PHY, and lane entries as local physical positions in logical order. The parser `v4l2-fwnode.c:124-250` parses each end independently and does not compare the ends. No explicit clock-lanes exists, so the CAMSS D-PHY parser retains default clock position 0 without treating data position 0 as duplicate: the duplicate check is conditional on an explicit clock property. CAMSS retains data positions 0,1,2,3 for rear, and 0 for front; patch 0010 accepts C-PHY trio 0 with default polarity and ABC line order. On streaming, `camss-csid.c:1226` uses the local positions as lane assignment and CSIPHY uses them for lane masks (`camss-csiphy-3ph-1-0.c:1114`, patch 0009). It does not substitute sensor-local positions. Thus the differing lane numbers do not block notifier completion and are not evidence of an incorrect mapping; actual physical mapping, C-PHY sequence and resulting pixels remain unverified. The sensor endpoints and connection counts match their local binding examples in patches 0001 and 0015. OV13858 patch 0002 checks D-PHY, four lanes and frequencies; IMX681 patch 0016 checks C-PHY, 1–3 trios, frequency and blob mode count, not equality of remote lane values. Pinned mainline has no X1 camera DT; its `apq8016-sbc-d3-camera-mezzanine.dtso:46-85` demonstrates different local numbering on the two ends. This older example is not proof of this board's wiring; newer standalone-PHY proposals use a different API and should not be mixed mechanically with the legacy driver.

Both sensors set `V4L2_SUBDEV_FL_HAS_DEVNODE` and call `v4l2_async_register_subdev_sensor` (base `ov13858.c:1700-1713`, patch 0016). Successful sensor registration creates async subdevs; `/dev/v4l-subdev*` requires successful CAMSS completion, subdev-node registration and `CONFIG_VIDEO_V4L2_SUBDEV_API`. Nodes and internal CAMSS video entities alone do not prove both sensor links. Device numbers, ordering, default mutable downstream links and libcamera enumeration vary.

## LED

The compiled enabled `camera-leds` has GPIO225 node phandle 0x10d and GPIO105 node 0x113, both active high; front references 0x10d and rear 0x113, each named `privacy`. The disabled IR node also references 0x10d; hence patch 0020 shares front/IR classdev, not front/rear. The bundle `leds.txt.gz` shows `white:indicator` and `white:indicator-1`, both zero at collection, with matching OF node names: classdev registration is evidenced, physical LED and mapping are not. GPIO225/front and GPIO105/rear identities and polarity remain inference, not verified, pending independent hardware cross-check; see `2026-11-01-shared-privacy-led.md` and `2026-10-30-rea-seven-questions.md`.

`v4l2-fwnode.c:1261-1305` requests `led_get(..., "privacy")` during sensor async registration, before attachment and notifier completion; failed registration releases it. Missing CAMSS completion does not itself prevent an already registered sensor requesting its LED. Patch 0020 registers per-classdev shared bookkeeping when acquired, it does not register the GPIO LED classdev; first acquisition sets brightness zero. The legacy `call_s_stream` wrapper calls the sensor first and lights the LED only if start succeeds (`v4l2-subdev.c:475-505`); native streams have corresponding success handling. Therefore a dark LED is consistent with no successful wrapped sensor start, a start failure, an LED acquisition/configuration problem, or incorrect physical wiring; it does not prove absence of a link or rule out a sensor start that failed. No streaming is authorized until privacy indication is established.

## Decision

No concrete DT/driver defect established; no patch. Capture the read-only commands in `test-plan.md` on the current ISO. If CAMSS is absent, inspect probe/deferred errors and resources. If CAMSS internal entities exist but either sensor or immutable enabled sensor-to-correct-PHY link is absent, inspect sensor async registration, firmware, endpoint matching, child notifiers and completion failures. If both links and subdev nodes exist but `cam -l` lacks a camera, inspect libcamera pipeline, sensor helper, IPA and logs. If both enumerate but preview is black, inspect stream-start return/errors, media routing/formats, CSIPHY/CSID IRQs, buffers and SoftISP; the graph alone cannot certify frames. If a successful sensor start is independently demonstrated while the LED is dark, investigate LED acquisition, brightness and wiring; do not stream further until the indicator is reliable. Never enable IR illuminator or flash.
