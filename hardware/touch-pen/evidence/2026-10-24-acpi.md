## Namespace and controller

**Verified:** the DSDT contains `\_SB.SP11`, HID `QCOM0C0E`, subsystem
`MSHW0489`, UID `0x0b`, description `QUP_1_SE_2,QSPI`, `_CCA=0` and dependencies
on PEP0, QGP1 and MMU0 (A:51534–51546). `_CRS` declares MMIO `0x00a88000`,
length `0x4000`, and interrupt `0x342`, level/high/exclusive (A:51547–51561).
There are no controller-local `_PS0`, `_PS3`, `_RST` or `_DSM` in this device.

**Inference:** this is Linux `spi10`, QUP wrapper 1 engine 2, from the identical
MMIO range and its `GCC_QUPV3_WRAP1_S2_CLK`
(`sources/linux/arch/arm64/boot/dts/qcom/hamoa.dtsi:1689`). ACPI GSI 834
(`0x342`) corresponds to DT `GIC_SPI 802`, after subtracting the 32 private
interrupt numbers; the DT independently declares 802 at `hamoa.dtsi:1693`.
`spi10` is a DT label, not a promise about the Linux runtime bus number.

**Verified:** the touch device is `\_SB.GTCH` in the **SSDT**, under the
`TBID != 0x10` branch (B:1422, B:1547). `_HID` returns the nine-byte string
in the `SHSD` NVS field, not a literal ID (B:1551). SHSD is at MNVS offset
`0x0d`, length 72 bits (B:204–213); its runtime contents are not in the ASL.
`_CID=PNP0C51`, `_HRV=1`, `_S0W=2`, dependencies GIO0/SP11, `_STA=0x0f`,
and `_S1D/_S2D/_S3D=3` are declared at B:1556–1563 and B:1691–1708.

**Inference:** GTCH is the inventory's MSHW0484 device: C:2854–2855 reports
that ACPI HID with revision 1, while C:2766–2767 reports the matching QCOM
controller and subsystem. The dynamic SHSD bytes and TBID value were not
captured, so the namespace-to-ID association is not independently Verified.

## Direct GPIO operations and timing

**Verified:** GTCH defines GI64 at physical `0x0f140000`, GI48 at
`0x0f130000`, each length `0x18`. VCFG/RCFG occupy offset 0; VSTE/RSTE
occupy offset 4, DWordAcc/NoLock/Preserve (B:1669–1688).

**Inference:** VCFG/VSTE control TLMM GPIO 64 and RCFG/RSTE control GPIO 48.
The TLMM base is `0x0f100000`
(`sources/linux/arch/arm64/boot/dts/qcom/hamoa.dtsi:6095`), stride `0x1000`,
I/O offset 4, output enable bit 9 and output-value bit 1
(`sources/linux/drivers/pinctrl/qcom/pinctrl-x1e80100.c:12`, :32–44).
Thus `0x0200` configures GPIO output with no pulls and `0x02` drives high;
zero drives low. GPIO 48 is active-low reset because `_RST` pulses it low;
GPIO 64 is an active-high power enable because `_PS0` raises it before
releasing reset, while `_PS3` lowers it after asserting reset.
Physical supply voltage, regulator identity and parent supply remain **TBD**.

| Method | Verified actions, in order | Evidence |
|:--|:--|:--|
| `_INI` | RSTE=0; if VSTE bit 1 is clear: VCFG=`0x200`, VSTE=2, sleep `0x0a` ms (10 ms); RCFG=`0x200`, RSTE=2 | B:1711–1724 |
| `_PS0` | If VSTE bit 1 is clear: VCFG=`0x200`, VSTE=2, sleep `0x01f4` ms (500 ms); RCFG=`0x200`, RSTE=2 | B:1726–1738 |
| `_PS3` | RSTE=0, sleep `0x0a` ms (10 ms), VSTE=0 | B:1740–1745 |
| `_RST` | RSTE=0, sleep `0x012c` ms (300 ms), RSTE=2 | B:1747–1752 |

Decimal delay conversions are **Inference** from the Verified constants.
The 500 ms wait is conditional on power having been off, not unconditional
on every D0 transition. `_PS0` itself does not first force reset low;
normal sequencing relies on the previous state. `_INI` uses a distinct 10 ms
initialization delay; it is not evidence that the 500 ms D0 delay can be shortened.

**Verified:** the same SSDT's PEP LPXC data describes GTCH D0 as TLMMGPIO
`0x40` value 1, DELAY `0x0a`, TLMMGPIO `0x30` value 1, and D3 as GPIO `0x30`
value 0, DELAY `0x0a`, GPIO `0x40` value 0 (B:1424–1544). D1 and D2 carry no
extra operations. **Inference:** these reinforce the power/reset roles;
the units and complete six-field TLMMGPIO package semantics are not decoded
here. They do not supersede the explicit `_PS0` 500 ms sleep.

## GTCH `_DSM`

All raw results are **Verified**, UUID
`6e2ac436-0fcf-41af-a265-b32a220dcfab` (B:1595–1667).

| Revision | Function | Return type/value | Meaning |
|--:|--:|:--|:--|
| 1 | 0 | Buffer(1) `03` | Functions 0–1 supported, Inference |
| 1 | 1 | Integer `1` | Legacy semantics TBD; **not** a proven HID descriptor address |
| 3 | 0 | Buffer(1) `7f` | Functions 0–6 supported, Inference |
| 3 | 1 | Integer `0x1000` | Input report header address |
| 3 | 2 | Integer `0x1004` | Input report body address |
| 3 | 3 | Integer `0x2000` | Output report address |
| 3 | 4 | Buffer(1) `eb` | Read opcode |
| 3 | 5 | Buffer(1) `e2` | Write opcode |
| 3 | 6 | Integer `0xa000` | Quad mode for reads **and writes**, see below |
| Other UUID/revision/function | any unsupported | Buffer(1) `00` | Unsupported fallback |

Address/opcode semantics are **Inference** from the public specification
section 5.2.2, pages 15–16, and agree with v6 patch 07's ACPI implementation.
There is no separate HID descriptor-register address returned here: the
transport requests the device/report descriptors through HID SPI messages.

The downloaded [Microsoft HID-over-SPI specification 1.0](https://download.microsoft.com/download/c/a/0/ca07aef3-3e10-4022-b1e9-c98cea99465d/HidSpiProtocolSpec.pdf)
has SHA-256 `b1e7080c880c6328dcd102c52115bfe9fe9bb21353c64214f64496bb9c73f87b`
and is retained outside git at `out/build/touch-pen/HidSpiProtocolSpec.pdf`.
This external input still needs the sources owner's central pin.

**Verified (specification, p.16):** flag bit 13 selects multi-SPI writes;
bits 15:14 select single=0, dual=1, quad=2. **Inference:** `0xa000` has bit
13 set and bits 15:14 equal 2, requiring quad reads and quad writes. Section
4.1, p.12 requires the opcode on one data lane and the remaining address/data
on the selected multiple lanes. Consequently the FourWireMode resource must
not be interpreted as proof that ordinary single-data-lane SPI will work.
