## 1. SE index and personality (README Q1)

**Value.** The touch/pen SPI controller is `\_SB.SP11`, `_HID` `QCOM0C0E`, `_SUB` `MSHW0489`, `_STR` `"QUP_1_SE_2,QSPI"`. That is QUPv3 wrapper 1, serial engine 2, QSPI personality.

Supporting facts:

- `dsdt.dsl:51534-51561`: `Memory32Fixed 0x00A88000, length 0x4000`; `Interrupt Level ActiveHigh 0x342`. 0x342 = 834, so GIC SPI 802. `hamoa.dtsi:1689-1693` has `spi10: spi@a88000` with `GIC_SPI 802`, and `hamoa.dtsi:1655` has `i2c10` on the same address. Clock `GCC_QUPV3_WRAP1_S2_CLK` (`hamoa.dtsi:1695`). The parent node is `qupv3_1: geniqup@ac0000` (`hamoa.dtsi:1492`).
- `surface_spiext_den8380.inf` is an Extension INF matching `ACPI\VEN_QCOM&DEV_0C0E&SUBSYS_MSHW0489`. It sets `QSPIBinaryPath` to `BSRC_QSPI_DEN.bin`. The base `qcspi8380.inf` supplies both `SPIBinaryPath` and `QSPIBinaryPath`.
- In `BSRC_QSPI_DEN.bin`, node `\_SB.SP11` (string at file offset `0x5a2d`, node size 2599 bytes) uses `gcc_qupv3_wrap1_s2_clk` and 6 TLMM pins. The ordinary SPI policy `BSRC_SPI.bin` has only 4 pins for `SP11`.
- Pattern in the generic QSPI policy: in each QUP wrapper, SE2 and SE3 carry 6 pins (SPI3, SPI4, SP11, SP12, SP19, SP20) and all other SEs carry 4. So quad-capable engines look like SE2/SE3 of each wrapper. This is Inference.

Grade: SE index, base address, IRQ, clock = **Verified** (ACPI plus Linux DT). QSPI personality = **Verified** that Windows treats the device as QSPI (`_STR`, extension INF, 6-pin policy). That the same SE must be programmed for a QSPI protocol on Linux is **Inference**.

**Protocol number: TBD.** Nothing in ACPI or INF states the numeric GENI protocol of the QSPI personality. Linux v7.3 defines only `GENI_SE_NONE=0, SPI=1, UART=2, I2C=3, I3C=4, SPI_SLAVE=5` (`include/linux/soc/qcom/geni-se.h:33-40`; names at `qcom-geni-se.c:125`). There is no QSPI enumerator anywhere in `drivers/soc/qcom/qcom-geni-se.c` or `drivers/spi/spi-geni-qcom.c`. What would answer: the compare in `qcspi8380.sys` against the `GENI_FW_REVISION_RO` protocol field (`0xA88068`, bits 15:8; `geni-se.h:369-376`), or the controller-only diagnostic boot on the device reading that register.

## 4. Reset and shutdown timings (README Q3)

`GTCH` accesses the TLMM through two memory regions (`ssdt.dsl:1669-1688`). The TLMM base is `0x0F100000` (`dsdt.dsl:55541`, `hamoa.dtsi:6095-6097`) and each GPIO has a `0x1000` stride, with CFG at `+0` and IN/OUT at `+4` (`pinctrl-x1e80100.c:32-33`).

| Region | Address | GPIO | Role |
|:--|:--|:--|:--|
| `GI64` (`VCFG`, `VSTE`) | `0x0F140000` | 64 | power / shutdown control |
| `GI48` (`RCFG`, `RSTE`) | `0x0F130000` | 48 | reset |

Register decode from Linux: in the CFG register `0x0200` = bit 9 (`oe_bit = 9`) with function 0 (`mux_bit = 2`), no pull, drive 0. In the IN/OUT register bit 1 is the output level (`out_bit = 1`): `0x02` = high, `0x00` = low (`pinctrl-x1e80100.c:20-45`, macro fields). So `VSTE = 0x02` drives GPIO 64 high and `RSTE = 0x02` drives GPIO 48 high.

| Method | Sequence (from `ssdt.dsl`) | Lines |
|:--|:--|:--|
| `_INI` | GPIO 48 low; if GPIO 64 not high, configure as output, drive high, `Sleep 10 ms`; configure GPIO 48 as output and drive high | `1711-1724` |
| `_PS0` | if GPIO 64 not high, configure as output, drive high, **`Sleep 500 ms`** (`0x01F4`); then configure GPIO 48 as output and drive it high (reset released) | `1726-1738` |
| `_PS3` | GPIO 48 low; **`Sleep 10 ms`**; GPIO 64 low | `1740-1745` |
| `_RST` | GPIO 48 low; **`Sleep 300 ms`** (`0x012C`); GPIO 48 high | `1747-1752` |
| `_S1D`, `_S2D`, `_S3D` | `3` (D3) | `1696-1710` |
| `_S0W` | `2`; `_HRV` = 1 | `1557-1558` |

- No delay follows the release of reset in `_PS0`, `_INI` or `_RST`.
- PEP policy for `\_SB.GTCH` (`ssdt.dsl:1432-1534`): D0 = GPIO 64 entry, `DELAY 0x0A`, GPIO 48 entry; D3 = GPIO 48 entry, `DELAY 0x0A`, GPIO 64 entry. The unit of the PEP `DELAY` is not stated; its order matches `_PS3` (reset first, then power), which supports a 10 ms reading (Inference).
- `GpioIo` in `_CRS` declares only pin 64 with `PullDown` (`ssdt.dsl:1578-1583`). GPIO 48 is not in `_CRS`; it is reached by direct register access.

Conclusions:

| Item | Value | Grade |
|:--|:--|:--|
| Reset line | GPIO 48, reset asserted when low, deasserted when high | Verified register sequence; "active low" is Inference |
| Power / shutdown line | GPIO 64, high = powered, `PullDown` default off | Verified register sequence and `_CRS`; polarity name is Inference |
| Reset pulse low time | 300 ms | Verified (`_RST`) |
| Power-on wait after raising GPIO 64 | 500 ms in `_PS0`; 10 ms in `_INI` | Verified |
| Power-off order and gap | GPIO 48 low, 10 ms, GPIO 64 low | Verified |
| Wait after reset release before first SPI transfer | none in ACPI | Verified absence; the value Windows `hidspi.sys` waits is TBD |

## 5. Interrupt GPIO and trigger (README Q2)

`_CRS` of `GTCH` (`ssdt.dsl:1565-1593`), in order:

1. `SpiSerialBusV2` on `\_SB.SP11`.
2. `GpioInt Edge, ActiveLow, ExclusiveAndWake, PullNone`, pin `0x0033` = **GPIO 51**, `\_SB.GIO0`.
3. `GpioIo Exclusive, PullDown`, pin `0x0040` = GPIO 64.
4. `GpioInt Edge, ActiveHigh, ExclusiveAndWake, PullDown`, pin `0x0440` (1088).

Findings:

- Interrupt GPIO = **51**, falling edge (`IRQ_TYPE_EDGE_FALLING`), no bias. Grade: **Verified** value; its role as the HID device-to-host interrupt is Inference (first `GpioInt` in `_CRS` of a `PNP0C51` device, by ACPI index convention).
- GPIO 51 can wake: `{ 51, 79 }` is in the PDC wake map (`pinctrl-x1e80100.c:1811-1818`). Verified.
- `0x0440` is above the TLMM range: `.ngpios = 239` (`pinctrl-x1e80100.c:1837`). It is not a plain TLMM pin number. The same ACPI uses other out-of-range numbers (`0x0400` at `ssdt.dsl:2858`, `0x04C0` at `dsdt.dsl:51209`, `0x0480` at `dsdt.dsl:51591` for a UART whose pins are GPIO 56-59), so they are not "0x400 plus GPIO number" either. `qcgpio8380.inf` only sets `SupportLegacyPDC=1`. Grade: **Hypothesis** that it is a Windows-only wake route (an alias or a PDC pin). Confirm or kill with the `qcgpio.sys` pin-number translation, or by observing whether touch wake-up works with only GPIO 51 enabled. Not needed for first touch.
- The reset, power and interrupt pins are not shared: 48, 64, 51.

## 6. Fedora `qcom/x1e80100/qupv3fw.elf` (README Q4 and Q6)

Parsed as data: ELF32 little endian, `e_machine` 164 (Hexagon), 11 program headers, file size 52288 bytes. Layout of each SE firmware segment is `struct se_fw_hdr` (`qcom-geni-se.c:127-154`). The selection logic is `geni_find_protocol_fw()` (`qcom-geni-se.c:1270-1328`): a segment is a candidate when it is `PT_LOAD`, non-paged, not hash, `p_filesz >= sizeof(struct se_fw_hdr)`, `magic == 'SEFW'` (`0x57464553`), `version == 1`, and `serial_protocol == requested protocol`.

| PH | offset | filesz | SEFW fields |
|:--|:--|:--|:--|
| 0 | 0x0 | 0x194 | ELF/program header table |
| 1 | 0x1000 | 0x4018 | no SEFW magic (not an SE segment) |
| 2 | 0x5018 | 0x57b | protocol **6**, fw 0x114, cfg 9, 260 RAM words, 67 cfg items |
| 3 | 0x5598 | 0x785 | protocol **3** (I2C), fw 0x203, cfg 9, 388 words |
| 4 | 0x5d20 | 0x1079 | protocol **260** (0x104), fw 0x40c, cfg 9, 961 words |
| 5 | 0x6da0 | 0x1165 | protocol **4** (I3C), fw 0x501, cfg 9, 1020 words |
| 6 | 0x7f08 | 0x725 | protocol **8**, fw 0x203, cfg 10, 364 words |
| 7 | 0x8630 | 0x85d | protocol **1** (SPI), fw 0xb02, cfg 9, 442 words |
| 8 | 0x8e90 | 0x2d4 | protocol **5** (SPI slave), fw 0x10a, cfg 6, 89 words |
| 9 | 0x9168 | 0x885 | protocol **2** (UART), fw 0x405, cfg 10, 452 words |
| 10 | 0xa000 | 0x2c40 | hash segment (`p_flags` segment type 2), skipped by Linux |

All SE segments carry `core_version` `0x300c0000` and `version` 1. The decimal value 260 for segment 4 is read as a 16-bit field; it is not a Linux-named protocol.

Answers:

- The file contains protocol IDs {1, 2, 3, 4, 5, 6, 8, 260}. **No protocol 0, 7 or 9 segment exists.** Verified (ELF program headers).
- Whether one of 6, 8 or 260 is the QSPI personality is **TBD**, because the QSPI protocol number is TBD (section 1). Nothing in `sources/` names 6, 8 or 260.
- Linux v7.3 cannot load a QSPI segment anyway, for two independent reasons:
  - `geni_load_se_firmware()` rejects `protocol >= ARRAY_SIZE(protocol_name)`, and that array has 6 entries (`qcom-geni-se.c:125`, `:1560-1563`).
  - `spi_geni_init()` loads firmware only when `geni_se_read_proto()` returns `GENI_SE_INVALID_PROTO` (255). Protocol 0 (`GENI_SE_NONE`) is not 255 and not `GENI_SE_SPI`, so it logs "Invalid proto" and returns `-EINVAL` (`spi-geni-qcom.c:642-658`). The same gate is applied by the I2C and UART drivers.
- Firmware loading additionally needs `firmware-name` on the `geniqup` node (`qcom-geni-se.c:1565-1568`).
- The Windows DriverStore has no QUP firmware (the catalog has no `qupv3` file; `qcspi8380.inf` copies only `BSRC_*.bin` policy files). So Windows does not load SE microcode from the driver store; the SE personality is set earlier (boot firmware). This is **Inference**; it is killed or confirmed by reading `GENI_FW_REVISION_RO` at `0xA88068` before any driver touches the engine.

Grade: ELF content **Verified**; suitability for touch **TBD**.
