## Root cause: firmware hardware-rfkill configuration

**Verified:**

1. The complete PCI/power chain binds, the endpoint runs at Gen3 x2, and all
   reported AER counters are zero (`extra-wifi.txt:55-71,74-245`). Pins
   146/147/148 are claimed by PCIe4 (`:250-256`): patch 0001 is present.
2. Firmware reaches mission mode, board API 2 finds the exact id-255 entry,
   REGDB falls back successfully to `bus=pci`, and a netdev is registered
   (`dmesg.txt:2181,2201-2293,2309`). The missing `firmware-2.bin` is followed
   by `using fw api 1` (`:2164-2165`), as designed in
   `sources/linux/drivers/net/wireless/ath/ath12k/fw.c:160-174`. It does not
   prevent firmware start. Neither does the missing ACPI handler on a DT boot.
3. Linux programs rfkill pin 48, configuration 0, on-level 1; firmware then
   reports gpio 57, type 1, **radio_state 1** (`dmesg.txt:2306-2310`, boot
   monotonic times 30.552-30.556 s in `extra-wifi.txt:449-453`). These are WCN
   firmware pins, not TLMM GPIOs; do not infer a TLMM wiring change from 57.
4. `WMI_RFKILL_RADIO_STATE_OFF = 1`, `ON = 2`
   (`sources/linux/drivers/net/wireless/ath/ath12k/wmi.h:5472-5475`). The event
   handler sets `rfkill_radio_on` from equality to ON (`wmi.c:9450-9478`), and
   the worker sets the inverse as the wiphy hardware-block state
   (`core.c:1403-1433`). The prior dossier's proposed `radio_state 0` test
   was incorrect.
5. The rfkill listener records the wlan device being added with soft=0 hard=0
   at 30.541651 s, then changed to soft=0 hard=1 at 30.552518 s
   (`journal.txt:69139,69151`). NetworkManager changes to disabled by radio
   killswitch and the interface becomes unavailable (`:69806-69811`). The
   later snapshot still has soft=0 hard=1 (`extra-wifi.txt:574-588`). A soft
   unblock cannot clear this driver-reported hardware state.
6. The Surface ACPI WLAN `_DSM` function 2 returns `0x60`
   (`sources/windows/live-inventory/acpi/dsdt.dsl:59169-59200`). Bit 2 is
   clear. Linux's equivalent ACPI path interprets this as disabling hardware
   rfkill (`acpi.c:375-388`, `acpi.h:59-60`), but cannot read it in this DT boot.

**Inference (strong):** enabling the unusable WCN hardware rfkill input is
what prevents M8 scanning. The causal event and persistent hardware block
are observed, rather than inferred from an absent network list. Board data
and the recovered DMA warning are separate differences to correct.

**Upstream resolution:** François Roux's Surface workaround was applied to
ath.git as `5949d1910f13c20f6ebcd26eec9e0c02cb4951aa`; source patch fetched
from [ath.git](https://git.kernel.org/pub/scm/linux/kernel/git/ath/ath.git/patch/?id=5949d1910f13c20f6ebcd26eec9e0c02cb4951aa).
It gates the setup by `ATH12K_HW_WCN7850_HW20` and the root board compatible.
Patch 0002 carries the upstream code unchanged, with hunk offsets adjusted
for v7.3. The LCD DTS contains `microsoft,denali`
(`sources/linux/arch/arm64/boot/dts/qcom/x1p64100-microsoft-denali.dts:13`).
This preserves software airplane mode and leaves other chips/boards alone.
The upstream runtime tests do not constitute a pass for this unit.

The Windows policy path was independently re-derived through ARM64 REA MCP
in [the Windows-policy evidence](2026-10-29-windows-rfkill.md), including
function addresses, binary hash, forced language and evidence IDs.

## The rfkill listener did not hold NetworkManager indefinitely

**Verified:** systemd logs NetworkManager waiting for
`sp11-rfkill-events.service` at 29.109509 s; that Type=simple service finishes
its start job at 29.520362 s, NetworkManager begins starting at 29.527153 s
and completes at 30.922253 s (`journal.txt:63850,64367,64399,69803`). The
listener reports initial and changed rfkill states. It neither writes
rfkill nor remains in a startup job. The quoted wait line is an ordinary
ordering wait of approximately 0.41 s, not the radio failure.

The final Wi-Fi snapshot is at uptime 198.25 s, after NetworkManager's
shutdown at 142.323160 s (`extra-wifi.txt:1,678-685`;
`journal.txt:157380`). Its refused D-Bus connection cannot be used to claim
NetworkManager failed to start. M9 removes the listener's unnecessary
`Before=NetworkManager.service` edge, retains it as optional observation,
and retires the radio-toggle probe. This is image request I3.

## DMA allocation: unreachable CMA, successful small-chunk recovery

**Verified:**

- CMA is 128 MiB at `0xbf8000000` (`dmesg.txt:10-12`), while ath12k sets its
  PCI coherent DMA mask to 32 bits (`sources/linux/drivers/net/wireless/ath/ath12k/pci.c:863-865`).
  The DT does not provide a PCIe4 IOMMU mapping
  (`sources/linux/arch/arm64/boot/dts/qcom/hamoa.dtsi:3695-3797`), and M8
  reports no PCIe4 IOMMU group. Thus DMA-direct is the supported path here
  (Inference from the DT and the boot log). The DMA-direct addressability check rejects an allocation
  beyond the coherent mask (`sources/linux/kernel/dma/direct.c:51-81,118-152`).
- The default CMA area is used for this sleeping coherent allocation
  (`sources/linux/kernel/dma/contiguous.c:415-448`). Its pages above 4 GiB
  cannot satisfy ath12k's coherent mask. The buddy fallback needs order 11
  for 7274496 bytes with 4 KiB pages, while the M8 release `.config` sets
  `CONFIG_ARM64_4K_PAGES=y`, `CONFIG_ARCH_FORCE_MAX_ORDER=10` (local path
  `out/build/kernel/rpmbuild/BUILD/kernel-7.3.0-build/kernel-7.3/linux-7.3.0-65.sp11.5.fc44.aarch64/.config:533,570`;
  M8 `uname.txt.gz` and `kernel-rpm.txt.gz` confirm that release).
  Oversized orders are rejected (`sources/linux/mm/page_alloc.c:5338-5341`;
  `include/linux/mmzone.h:30-39`).
- The allocation warning is at `dmesg.txt:2192`. Linux requests small chunks
  after a large chunk fails (`qmi.c:2462-2538,2631-2678,2774-2775`), and
  firmware then progresses through board loading, WMI and netdev creation.
  There is no terminal memory-allocation failure in the full M8 dmesg.
- The existing Denali CMA node is reusable, 128 MiB, unconstrained
  (`sources/linux/arch/arm64/boot/dts/qcom/x1-microsoft-denali.dtsi:119-125`).
  M8 `iomem.txt.gz` (SHA-256
  `93058d67e6804f5ab928538c73cd91425fa501ac94aa14bc922539efb470194a`)
  has usable RAM extents larger than 128 MiB below 4 GiB (`:234,238,254`).

**Inference (strong):** the inaccessible CMA placement explains the initial
allocation failure. The recovery succeeded; it is not the cause of the
observed hard block. Patch 0003 adds an `alloc-ranges` window starting at
`0x80000000` with size `0x80000000`, allowing memblock to place the existing
pool in usable lower RAM while respecting reservations. It does not enlarge
the pool, change a DMA mask, claim a fixed firmware reservation, or change
power/thermal policy. Independent cross-check and M9 runtime evidence are
still required: CMA must be below 4 GiB and the initial QMI request must
succeed. Increasing the pool at its current high address would not fix
reachability.
