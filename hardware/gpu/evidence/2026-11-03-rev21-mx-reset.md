# Revision 21: MX vote, reset evidence and early pin

Date: 2026-11-03. Status: **designed**, not a device-verified reset fix. Raw evidence is under `out/device-logs/m16-20261103/`; abbreviated boot IDs below identify the directories. Line numbers refer to decompressed text, except plain `kmsg-live-*.txt`. The archive is a set of early snapshots, not a complete record until reset.

## Findings and grades

1. **Verified — the MX lookup fails in both debug boots.** `20079066/dmesg.txt.gz:1548` and `16aa40e6/dmesg.txt.gz:1619` report level 432; `20079066/gpu.txt.gz:21-38` lists 0, 16, 64, 128, 192, 224, 256, 320, 384, 416, then six zero padding entries. The error string uniquely identifies the dependency lookup (`sources/linux/drivers/gpu/drm/msm/adreno/a6xx_gmu.c:1783-1828`); the symbol shown in the log is an inlined caller. Revision 21 includes the prerequisite GPU OPP device correction (`kernel/series`, `kernel/patches/0005-drm-msm-a6xx-fix-rpmh-dependency-votes.patch`). Chip `0x43050c01` selects GEN2 and GMU support (`sources/linux/drivers/gpu/drm/msm/adreno/a6xx_catalog.c:1573`); its GMU probe constructs those tables (`a6xx_gmu.c:1941-1981`, `:2458-2459`).
2. **Inference — the upstream clamp is applicable and a targeted backport is warranted.** [Upstream 86f80884](https://git.kernel.org/torvalds/c/86f80884fb7f4601a49444a3c36df894b218336e), [patch posting](https://lists.openwall.net/linux-kernel/2026/09/23/1363), and its [preceding lookup refactor](https://lists.openwall.net/linux-kernel/2026/09/23/1400) select the last nonzero MX entry when no entry is high enough, with trailing zeros removed and an empty list rejected. On this observed sorted table that is index 9, level 416. [Patch 0003](../patches/0003-drm-msm-a6xx-clamp-mx-dependency-vote.patch) implements those semantics in the v7.3 open-coded dependency loop; it keeps the first sufficient vote, zero-frequency vote, and vote packing. It applies after the revision-21 RPMh fixes. This is a vote corner index, not a new frequency or a direct voltage setting. The upstream change is generic and its original example is Hawi; selecting 416 on X1P is supported by the observed table and upstream algorithm, not an independent measurement of rail voltage or proof of stable operation. Independent review and device verification remain required.
3. **Verified / Inference — initialization continued after a failed vote build.** The baseline function returns `-EINVAL` before writing the failing and later entries (`a6xx_gmu.c:1803-1831`), but `a6xx_gmu_init` ignores `a6xx_gmu_pwrlevels_probe`'s return (`a6xx_gmu.c:2458-2459`); HFI copies the stored dependency votes (`a6xx_hfi.c:305`). Both debug logs then record successful GMU/HFI starts and GPU hw init. This explains why an error and successful startup can coexist. It does not establish the contents actually received by firmware, rail behavior, or whether this defect caused a reset.
4. **TBD — GPU versus camera trigger.** Operator reports opening the camera before the reset in `20079066`, approximately 142 s into the session. This action is not independently timestamped in the archived session journals. `20079066/kmsg-live-20079066-0668-4323-bdd3-7ab7584f1c19.txt:5346` ends at monotonic 60.697 s; `STATUS` is the 32.84 s snapshot, and both session journals are snapshots around 34 s. Camera files explicitly say enumeration only, no capture (`20079066/extra-cameras.txt.gz`, section 6); IMX681 enumeration reports missing controls and failure to create that sensor, while the rear OV13858 is enumerated. These are observations, not proof of streaming or a failure at the reported action. GPU rendering, GPU power events, camera sensor/CSI/ISP, userspace and shared resources remain possible. Neither absence of panic/oops/fault in the captured interval nor an early successful resume excludes later faults. A/B isolation with continuous durable markers for actual camera stream on/off, GPU submissions/PM and reset reason is needed.
5. **Verified — the supposed pstore messages are the new boot's own events.** `16aa40e6/dmesg.txt.gz:114,625,1594,1619,1699-1712` has its own boot command line, pstore mount, early pin, mismatch and initialization at 11:48:45. The same events and sequence numbers appear in its own `kmsg-live-16aa40e6-4092-4669-9909-aa18f931b74a.txt:2836,2883,3027-3064`, monotonic 5.159–5.538 s. They are not an imported ending of `20079066`; that boot had its own corresponding events at 11:46:03–04 and 4.454–5.083 s. Searching the dmesg for pstore finds the command line, mount and preset, with no identified prior-boot record. No pstore payload file is in the archive. Pstore mounting alone does not establish retention. `reset-watchdog-dmesg.txt.gz` consists of early watchdog/retimer and unrelated preset text, not a reset cause. Request the image owner to capture actual pstore files, provenance and continuous evidence through the event.
6. **Verified — early GPU pin did execute in both debug boots.** `20079066/kmsg-live-20079066-0668-4323-bdd3-7ab7584f1c19.txt:2257,2728` records `3d00000.gpu ... written=on readback=on` at 4.454 s, before load begin at 5.027 s; `16aa40e6/kmsg-live-16aa40e6-4092-4669-9909-aa18f931b74a.txt:2836,3027` records it at 5.160 s before load at 5.488 s. Further udev replay and the service repeat it at about 29–30 s. `gpu.txt.gz` uses a filter for `adreno|a6xx|gmu|zap|msm_gpu|gpu-speed|speed.?bin` (`image/overlay/usr/libexec/sp11-log-collector:337`): the GMU path matches but the GPU helper line does not, explaining the apparent absence; the complete dmesg and kmsg contain it. Both snapshot `gpu-runtime-pm.txt.gz` report GPU `on`, `active`, suspended time 0, GMU `auto`, `active`, suspended time 95/164 ms respectively. The two cmdlines do **not** contain `sp11.gpu_pin=0`. These samples and ordering support an early GPU pin; they do not prove PM callbacks, IFPC, or behavior throughout the missing reset interval. No rule repair is indicated by these logs. The udev event is asynchronous, so a future build must continue to verify the pin before first load and preserve the late service as fallback; a guarantee against an earlier DRM open would require explicit ordering, not merely another udev rule. Never write GMU `power/control`.
7. **Verified — ten CPUs are already described and online.** Safe `lscpu.txt.gz` gives 10, online 0–9; all three dmesg files report `SLUB ... CPUs=10`, `nr_cpu_ids=10`, and `smp: Brought up 1 node, 10 CPUs`. Safe `devicetree.dts.gz` `/cpus` has ten CPU nodes, without `cpu@10300` and `cpu@20300`; the already-integrated board parity patch deletes those nodes and their map entries (`hardware/soc-boot/patches/0001-arm64-dts-qcom-denali-lcd-boot-parity.patch`). Windows MADT `sources/windows/live-inventory/acpi/apic.dat`, SHA-256 `50b032d657ad12b06793d4de71f0425d93a143fbf45965645203b40009a038d0`, GICC offsets `0x25c` and `0x39c`: UIDs 7 and 11, flags 0 at `0x268`/`0x3a8`, MPIDRs `0x10300`/`0x20300` at `0x2a0`/`0x3e0`. These records match the already removed nodes. **Inference:** disabling two additional online CPUs is unsupported as a reset remedy; topology alone cannot rule out every CPU-related failure. No change to idle states or frequencies is proposed.
