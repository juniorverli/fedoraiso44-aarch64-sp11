# Revision 20: reset capture and GMU restart analysis

## Observations and interpretation

**Operator-reported, not independently verified in this workspace:** debug boot `b1c603b5` starts GMU firmware and HFI at approximately 30.3 and 58.9 seconds, both return 0, and the 385 KiB live kmsg has no panic, oops or SMMU line; its final write is at 61.2 s. The reset follows GNOME appearing. Firmware `gen70500_sqe.fw` and `gen70500_gmu.bin` loaded from initramfs; GMU reports v4.3.17. Obtain and hash the raw capture before promoting these observations to Verified. A hard reset is a hypothesis, not a conclusion from missing logs.

**Verified in Linux:** patch [0001](../patches/0001-drm-msm-add-opt-in-gpu-boot-phase-trace.patch) places both GMU marker pairs inside `a6xx_gmu_resume()`. On this generation, `adreno_runtime_resume()` calls `gpu->funcs->pm_resume()` (`sources/linux/drivers/gpu/drm/msm/adreno/adreno_device.c:307`); that function is `a6xx_gmu_pm_resume()` (`a6xx_catalog.c:1573`, `a6xx_gpu.c:2866`), which calls `a6xx_gmu_resume()` (`a6xx_gpu.c:2138`). The second marker therefore proves execution of the GPU runtime-resume callback's GMU-start path, not the reason for it or completion of the entire callback. HFI success precedes further setup (`a6xx_gmu.c:1364`).

**Recovery is not excluded by timestamps:** `recover_worker()` prints `hangcheck recover!` before taking its runtime PM reference and invoking recovery (`sources/linux/drivers/gpu/drm/msm/msm_gpu.c:464`, `:478`, `:529`, `:559`); `a6xx_recover()` drops and reacquires GPU runtime references (`a6xx_gpu.c:1569`, `:1624`, `:1636`), potentially invoking the same resume and markers. A complete ordered kmsg without that message makes ordinary autosuspend/resume more likely, but recovery before a lost/truncated ring record cannot be ruled out. Need the raw capture, sequence-number gaps, `hangcheck recover!`, runtime PM tracepoints and both device states to decide. No evidence shows a direct independent GMU-platform runtime callback starting firmware: GMU is explicitly acquired within the GPU resume (`a6xx_gmu.c:1322`).

**Why the pin may fail:** the existing debug service waits for GPU sysfs and exits after writing only `3d00000.gpu`; it has no kmsg/readback confirmation, runs only after udev and before GDM (not before all earlier DRM clients), and a prior suspend/resume may already have happened (`image/overlay/usr/libexec/sp11-gpu-no-runtime-pm`, `image/overlay/usr/lib/systemd/system/sp11-gpu-no-runtime-pm.service`). This GPU selects a 66 ms inactivity delay (`sources/linux/drivers/gpu/drm/msm/adreno/a6xx_catalog.c:1580`, `sources/linux/drivers/gpu/drm/msm/msm_gpu.h:235`, `sources/linux/drivers/gpu/drm/msm/adreno/adreno_gpu.c:1247`), so a userspace unit ordered only before GDM can easily miss the first idle interval. `power/control=on` calls `pm_runtime_forbid()` for *that device*, increments its PM usage and requests resume (`sources/linux/drivers/base/power/sysfs.c:107`, `runtime.c:1654`); it does not prove the callback succeeded, block system sleep/IFPC, stop explicit GMU firmware shutdown during GPU suspend, or pin the distinct GMU platform device. Conversely a successful early GPU pin should normally prevent ordinary GPU runtime suspend; a second start does not establish that the GMU independently autosuspended. The driver enables runtime PM independently for GMU (`a6xx_gmu.c:2282`, `:2306`), acquires it during GPU resume and releases it after explicit GMU shutdown and clock disable during GPU stop (`:1486`, `:1515`). Pinning the GMU alone does not prevent this explicit stop. Pinning both changes power-domain behavior and may interfere with recovery's expected CX collapse (`a6xx_gpu.c:1615`); treat it as a diagnostic intervention, not a fix.

## Proposed ramoops layout: candidate, not cleared for deployment

**Inference, candidate address:** `0x84000000..0x841fffff` (2 MiB). The earlier device capture `out/device-logs/m16-20261102b/55d1ef37-d2e4-4ec0-8fa6-7b6a92d846f8/iomem.txt.gz`, SHA-256 `466f882e9532d0f6a23076a454a938b3e05db71d909888e8d50ce2edac4455d0`, reports `84000000-84afffff : System RAM`, with no child reservation there; five other M15/M16 captures show the same System RAM range. This is separate from GPU PRR `81f00000..81f0ffff`, PLD GMU `81f36000..81f36fff` and the ADSP heap `84b00000..852fffff` (patch [0002](../patches/0002-arm64-dts-qcom-reserve-gpu-firmware-memory.patch); `sources/linux/arch/arm64/boot/dts/qcom/hamoa.dtsi:549`). The 2 MiB region is aligned and contains 1 MiB console, 256 KiB pmsg and three 256 KiB crash records; buffer headers/ECC reduce usable payload. This captures more than the 385 KiB previous stream while preserving multiple crash slots. DT syntax, subject to the gates below:

```dts
ramoops@84000000 {
        compatible = "ramoops";
        reg = <0x0 0x84000000 0x0 0x200000>;
        record-size = <0x40000>;
        console-size = <0x100000>;
        pmsg-size = <0x40000>;
        max-reason = <2>;
};
```

The `ramoops` binding requires a fixed physical `reg`; kernel allocation of a new dynamic address each boot cannot reliably find the previous records (`sources/linux/Documentation/devicetree/bindings/reserved-memory/ramoops.yaml`). `/proc/iomem` from an earlier boot is not the UEFI allocation map or evidence of retention: firmware may allocate, write, clear or use the range before Linux reserves it. Before integrating this hamoa-wide node, kernel/firmware owners must capture the full EFI descriptors for the **actual** device and boot configuration, confirm the complete candidate range is conventional RAM with no firmware, bootloader, initrd, DTB, secure-world, crashdump or other owner across boots, and check full live DT reservations and `/proc/iomem`; independently cross-check address and size per protocol §5.1. Firmware cooperation or a firmware-reserved stable region is required if it can allocate or overwrite the range before the kernel reads it. If any overlap or ownership is unclear, do not use this address; acquire a verified fixed range. Confirm actual retention and pstore extraction across a controlled warm reboot before relying on it. A power loss, hard reset, early overwrite or unregistered backend can erase everything; empty pstore does not prove hardware/firmware reset.

## Integration requests and completion criteria

**Kernel:** request built-in `CONFIG_PSTORE=y`, `CONFIG_PSTORE_RAM=y`, `CONFIG_PSTORE_CONSOLE=y`, `CONFIG_PSTORE_PMSG=y` (plus existing BTF settings), check actual final config and built-in early registration; enable ramoops only after address gates above. Validate schema, all hamoa DTB variants, non-overlap, kernel boot reservation and pstore registration. Keep trace patch 0001. No additional kernel patch is warranted now: the address is conditional, no behavioral bug is established, and the code does not prove recovery versus normal autosuspend. HFI message-level tracing is not supplied by the existing four phase markers; check what actual v7.3 tracing provides before requesting more instrumentation, and avoid claiming a nonexistent `msm.debug` parameter. Enable available DRM/IOMMU diagnostics selectively and capture any trace buffer loss and performance effects.

**Image:** debug entry service must wait boundedly for **both** exact paths `/sys/bus/platform/devices/3d00000.gpu/power/control` and `/sys/bus/platform/devices/3d6a000.gmu/power/control`, write `on`, independently read each back, and log a timestamped `/dev/kmsg` success with full path, written and resulting value, or a clear failure for each missing, unwritable, failed or mismatched path; return failure unless both verified. Preserve stderr/journal failure even if `/dev/kmsg` fails. Start at earliest practical udev/device appearance before render opens; retain the entire timeline because service ordering before GDM alone is insufficient. Log `runtime_status` too; `on` readback alone is not proof of active hardware.

Each existing collector cycle, including fast/early cycles, record monotonic time, boot ID and, for **each** exact platform device, full path, `power/control`, `power/runtime_status`, `power/runtime_suspended_time`, and explicit missing/read error; do not wake devices merely to observe. Sample at service start and after writes too. Collect PM resume/suspend tracepoints when available and trace-buffer overruns; repeated-start and `hangcheck recover!` marker stream remains essential because snapshots can miss transitions.

`sp11-kmsg-tail` must parse `/dev/kmsg` priority as `PRI & 7`, and trigger immediate publication for severity <= 3 (KERN_ERR and more severe) or case-insensitive `adreno|msm|gmu|arm-smmu|qcom_scm|panic` in the message. A condition notification must bypass the existing size/deadline loop, with a persistent pending-urgent flag so concurrent reads/publication cannot lose wakeups. Preserve record order, bound backlog and report dropped bytes/sequence gaps, write failures, lock contention and timeouts. `live-append` must perform `sync -f` on the actual output and directory after creation/rotation; urgent means begin publish/sync immediately, not a durability guarantee while mount, lock, I/O or reset interrupts it. Test priority, matches, nonmatches, concurrent urgent events, retry and induced blocked storage.

Enable Fedora's `systemd-pstore.service`, verify package/unit and pstore mount. Configure `/etc/systemd/pstore.conf` with `Storage=external` and `Unlink=no` during this diagnostic: the service archives to `/var/lib/systemd/pstore/` and preserves raw entries until a verified copy exists. On the **next boot**, order collector after `systemd-pstore.service`; copy archive recursively and, where present, raw `/sys/fs/pstore/` entries to the boot-ID-labelled durable collector destination, preserving names and failures, then sync files and directory. This is essential on a live system whose `/var` may be volatile. Do not clear raw pstore until durable copy succeeds; report empty separately from unavailable, failed service and copy failure. Associate the archive with prior boot ID/time where possible, preserve records before any new intentional reboot, and avoid conflating current-boot data with the previous boot. Test with a non-destructive pmsg sentinel and a controlled warm reboot; an actual panic test is not required. Confirm record persistence before a debug reset experiment.
