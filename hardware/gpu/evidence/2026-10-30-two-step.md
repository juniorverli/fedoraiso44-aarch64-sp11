## 2. DTB variant `m13-gpu` (written)

`kernel/dtb-variants/x1p64100-microsoft-denali-m13-gpu.dts` = `#include` of the M12 variant (touch on, 10 CPUs with D20
parity, speakers and microphones off) plus `&gpu { status = "okay"; }`. That reverts exactly patch 0002 and nothing else,
which is "enabled exactly as M5 did". S1 holds: the M12 base keeps `/sound` and `&swr0` off. Check done here without a
build: the M12 effective DTS (`out/build/dtb-m12-checks/m12.effective.dts`) with only `gpu@3d00000` flipped to okay passes
`scripts/kernel-dtb-safety.py` (all three watched nodes effectively disabled). A real `dtc` compile and `dt-validate`
were not run (needs the container and the integrated tree; the kernel worker does it).

### Speed-bin / nvmem alignment (Verified observation, Inference conclusion)

- The cell is `gpu-speed-bin@119`, `reg = <0x119 0x2>`, `bits = <7 8>` (`hamoa.dtsi:8790`). qfprom has stride 4 and a
  `fixup_dt_cell_info` that aligns the offset down to `0x118` and moves the bit offset to 15
  (`sources/linux/drivers/nvmem/qfprom.c:338-346`, `.stride = 4` at `:386`). So the **kernel** cell read is aligned.
- The failed read in the M5 log (`gpu-speed-bin.txt`: "read of 2 bytes at 0x119 failed (got '')") is the collector's
  userspace `dd bs=1 skip=0x119` on the sysfs `nvmem` file, which rejects an unaligned offset. It tests the sysfs
  interface, not the driver.
- Evidence that the kernel read worked: in the GPU-on boot devfreq lists 11 OPPs with `max_freq` 1250000000 and no
  1375/1500 MHz entry, and dmesg has no "failed to read speed-bin" and no "missing support for speed-bin". A failed read
  would abort GPU init (`a6xx_gpu.c:2628-2633`); an unknown fuse would leave bit 0 (1.5 GHz allowed, `:2641`). The
  observed table matches supported-hw mask `0x04` (fuse 7), as expected. This corrects the earlier note: the ceiling
  does come from a successful kernel read, only the userspace copy of it failed.
- Result: **no kernel patch exists or is needed** (`hardware/gpu/patches/` does not exist). The DT is unchanged. The
  image owner's collector must read the aligned word as `test-plan.md` section 1 already does (4 bytes at `0x118`, shift 15).
  The DRM `MSM_PARAM_CHIP_ID` ioctl in `test-plan.md` section 2 is the second check.

## 3. What a two-step split can and cannot do (Verified, source)

The task assumed that writing `on` to the GPU device's `power/control` boots the GMU. It does not.

- `adreno_load_gpu()` is the only place that calls `pm_runtime_enable()` for `3d00000.gpu`
  (`drivers/gpu/drm/msm/adreno/adreno_device.c:106`) and it runs from `msm_open()` (`msm_drv.c:271`, `load_gpu`). Before the
  first render-node open, runtime PM of the GPU device is disabled, so `echo on > .../3d00000.gpu/power/control` is a
  no-op (it only raises the usage count; once the GPU is opened it then never autosuspends, which is harmless).
- Inside one `open()`: firmware load (`adreno_load_fw`, SQE; GMU image was loaded at probe), `ucode_load`, `pm_runtime_get_sync`
  (= `a6xx_gmu_resume`: CX/GX GDSC, clocks, `a6xx_gmu_fw_start`, HFI; the REA ranks the GMU boot hang and AHB fence ranges here),
  then `msm_gpu_hw_init` -> `a6xx_zap_shader_init` (PAS 13 authentication, cause 1) (`a6xx_gpu.c:1128-1137`). Userspace cannot
  separate GMU boot from zap load.
- What userspace **can** power separately: the GMU **device** (`3d6a000.gmu`, runtime PM enabled at probe,
  `a6xx_gmu.c:2306`). `echo on > .../3d6a000.gmu/power/control` resumes it through genpd (CX GDSC `gpu_cx_gdsc`, off in the
  M5 boot: `genpd_summary.txt`), nothing more. That is step 1 in the collector.
- In the M5 GPU-on boot: `gpu_cx_gdsc` and `gpu_gx_gdsc` off, regulators `3d00000.gpu-vdd/-vddcx` dummy, devfreq `cur_freq` 0,
  so nothing had powered the GPU before the reset, and the reset followed the first user session (first `msm_open`).
  This is consistent with the reset being inside `adreno_load_gpu()` (GMU boot or zap), not at probe. **Inference.**

Therefore: step 1 = GMU device on (CX GDSC); step 2 = one `open()` (GMU boot + zap together). To tell causes 1 and 2 apart
inside step 2 the kernel needs markers (section 4). Until then the collector's kernel-log follower (fsync per record)
shows the last kernel line reached.

## 4. The collector (written)

Files in `hardware/gpu/collector/`: `gpu-two-step.sh` (to `/usr/libexec/sp11-gpu-two-step`), `sp11-gpu-two-step.service`,
`grub-entry.txt`. Behaviour:

- Gate: exits 0 unless the command line has `sp11.gpu_diag=1`; the unit also has `ConditionKernelCommandLine`.
- Target (S4): same rules as `sp11-log-collector` (boot disk from `root=live:CDLABEL`, refuse NTFS/BitLocker/MSR, FAT
  `SP11LOGS` else `ANACONDA` on that disk only, never the internal disk). Files: `<root>/gpu-two-step/state.log` and
  `<root>/gpu-two-step/<boot-id>/` (`/EFI/sp11-logs/gpu-two-step/` on the ESP fallback).
- Markers: before and after each step and at every sub-step the script appends `T= UP= BOOT= EVENT=` to `state.log`, runs
  `sync -f` on that file system and writes the same text to `/dev/kmsg`. Events: `BOOT_START`, `STEPn_BEGIN`, `STEPn_SUB`,
  `STEPn_SAMPLE`, `STEPn_END`, `ABORT`, `SKIP`, `DONE`. The last marker before `STEP2_SUB open-call` and the one after
  `open-returned` bracket the single risky call.
- Step 0: waits (90 s) for `3d00000.gpu` to be bound, checks both Fedora `gen70500_*` files and the zap file exist (`.xz` and
  `.zst` accepted) and aborts without risk if not, then captures dmesg, regulators, clocks, genpd, runtime-PM and devfreq
  attributes (debugfs files only from the collector's allow-list; never `dri/*`).
- Step 1: capture; `on` to `3d00000.gpu/power/control` (recorded as the expected no-op: compare `step1.before.pm` and
  `step1.after-gpu-on.pm`); `on` to `3d6a000.gmu/power/control`; 20 s of sampling every 5 s (one marker each); capture.
- Step 2: capture; marker; one `open()` of the render node whose driver is `msm`; marker; capture; 20 s sampling; close; capture.
  No ioctl, no job, no Mesa. The fd is held 20 s so a delayed fault is seen.
- Kernel-log follower: `dmesg -w` appended and fsynced per line to `kmsg-follow.txt`, started before step 1. It captures the
  lines printed up to the reset if userspace still runs.
- Death report: the next diagnostic boot reads `state.log`; for every earlier boot whose last marker is not `DONE`/`ABORT` it
  writes `previous-boot-report.txt`, logs `REPORT ... previous boot died during step N (last marker ...; uptime ...)` to the
  journal and kmsg, and copies `/run/sp11-gpu-two-step/report.txt` for the normal collector. A boot counter is in `BOOT_START n=`.
- Reset-loop guard: after a death in step N, later boots of the same kernel release run only steps below N, unless
  `sp11.gpu_diag_force=1`.
- Entry: boots to `multi-user.target` so GDM/mutter cannot open the render node first; carries `printk.devkmsg=on
  log_buf_len=16M`, `clk_ignore_unused pd_ignore_unused` as the M5 entry did.
- Mock test (done here, no device): fake sysfs/firmware tree and a directory as target. A full run produced the expected
  marker sequence; truncating `state.log` after `open-call` made the next run report "died during step 2" and skip step 2; a
  further run of the same kernel kept skipping it; `sp11.gpu_diag=0` exits 0. The real device behaviour is untested.

### Persistent logging options (from `kernel/config` and the M12 build config)

| Option | State | Applies here? |
|:--|:--|:--|
| `printk.devkmsg=on`, `log_buf_len=16M` | already in every entry | yes (the follower reads the ring) |
| pstore core, `CONFIG_PSTORE=y`, `CONFIG_EFI_VARS_PSTORE=y` | enabled (`dev-m12/.config:11238`, `:2092`) | only for a **panic/oops**: pstore dumps on kmsg_dump. A silent hardware reset (the case here: no log line, `sbsa-gwdt` also resets) writes nothing. If the failure is an SError that panics, an EFI pstore record may exist, if this firmware allows runtime variable writes (unknown). The collector copies `/sys/fs/pstore/*` at the next boot. |
| `CONFIG_PSTORE_RAM=m`, ramoops | module built, `CONFIG_PSTORE_CONSOLE` not set, **no `ramoops` reserved-memory node** in any x1e DT | no, not without a DT node in RAM that the Qualcomm UEFI and TZ do not clear on a warm reset (Hypothesis: unproven; needs a spare region address and a kernel build). | `CONFIG_FTRACE`, `CONFIG_DYNAMIC_DEBUG` | **not set** in the M12 config | no: `dyndbg=+p` arguments in current entries do nothing, and no function trace of the GMU/zap path is possible |
