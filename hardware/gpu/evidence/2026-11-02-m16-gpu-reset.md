**Verified:** this was not an isolated first-open experiment. The kernel trace
shows `adreno_load_gpu` and successful hardware init at 5.42 s, before the
collector began at 30 s. At 31.78 s it wrote GPU `power/control=on`; GMU
firmware/HFI had already restarted at 31.91–31.93 s, *before* the recorded
GMU-device write at 32.49 s. `step1.before.pm` shows both devices suspended;
`step2.after-open.pm` shows both active, GPU `control=on`, `cur_freq` and
`target_freq` 300000000, max 1250000000 Hz. The step-2 open returned 0; the
collector held the fd and submitted no jobs. `msm_drv.c:198` caches the GPU
after successful first initialization, so this later open does not by itself
re-run the first firmware/zap initialization. `open` success alone would not
prove GPU initialization: `msm_open` can continue with a NULL GPU on a failed
load. Here the independent `hw init returned=0` is the stronger evidence.

## What the driver success means

**Verified source:** `adreno_device.c:68` loads firmware/ucode, enables runtime
PM, resumes and calls `msm_gpu_hw_init`. `a6xx_gmu.c:1309` sequences GMU device
power, GX domain, clocks, secure init, bandwidth, GMU firmware, HFI, and initial
frequency; 0 from the two inner trace points is not success of the whole path.
The trace patch marks the later whole resume and hw-init returns independently.
`a6xx_gpu.c:1499` calls `a6xx_zap_shader_init`, PAS ID 13 (`:17`, `:1129`);
`adreno_gpu.c:31` requests the DT-named image, calls `qcom_mdt_load` and
`qcom_pas_auth_and_reset`. A successful zap permits a secure-mode command and
idle check. **Inference:** hw-init success supports successful execution of that
path, but also allows its `-ENODEV` fallback at `a6xx_gpu.c:1510`; absence of a
warning in a collected log is not a per-call PAS result. There are no explicit
zap/PAS markers in this trace patch; neither firmware authenticity nor later
GPU stability is independently proven. Do not disable zap or use another OEM's
image as a workaround.

**Verified:** safe boot `gpu-speed-bin.txt.gz` reads aligned qfprom bytes
`80 03` at cell 0x119, yielding fuse 7. GPU snapshot above shows the 1.25 GHz
ceiling and 300 MHz target. Linux `a6xx_catalog.c:1608` maps fuse 7 to bin 2;
`hamoa.dtsi:4022` filters OPPs. This agrees with the previously established
Windows selected base configuration and 1.25 GHz ceiling, not evidence of an
overclock. The clock is a sampled software-visible value, not electrical proof.

**Verified:** the boot reports dummy vdd/vddcx regulators; this alone does not
prove a missing physical rail. The DT has GPU thermal cooling maps, e.g.
`hamoa.dtsi:9643`; the Windows `QCOM0CF7` equivalence is unresolved. No
voltage, thermal threshold, clock or power sequencing change is justified by
these observations. Prior REA analysis of Windows SYS `qcdxkm8380.sys`, SHA-256
`46237eba1c2c0a51d700cdf14730aae3f41b0a55775a185b87e618cab8285814`,
Ghidra forced `AARCH64:LE:64:v8A`, procedure `0x140431488`, evidence
`ev_3397a1efbf71cceec903316395b30d6453bd4d6e34ba0bca2cebd9ffb1e9480a`,
establishes the configuration loading path, not a reset fix; details and other
REA evidence IDs are in [speed-bin evidence](2026-10-24-speedbin.md). The zap
SHA-256 is `950f17eb439326548cba20603b30cda653d612d1564feb397ddbd92987f0e8ac`;
the catalog explicitly forbids disassembling its GPU payload as Hexagon.
The Fedora gen70500 payloads are not catalogued code inputs. A requested REA
MCP firmware inspection was rejected: `MCP tool call requires approval, but
approval policy is never`. No new REA analysis or firmware version/hash match
is claimed. Request sources to enable compliant REA access and catalog any

## Safe entry and minimal next change

**Verified:** safe boot's `COMPLETE` exists; `vulkaninfo.txt.gz` says Turnip
`could not get GPU ID (VK_ERROR_INITIALIZATION_FAILED)` and lists
`deviceType = PHYSICAL_DEVICE_TYPE_CPU`, `deviceName = llvmpipe (LLVM 22.1.8, 128 bits)`.
The render node's existence does not establish acceleration. **Inference:**
software rendering can account for stutter with GPU off, but the capture is a
headless Vulkan query, not the GNOME compositor's GL renderer or a frame-time
trace; the actual cause of the reported stutter is unproven. On the safe
entry, inspect the running session's renderer and frame timing; reduce desktop
animations or resolution/workload and check CPU/memory/display timing without
enabling the GPU. Do not promise acceleration without the GPU.

**Decision:** no justified GPU stability patch. Image owner should make the
normal debug entry use an existing GPU-disabled DTB, remove the automatic
two-step trigger, retain a separate GPU-disabled recovery entry, and put the
GPU-enabled diagnostic behind an explicit non-default entry with a warning and
no automatic repeats. Merely removing `sp11.gpu_diag=1` while leaving GPU DT
on is insufficient: an in-kernel DRM client initialized it at 5.36 s, before
any service guard. Verify all other entries' DT choices and update integration
checks. The available safe boot supports this default but does not prove all
other debug features or future boots stable.

**Controlled device test, planned only:** first boot the rebuilt default and
recovery entries with GPU DT disabled, no GPU diagnostic trigger, and record
actual DT status, boot completion, renderer/session, and frame timing. Confirm
there are no GPU initialization markers even with display/session starts. No
GPU open, no forced two-step, no voltage/thermal/power experiment. If later
operator-authorized GPU investigation is justified after independent safety
cross-check and power-thermal review, first use persistent reset-reason/pstore
or external logging and isolate the CDSP experiment and early DRM client;
ensure a recovery path and no automatic retry. A test which can initialize the
GPU still carries an unavoidable reset risk, and success of a boot is not a
load-test release. Do not rerun revision-15 two-step on the basis of this plan.
