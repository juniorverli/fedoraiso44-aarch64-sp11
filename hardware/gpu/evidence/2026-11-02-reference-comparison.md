## Reserved-memory candidate

[Patch 0002](../patches/0002-arm64-dts-qcom-reserve-gpu-firmware-memory.patch) restores only the two reference `no-map` regions to `arch/arm64/boot/dts/qcom/hamoa.dtsi`: `gpu-prr@81f00000`, base `0x81f00000`, size `0x10000` (64 KiB), and `pld-gmu@81f36000`, base `0x81f36000`, size `0x1000` (4 KiB). **Verified:** these values are in reference R `hamoa.dtsi:477-597`, whose commit and file hash are recorded above. They are separate from the retained zap region. The candidate affects all DTBs using hamoa, not just a variant; the reference names do not establish actual firmware use on this unit. Independent cross-check remains pending.

**Hypothesis:** if firmware uses either range and EFI leaves it available to Linux, reserving it may prevent memory reuse and a resulting reset. EFI may already reserve the memory, or the ranges may be irrelevant. At most 68 KiB of additional RAM is reserved if previously available; the actual effect is unknown.

**Comparison:** capture the EFI memory map and `/proc/iomem` on the same device before and after, retaining complete boot logs and the actual DTB identity. Check both ranges against EFI descriptors, existing reservations and kernel reserved-memory/conflict messages; distinguish already-reserved memory from newly excluded RAM. Do not access raw physical memory. Compare a clean GPU-on debug entry under otherwise matching conditions with GPU two-step and CDSP restart diagnostic agents both off, independent early durable logs and reset reason where available. The baseline and test are subject to the existing safety and thermal gates; see [test-plan.md](../test-plan.md).

**Reject** the candidate for a reservation conflict, regression, continuing GPU reset, or no relevant change in the controlled comparison. A successful boot alone does not prove the mechanism; review the maps and repeatability before attributing a change to the reservations.
