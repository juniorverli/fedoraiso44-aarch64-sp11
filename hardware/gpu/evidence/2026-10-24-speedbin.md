# X1P64100 GPU speed bin and Windows configuration

Date: 2026-10-24. Static investigation only; no device access, kernel build or
kernel modification. Cross-check on the other runtime is still required before
these conclusions authorize a safety decision (`agents/protocol.md` §5.1).

## Decision and remaining uncertainty

**Inference:** retain the existing kernel and DT. The captured Windows
configuration has a 1,250,000,000 Hz maximum graphics core clock; Linux already
selects that ceiling for fuse **7**, logical speed-bin **2**, supported-hardware
mask **0x04**. There is no evidence yet that this unit needs a new mapping or
frequency patch. This is conditional compatibility, not a verified fuse read.

**TBD:** the actual NVMEM speed-bin value on this Surface. Expected value **7**
is an **Inference** from the Windows ceiling and the existing Linux mapping,
not from ACPI REV `0x8A`. A different/unknown fuse would change this decision.
In particular, the driver's unknown-fuse fallback enables a **1.5 GHz** ceiling
and must not be treated as conservative. Do not start a GPU load test until
the fuse and the filtered frequency ceiling have been checked; see
[`../test-plan.md`](../test-plan.md).

## Which base file Windows selects

**Verified:** INF decoded line 166 maps `ACPI\VEN_QCOM&DEV_0C36&REV_008A` to
`QCDX_Inst_Base`. Lines 302–305 select `QCDX_AcpiConfig`; lines 537–538 set
`AcpiBaseFile = qcdxkmbase8380.bin`. The more specific CRD model at decoded
line 248 makes the same selection. Other revisions use separately named
install sections and the `_68`, `_110`, `_150` or Purwa configurations.

**Verified:** REG line 5 gives active version `31.0.148.0`; line 7 records
`InfSection = QCDX_Inst_Base.NT`; line 8 records the REV `008A` matching ID;
line 21 records `AcpiBaseFile = qcdxkmbase8380.bin`. Thus selection for this
installation is established by both the installer and captured active state,
not guessed from filename suffixes.

REA also reproduced the `AcpiBaseFile` string in SYS at **0x1401eb390**
(and `AcpiBaseBootCount` at **0x1401ebac0**), evidence
`ev_ebdfea8bb136fc81e1a93442781d8132bdb4d383e46de8a82975c4e34c75a862`.

**Verified decompiled behavior:** function **0x140431488** selects
`AcpiBaseFile` in its selector-zero branch (reference **0x14043156c**), or
`AcpiExtFile` in its selector-one branch. It passes the selected string to
helper **0x140456ab8**, receives a wide-string filename, constructs a path,
calls `ZwOpenFile` and `ZwReadFile`, and checks configuration magic
**0x80807070** and version **1** before retaining the data. BASE bytes at
file offsets **0x4** and **0x8** match those checks. The helper's registry
lookup semantics are an **Inference** from this behavior plus INF/REG; the
helper itself was not decompiled. This supports installer/registry-controlled
base selection rather than a claim that the loader hardcodes REV-to-filename
switches. Later consumers/overrides have not been exhaustively traced.

## Base clock table, read as data

The bounded package at BASE file offset **0x1799e**, payload length **0x575**,
contains the strings `ENGINE_PSTATE_SET`, `GRAPHICS_FREQ_CONTROL`,
`CORE_CLOCK`. **Verified bytes:** records use little-endian 16-bit type and
payload length; observed types here are 0 (8-byte integer), 1 (NUL-terminated
ASCII), 3 (nested records). Recursion ends exactly at the parent boundaries;
the declared count is 11 and there are 11 `PSTATE` children. The interpretation
of these particular fields as clock states and Hz is an **Inference** from
the labels, scale, variant comparison and Linux/vendor agreement.

[`../tools/read-clock-table.py`](../tools/read-clock-table.py) reproduces the
bounded decode for all eight catalogued base variants, validates input hashes,
record lengths and state counts, and prints only the graphics clock values.
Run from the project root:

```sh
python3 -I hardware/gpu/tools/read-clock-table.py
```

## Linux selection and ceilings

**Verified source:** `sources/linux/drivers/gpu/drm/msm/adreno/a6xx_catalog.c:1573`
identifies `0x43050c01`; its speed-bin pairs are at lines 1608–1614. The
following ceiling calculation is **Inference**, applying those verified pairs
to the verified OPP masks in `sources/linux/arch/arm64/boot/dts/qcom/hamoa.dtsi:4022`.

| Fuse value | Logical bin | `BIT(bin)` | Highest matching OPP |
|--:|--:|:--|--:|
| 0 | 0 | `0x01` | 1500000000 Hz |
| 59 | 1 | `0x02` | 1500000000 Hz |
| 7 | 2 | `0x04` | 1250000000 Hz |
| 232 | 3 | `0x08` | 1100000000 Hz |
| 146 | 4 | `0x10` | 687000000 Hz |

The 1.5/1.375 GHz entries have mask `0x03` (hamoa lines 4025–4038), 1.25 GHz
has `0x07` (4041–4046), the 1.1 GHz Fmax variant has `0x08` (4065–4071),
and the 687 MHz Fmax variant has `0x10` (4114–4120). The distinct Fmax
entries carry the larger memory bandwidth vote; equal frequency does not mean
the same OPP data. OPP filtering tests a nonzero bit intersection at
`sources/linux/drivers/opp/of.c:543`.

**Verified source:** the GPU references `gpu_speed_bin` in hamoa lines
4010–4011. That cell is at qfprom offset `0x119`, length 2, bits `<7 8>`
(hamoa lines 8784–8793). `adreno_read_speedbin()` reads the variable-size
little-endian NVMEM value at
`sources/linux/drivers/gpu/drm/msm/adreno/adreno_gpu.c:1189`.
`sources/linux/drivers/gpu/drm/msm/adreno/a6xx_gpu.c:2590` maps the fuse to
`BIT(logical_bin)` and lines 2628–2650 apply it before GPU initialization
(line 2739).

**Verified source:** an unrecognized fuse logs `missing support for speed-bin`
and falls back to `BIT(0)` (a6xx_gpu.c lines 2643–2647). **Inference:** that
fallback permits 1.5 GHz on this DT and exceeds the observed Windows ceiling.
A missing cell (`-ENOENT`) returns without setting a supported mask (2633–2634);
OPPs carrying `opp-supported-hw` are then rejected by `drivers/opp/of.c:507`.
Other NVMEM errors fail initialization (a6xx_gpu.c 2635–2638). Missing and
unrecognized fuse cases therefore have different behavior.

**Verified source / Inference:** bin 2 additionally permits a 1175 MHz OPP
(hamoa lines 4049–4054), which is absent from BASE's Windows clock table. Its
ceiling remains 1250 MHz. This investigation does not prove that every Linux
intermediate clock was used by Windows; it does not propose adding or raising
any OPP. GMU builds its frequency list from the filtered OPP set at
`sources/linux/drivers/gpu/drm/msm/adreno/a6xx_gmu.c:1877`.

## What closes Q1

1. Independent cross-check of the active base-file selection, table decode,
   and fuse/mask/ceiling arithmetic by the orchestrator's other runtime.
2. A controlled device read of DRM `MSM_PARAM_CHIP_ID` (upper bits expose the
   fuse) plus devfreq `available_frequencies` and `max_freq`, before 3D load.
   Linux exports the fuse at `adreno_gpu.c:390` and `a6xx_gpu.c:2756`; zero or
   failed reads become `0xffff`, so that sentinel does not verify a physical
   zero fuse. No successful fuse value is guaranteed to appear in `dmesg`.
3. If the fuse is 7 and the ceiling is 1250000000 Hz, no speed-bin patch is
   needed. If an unknown fuse or a higher ceiling is observed, stop loading
   the GPU and investigate a supported, independently checked mapping/cap.
