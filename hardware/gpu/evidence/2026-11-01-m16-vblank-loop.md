# M16: fbdev vblank timeout and early DRM client

## Evidence and limits

**Reported device observation, photo transcription, not an independently captured log:** Surface Pro 11, M16 private ISO, `7.3.0-65.sp11.14.fc44`. The available fragment, as supplied by the operator, is:

```text
WARNING at drivers/gpu/drm/drm_vblank.c:1329
msm_dpu ae01000.display-controller: [drm] vblank wait timed out on crtc 0
 drm_crtc_wait_one_vblank
 drm_client_modeset_wait_for_vblank
 drm_fb_helper_fb_dirty
 drm_fb_helper_damage_work
```

This preserves the reported message and call order, not exact formatting or a complete raw trace. Repeated warnings are operator-reported; frequency and full timestamps are unavailable. A prior DIE and `D` taint before 46.66 s are also reported, but its header and trace are missing. The operator considers cameras more likely; no subsystem can be attributed from this tail. M15 saw the `gen70500_sqe.fw` request fail at 5.197 s ([M15 evidence](2026-11-01-m15-debug-step0.md)). M16 image commit `2ee4dbf` is reported to add SQE, GMU and Microsoft zap firmware to initramfs; independently verifying the actual booted initrd is still needed. M16's running fbdev damage worker establishes a framebuffer client reached that path, not which load succeeded, nor why a vblank was absent.

## Mechanism

**Verified, pinned Linux source:** msm registers DRM and `msm_drm_kms_post_init` invokes `drm_client_setup` (`sources/linux/drivers/gpu/drm/msm/msm_drv.c:170`, `msm/msm_kms.c:380-387`). With the fbdev client selected, setup allocates the helper then calls `drm_client_init` before registering it (`clients/drm_client_setup.c:34-49`, `clients/drm_fbdev_client.c:165-176`). That initializes modesets and allocates an internal DRM file (`drm_client.c:36-49,80-106`); `drm_file.c:175-178` invokes `msm_open`. `msm_open` calls `load_gpu` on every open, then returns `context_init`'s result (`msm/msm_drv.c:198-208,266-273`): **a failed firmware load does not by itself make this open fail**. A later open can retry while `priv->gpu` is NULL; whether that succeeds after root mount and the exact fbdev state require a device test. The historical `-ENOENT` proves a firmware request failed, not that the internal client open failed or suppressed fbdev.

The msm fbdev sysmem/deferred operations report damage (`msm/msm_fbdev.c:29-31,56-62`); helper damage schedules work (`drm_fb_helper.c:536-553,593-612`). The running worker calls `drm_fb_helper_fb_dirty`, finds the CRTC displaying its framebuffer, waits for vblank, then consumes the damage and invokes msm's dirty callback (`drm_fb_helper.c:315-365`; `msm/msm_fbdev.c:65-85`). New console or framebuffer damage can schedule the work again; this is not a self-rescheduling retry loop shown by the timeout alone. Warning output reaching fbcon may itself produce further damage, a plausible feedback source, but no available trace proves it. The dirty-callback error path restores damage for a future run, not an immediate retry (`drm_fb_helper.c:339-355`).

**Verified:** the atomic finder already checks the primary plane's framebuffer and `crtc->state->active` under modeset locks (`drm_fb_helper.c:225-269`); legacy checks `crtc->enabled` at :279-295. Locks are dropped before waiting, so state can change between lookup and wait. The client takes internal master, calls `drm_crtc_vblank_get`, and waits only if it succeeds (`drm_client_modeset.c:1309-1337`). The waiter gets another vblank reference, waits for its count to change for 1000 ms, warns on timeout and returns `-ETIMEDOUT` (`drm_vblank.c:1310-1333`); the client ignores that return and releases its reference. DPU's vblank enable delegates to `dpu_crtc_vblank` (`msm/disp/dpu1/dpu_kms.c:430-437`); its encoder IRQ callback eventually calls `drm_crtc_handle_vblank` (`dpu_encoder_phys_vid.c:346`, `dpu_encoder.c:1463-1479`, `dpu_crtc.c:640-652`).

**Inference:** the report shows a successful vblank reference and no count change within the wait, not that the atomic CRTC was inactive. Software-active but hardware stalled, IRQ/encoder failure, a state transition or damage from an earlier fault are hypotheses. Capture atomic state, modeset and DPU/DP/IRQ evidence before choosing a root-cause fix. An inactive-state check alone already exists and cannot address a software-active CRTC that produces no interrupts.

## Can the worker DIE?

A kernel worker can oops on an invalid access, including a hypothetical use-after-free; the timeout WARN itself is not a DIE. The normal full fbdev teardown unregisters the framebuffer (`clients/drm_fbdev_client.c:24-38`); msm's framebuffer destroy calls `drm_fb_helper_fini`, which synchronously cancels damage work before buffer deletion and client release (`msm/msm_fbdev.c:41-54`, `drm_fb_helper.c:505-518`). Client release frees modesets and closes the file (`drm_client.c:165-177`). This is evidence of intended lifetime synchronization, not proof that all races or all partial-initialization paths are impossible. No evidence here establishes a teardown, UAF or GPU-caused DIE. A full oops header and trace would identify the exception/fault address, PC/LR, task/CPU, registers, call chain and taint at the time; together with symbols and preceding logs they could distinguish the faulting worker or another subsystem and guide a lifetime analysis. `D` alone identifies an earlier oops/BUG taint, not its cause.

## Options and device isolation

Grades describe confidence in the proposed outcome, not device validation. For all tests preserve the existing known-good no-GPU recovery entry, collect the complete boot journal from boot start including the first oops, exact command line and screen behavior, and compare otherwise identical M16 settings. Do not start accelerated load tests before the existing fuse and thermal gates. A successful boot or absent warning is not proof of rendering or a repaired display.

| Option | Grade and risk | Isolation / expected discriminator |
|:--|:--|:--|
| (a) Omit SQE, GMU and zap from initramfs, retain all in rootfs | **Verified** M15 early SQE lookup failed; **Hypothesis** this removes the M16 loop or later userspace initializes successfully. Firmware failure does not necessarily fail the internal open or prevent fbdev setup. Initramfs can encounter other firmware sources and open timing varies; later first open can initialize GPU before guard, and display may remain dark. | Image owner builds a comparison with these three omitted, verifies `lsinitrd` contents and rootfs files/loader support, and boots unchanged entry. Capture early `-ENOENT`, fbdev creation, vblank WARNs, and timestamped later guarded opens and firmware success. GRUB alone cannot remove files from the initrd. If warnings persist despite verified absence, omission does not isolate the loop. |
| (b) Keep firmware, append `drm_kms_helper.fbdev_emulation=0` | **Verified source / device outcome TBD:** initial fbdev configuration is skipped (`drm_fb_helper.c:1800-1805`), so the damage worker should not run. Loses DRM fbcon; other firmware framebuffer consoles may remain. This switch does **not** prevent client setup and the earlier internal `msm_open` in this 7.3 source; it does not enforce the guard. | On the affected entry, press `e`, append parameter to the Linux line, boot once. Check `/proc/cmdline`, `/sys/module/drm_kms_helper/parameters/fbdev_emulation`, first GPU trace markers, framebuffer devices and full journal. Disappearance of this specific damage-work stack supports fbdev as warning trigger; continuing early GPU phase markers are expected. Other vblank warnings or first DIE may persist. |
| (c) Patch a skip for inactive CRTC | **Verified** existing atomic active check and vblank-get gate; **Hypothesis** a transition race exists. Low justification: another unlocked state check can race and mask a real missing IRQ, affect all drivers and remove pacing. No patch is justified by this log. | First record atomic state and timestamps at selection, get and timeout; reproduce a state transition or disabled CRTC with successful get. Only then test a properly synchronized targeted patch against unpatched same image; confirm no warnings, no regressions in suspend/hotplug/fbcon, and real vblank counts. A warning-free build alone is insufficient. |
| (d) Select no in-kernel DRM client with `drm_client_lib.active=` | **Verified source / device outcome TBD:** empty selection bypasses both fbdev and log client setup (`clients/drm_client_setup.c:11-16,34-59`); avoids this client open and its fbdev damage path. It is global, loses DRM fbcon, and does not prevent initramfs userspace or another client opening DRM. Exact kernel command-line empty-string handling and module parameter value must be checked on the built image. | GRUB-edit the affected entry, append `drm_client_lib.active=` and boot once; check `/proc/cmdline` and `/sys/module/drm_client_lib/parameters/active` (empty), GPU phase traces, fbdev registration, full journal and timing of every subsequent DRM opener. Compare with (b): if (b) still opens early but (d) does not, the in-kernel client was the opener. If empty value is not honored, investigate actual parameter parsing/config rather than treating the result as a pass. |

**Recommendation:** use (d) as the first controlled diagnostic for GPU-enabled entries, retaining firmware in the initramfs for this A/B so only client selection changes. It addresses both the fbdev worker and this specific early in-kernel open without a patch; it is not a guard against other opens. Run (b) separately to isolate damage scheduling, and (a) only as a controlled image comparison. Do not change the default or claim the vblank root cause fixed until device evidence and the guard's ordering are established. Preserve console/log recovery and the existing safety gates. After obtaining the full first oops and DPU state/IRQ evidence, fix the actual display or lifecycle fault if substantiated.
