## Runtime path: source versus device

**Verified source:** Pinned v7.3 `sources/linux/drivers/gpu/drm/msm/adreno/a6xx_gmu.c` SHA-256 `6d7a4c3f75bec2043ac28e3d27632717f11d2156d3e91e05279d30ee6bdd5038`. Rev22 built source `out/build/kernel/rpmbuild/BUILD/kernel-7.3.0-build/kernel-7.3/linux-7.3.0-65.sp11.22.fc44.aarch64/drivers/gpu/drm/msm/adreno/a6xx_gmu.c` SHA-256 `c082e19c1e96073fa32e52cabfc54e363478f776462d801361fc356cc207b07a`, identical to `out/linux/m15` copy. Build identification is supported by `out/build/kernel/rpmbuild.log:21-22` and debug RPM record; source alone is not binary-to-source attestation.

- **OPP/RPMh:** GPU DT OPPs, speed-bin masks and bandwidth/ACD properties are at `sources/linux/arch/arm64/boot/dts/qcom/hamoa.dtsi:3990,4022`; fuse 7 maps to 1.25 GHz maximum per prior [evidence](2026-11-02-m16-gpu-reset.md). GMU code builds GX/CX/secondary and MX dependency plus optional BCM votes (`sources/linux/drivers/gpu/drm/msm/adreno/a6xx_gmu.c:1710,1783,1842`); rev22 built file `:1797-1839` trims trailing zero MX entries and clamps an above-table request to final entry. Legacy failure returned `-EINVAL`; probe caller's behavior is documented in [rev21 evidence](2026-11-03-rev21-mx-reset.md). GPU frequency selection uses HFI perf/bandwidth indices when active, caches when suspended and conditionally calls OPP framework (`sources/linux/drivers/gpu/drm/msm/adreno/a6xx_gmu.c:155-248`). Returned HFI start does not validate every subsequent vote, rail or physical voltage.
- **IFPC and preemption:** chip entry carries IFPC and preemption (`sources/linux/drivers/gpu/drm/msm/adreno/a6xx_catalog.c:1573-1608`); GMU idle selection is IFPC (`a6xx_gmu.c:2303`). A7xx returns early from host power-config routine (`:802-815`); do not infer a host-written IFPC register from the older branch below it. IFPC may occur within a Linux runtime-active device, and preemption trace events do not report every hardware collapse (`a6xx_gpu.c:505-526,628-638`, `msm_gpu_trace.h:180-207`). Actual IFPC/preemption before reset is **TBD**.
- **ACD:** OPP ACD data is assembled and AOSS notified by QMP (`a6xx_gmu.c:1984-2050`); HFI ACD table sent only if enabled (`a6xx_hfi.c:868-882`). Kernel has unsafe `disable_acd` module parameter (`adreno_device.c:23-25`); neither ACD use nor a reset connection is proven, so do not change it in the A/B.
- **Runtime and starts:** the catalog chooses `DRM_MSM_INACTIVE_PERIOD`, 66 ms (`a6xx_catalog.c:1580`, `msm_gpu.h:235`), installed as GPU autosuspend delay (`adreno_gpu.c:1247`), with job completion putting autosuspend (`msm_gpu.c:721-733`). Rev22 pin is GPU-only; GMU resume gets GMU runtime reference, powers resources/clocks, chooses cold/warm, starts firmware then HFI and sets initial frequency (`a6xx_gmu.c:1309-1383`). Recovery also can restart GMU: a repeated start is not automatically autosuspend. GPU pin is not a global PM or IFPC lock.
- **Dummy regulators:** log explicitly shows `vdd` and `vddcx` fallback. Generic GPU code requests and enables these supplies (`sources/linux/drivers/gpu/drm/msm/msm_gpu.c:26-55,958-968`); hamoa GPU node has no corresponding supplies (`hamoa.dtsi:3990-4022`). **Inference:** dummy handles do not directly control real rails; existing GMU, power domains and RPMh vote path is separate. This is not proof a supply is missing, that votes work, or that a regulator should be added.
- **PMIC/EC/thermal:** QCOM0CF7 Windows PEP association and unresolved policy are in [thermal hand-off](2026-10-24-thermal-policy-request.md). Shared supply, PMIC brownout/overcurrent, AOSS firmware, EC or autonomous thermal reset with no surviving kernel printk is a **hypothesis**, not an observed reset reason or established coupling. Ask power-thermal/EC owners for actual reset-cause registers, thermal throttling/rail mapping and safe read-only collection; never invent a voltage or raise a cap. Safe boot and no log do not rule out these mechanisms.

## October 24 stale bandwidth vote: rev22 audit and backport

**Verified source and inference, not a direct runtime measurement:** The pinned v7.3 and rev22 built `a6xx_gmu.c` lack `a6xx_gmu_scales_bw()` and the proposed clear after initial frequency; rev22 calls `a6xx_gmu_set_initial_bw()` before firmware start and returns after `a6xx_gmu_set_initial_freq()` without clearing it (rev22 built `a6xx_gmu.c:1187-1198,1309-1391`; pinned `sources/linux/drivers/gpu/drm/msm/adreno/a6xx_gmu.c:155-248`). Its shutdown clear at rev22 `:1514` is a different path. Rev22 is identified and hashed above. The proposed [patch 3](https://lore.jethome.com/lkml/20261024-assorted-fixes-oct-v1-3-2977f974ddb7@oss.qualcomm.com/) describes a redundant boot vote, not an established reset, undervote or thermal failure.

- The selected chip catalog entry `sources/linux/drivers/gpu/drm/msm/adreno/a6xx_catalog.c:1573-1608` has non-NULL BCM entries SH0, MC0 and ACV. `hamoa.dtsi:3990-4022` supplies `gfx-mem`, and `:4031-4155` specifies positive peak bandwidths. Rev22 debug `gpu-speed-bin.txt.gz` reads fuse 7 and `gpu.txt.gz` lists the corresponding 11 OPP frequencies from 300 MHz to 1.25 GHz. The integrated m15 variant enables the GPU and the source includes the hamoa OPPs; no runtime DTB dump was in this archive. The builder (`sources/linux/drivers/gpu/drm/msm/adreno/a6xx_gmu.c`, `a6xx_gmu_build_bw_table()` / `a6xx_gmu_pwrlevels_probe()`; rev22 `:1919-1989`) inserts zero, then searches available positive OPP bandwidths. For the observed bin, the source OPPs contain eight distinct positive peaks (2,136,719 through 16,500,000 kB/s), implying nine entries including off if the captured DT matches the integrated source and OPP lookup succeeds. Thus **both predicate terms are strongly supported and expected true**, not directly verified: `nr_gpu_bws` and the live DT were not captured. Successful GMU/HFI and rendering are consistent with this, but do not read the counter, prove boot OPP application, or show actual ICC/GMU votes. Capture these read-only on the test artifact.
- The boot OPP is requested before HFI start and its return value is ignored. If set, the host ICC vote can remain as a floor alongside GMU-generated votes; it is **not demonstrated to be an undervote**. A stale high floor might alter aggregate bandwidth, power or shared-domain behavior, but no causal route to this platform's reset has been established. Generic OPP handling (`sources/linux/drivers/opp/core.c:1150-1175,1266-1297`) makes `dev_pm_opp_set_opp(dev, NULL)` clear bandwidth and may also disable configured regulators and set PM-domain/required OPPs to zero. The hamoa GPU OPP nodes contain no `required-opps` or regulator supply properties and this wrapper delegates GPU frequency to GMU; nevertheless the kernel owner must review actual OPP configuration, dependencies and ignored return against the integrated artifact before testing. A NULL request does not remove the OPP definitions.
- [GPU patch 0004](../patches/0004-drm-msm-a6xx-clear-stale-boot-bw-vote.patch) preserves the upstream code, author, sign-offs and Fixes tag; only diff context was regenerated for rev22. SHA-256 `eaa1e71d08e609a25bf1278d7e229ce31fd3b1ef566fd980ad1c620527552cc5`. Upstream patch 3 applied to copies of all three rev22 files with `patch -p1 --fuzz=0` (offsets only); regenerated patch dry-run applies with zero fuzz and zero offsets to those files. It follows the already integrated rev21 RPMh dependency and secondary fixes and GPU MX clamp 0003; no semantic dependency on Oct patches 1 or 2, whose newer context is absent. ### Reset interpretation and discrimination

**Rank for test ordering, not a probability:** (1) camera-stream-associated CAMSS or shared load, weakly prioritized by the uninstrumented LED report; (2) GPU/GMU/shared-domain path, including a stale host BW floor as a specific source-supported subcandidate; (3) other autonomous PMIC, EC, firmware, watchdog, thermal or unrelated triggers. The missing MX message confirms only that prior probe symptom disappeared. The GPU pin does not turn off IFPC or guarantee GMU residency. The last kmsg at 64.349 s is the last captured message, not a measured reset timestamp; there is no panic/oops/SMMU or reset reason in the captured window. Trace stops at 29.469 s, long before that point. A reset can occur without a surviving Linux message if hardware or firmware resets/hangs the machine or the record is lost; **whether this particular vote can cause that is unknown**, and no upstream source establishes it here.

Compare an otherwise identical rev22-derived control and 0004-patched kernel with the same instrumentation, DTB, initramfs, firmware, pin, workload and timing. GPU-only versus individually confirmed rear/front streams separates stream association; matched control/patched repetitions separate patch association. A reproducible control-only reset with patched survival strengthens the patch association but does not prove the vote or exclude timing effects; resets in both weaken it without ruling out multiple causes, and survival in both is inconclusive. The requested trace can correlate host RPMh/PM, frequency and GPU job/preemption events and markers; it cannot itself show the firmware's internal BW vote, physical rail, IFPC, or causal reset. Request read-only host ICC aggregate/client vote and GMU table count/entries where actually exposed, with errors and timestamps, before/after GMU start; safely add explicit read-only diagnostic instrumentation only if owner-reviewed. A changed host vote after resume is a mechanism check, not proof of causality; absence of a host trace event does not establish no GMU vote. Preserve continuous trace and kmsg past reset and actual pstore, with loss accounting, as in the matrix.
