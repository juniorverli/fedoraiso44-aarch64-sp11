### 1.2 Windows: Fmax inside the file (Verified, data decode)

`qcdxkmbase8380.bin` is catalogued as `opaque blob`, `kind=data`, SHA-256 `45af47f3df7f16afef52e0b2f646d27826630a58ffe98423e1de5f3f0d8dea04`, size 125782.

Layout decoded as data:

- Header: 0x34 bytes (u32 size 0x34, magic 0x80807070, version 1, name `base_8380`), then a section table of `tag, offset, size` records: `ENGS` 0xc4, `G1MD`..`G6MD`, `GNMD`, `GPMD`, `PMCL` 0x1758b (size 0x7078), `REGR`, `TMDT`.
- Each section is an `AeoB` container of TLV elements `[u16 type][u16 len][payload]`: type 0 = u64 (len 8), 1 = NUL-terminated string, 2 = 16-byte GUID, 3 = nested node (len = size of content). One quirk: the string `*` is followed by two zero bytes that belong to no element.
- In `PMCL`, component `GRAPHICS_POWER_STATES` holds node `ENGINE_PSTATE_SET` / `GRAPHICS_FREQ_CONTROL` / `CORE_CLOCK` with `PSTATE` nodes `[index, frequency in Hz, index]`, a `GPU` child (a number: 100, 88, 80, ... 0) and a child whose second value is an ACD word.
- PSTATE 0 frequency element at file offset 0x17a41 (value at 0x17a45) is `80 7c 81 4a 00 00 00 00` = 0x4A817C80 = 1 250 000 000 Hz.
- Full table (index, MHz): 0 1250, 1 1100, 2 1000, 3 925, 4 800, 5 744, 6 687, 7 550, 8 390, 9 300, 10 0 (off).
- The ACD words equal the Linux `qcom,opp-acd-level` values at all ten frequencies (for example 1250 and 1100 MHz: 0xa82a5ffd; 1000 and 925: 0xa82b5ffd; 800: 0xa82c5ffd; 744 and 687: 0x882e5ffd; 550 and 390: 0xc0285ffd; 300: 0xc02b5ffd). This ties the file to the same GPU tuning data as the DT and supports the decode.
- `ENGS` also holds `GmemSize` = 0x300000 (3 MiB; element at 0x426), equal to `.gmem = 3 * SZ_1M` in the Linux catalog entry.

Same decode for the siblings (PSTATE 0, element offset 0x17a41 unless noted), to show that the selection matters:

### 1.3 Linux 7.3: selection chain (Verified)

- DT node: `L/arch/arm64/boot/dts/qcom/hamoa.dtsi:3991` (`compatible = "qcom,adreno-43050c01", "qcom,adreno"`), `:4010-4011` (`nvmem-cells = <&gpu_speed_bin>; nvmem-cell-names = "speed_bin"`), `:4005` (`operating-points-v2 = <&gpu_opp_table>`), `:4022` (OPP table).
- Fuse cell: `hamoa.dtsi:8790-8793`: `gpu_speed_bin: gpu-speed-bin@119 { reg = <0x119 0x2>; bits = <7 8>; }` in `qfprom: efuse@221c8000` (`:8784`). The value is `(le16 at qfprom+0x119 >> 7) & 0xff`.
- Read: `L/drivers/gpu/drm/msm/adreno/adreno_gpu.c:1189-1192` (`nvmem_cell_read_variable_le_u32(dev, "speed_bin", speedbin)`); `a6xx_gpu.c:2602-2619` (`a6xx_read_speedbin()`: uses the cell; falls back to the soft fuse only if the cell is absent and `ADRENO_QUIRK_SOFTFUSE` is set, which the `0x43050c01` entry does not have).
- Table for `0x43050c01`: `L/drivers/gpu/drm/msm/adreno/a6xx_catalog.c:1573` (entry), `:1608-1614`: `ADRENO_SPEEDBINS({0,0},{59,1},{7,2},{232,3},{146,4})`, so fuse 0 -> bin 0, 59 -> 1, 7 -> 2, 232 -> 3, 146 -> 4.
- Map to mask: `a6xx_gpu.c:2590-2600` `fuse_to_supp_hw()` returns `BIT(bin)`. `a6xx_gpu.c:2621-2655` `a6xx_set_supported_hw()` calls `devm_pm_opp_set_supported_hw(dev, &supp_hw, 1)` (called at `a6xx_gpu.c:2739`, before `adreno_gpu_init()` parses the OPP table).
- Filter: `L/drivers/opp/of.c:520-545` keeps an OPP only if `opp-supported-hw & supp_hw` is non-zero.
- OPP table (`hamoa.dtsi:4022-4147`) masks: 1500 MHz 0x03; 1375 MHz 0x03; 1250 MHz 0x07; 1175 MHz 0x07; 1100 MHz (`-0`) 0x07; 1100 MHz (`-1`, "only for SKUs which has 1100Mhz as Fmax") 0x08; 1000, 925, 800, 744, 687 (`-0`) 0x0f; 687 (`-1`, "Fmax") 0x10; 550, 390, 300 0x1f.
- Result per fuse/bin:

| Fuse | Bin | `supp_hw` | Fmax (MHz) |
|--:|--:|:--|--:|
| 0 | 0 | 0x01 | 1500 |
| 59 | 1 | 0x02 | 1500 |
| 7 | 2 | 0x04 | 1250 |
| 232 | 3 | 0x08 | 1100 |
| 146 | 4 | 0x10 | 687 |

- Also: the speedbin goes to user space in `MSM_PARAM_CHIP_ID` bits 63..32 (`adreno_gpu.c:390-394`; `a6xx_gpu.c:2756-2759`, a read error or a zero fuse becomes 0xffff). `MSM_PARAM_MAX_FREQ` returns `fast_rate` (`adreno_gpu.c:395-396`). These are usable as run-time checks.

### 1.4 Linux 7.3: unknown or unreadable fuse (Verified)

- Unknown value (nvmem read works, value not in {0, 59, 7, 232, 146}): `a6xx_gpu.c:2641-2648`. Message `missing support for speed-bin: %u. Some OPPs may not be supported by hardware`, then `supp_hw = BIT(0)`. Effect: the 1500 MHz tier (OPPs with mask bit 0: all with 0x03/0x07/0x0f/0x1f; `-1` variants at 1100 and 687 dropped). Probe continues. Risk: a unit whose fuse is outside the table is clocked up to 1500 MHz, above Windows' 1250 MHz for this SKU.
- Cell absent (`-ENOENT`): `a6xx_gpu.c:2630-2634` returns 0 without calling `set_supported_hw`. Then `of.c:507-518` drops every OPP that carries `opp-supported-hw`; every OPP in the `hamoa.dtsi` GPU table carries `opp-supported-hw`, so the OPP table ends up empty. Not our case (the cell is in the DT).
- Other read error (for example the qfprom driver or nvmem cell not ready): `a6xx_gpu.c:2634-2639` logs `failed to read speed-bin` and probe returns the error (a deferred probe returns `-EPROBE_DEFER`). The kernel needs the qcom qfprom nvmem driver built or loaded (config not checked here; `kernel/` is out of scope).

### 1.5 Which Linux bin is this unit (Inference)

- Facts: Windows selects the 1250 MHz file for `REV_008A` (1.1, 1.2); Linux has exactly one bin whose Fmax is 1250 MHz: bin 2, fuse 7 (1.3).
- Reasoning: if the Windows tier equals the fused Fmax of the part (the four tiers match one to one, and the ACD words match), the unit has fuse 7, bin 2, `supp_hw = 0x4`, and Linux enables 1250, 1175, 1100 (`-0`), 1000, 925, 800, 744, 687 (`-0`), 550, 390, 300 MHz.
- Weak points: the INF picks the file by ACPI `_REV`, not by fuse, so a part binned differently from its marketing tier would not show here; no source in `sources/` records the fuse value of this unit; the Linux tree has no commit message for the table (single squashed history). Also, Windows' `base` table omits 1175 MHz, which Linux enables for bin 2; this is a difference in tables, not in Fmax.
- What would confirm it: on the device, `dmesg` (absence of `missing support for speed-bin`), `MSM_PARAM_CHIP_ID >> 32` (expected 7), `MSM_PARAM_MAX_FREQ` (expected 1250000000), or the qfprom bytes at 0x119-0x11a through nvmem.

## 2. Q2: zap shader versus the 7.3 loader (header reading only)

File: `PKG/qcdxkmsuc8380.mbn`, SHA-256 `950f17eb439326548cba20603b30cda653d612d1564feb397ddbd92987f0e8ac`, 12088 bytes. Catalog row: ELF (Qualcomm MBN), `gpu-firmware`, hand-checked override "Adreno zap shader in a signed PIL ELF; e_machine 164" (`sources/binary-formats.md` section 5): not disassembled, not loaded as Hexagon.

Header values (read with a struct parser, bytes only):

| Item | Value |
|:--|:--|
| ELF | class 32-bit, little endian, `e_type` 2, `e_machine` 164 (not checked by the loader), `e_entry` 0x1000, `e_phoff` 52, `e_phentsize` 32, `e_phnum` 3, `e_shnum` 0, `e_flags` 3 |
| Phdr 0 | `PT_NULL`, offset 0, `filesz` 0x94 (= ELF header + 3 phdrs), flags 0x07000000 |
| Phdr 1 | `PT_LOAD`, offset 0x1000, `vaddr = paddr` 0x1000, `filesz = memsz` 0x430, flags 0x08000007 (bit 27 = `QCOM_MDT_RELOCATABLE` set, type bits 0) |
| Phdr 2 | `PT_NULL`, offset 0x2000, `filesz` 0xf38, flags 0x02000000 (type 2 = `QCOM_MDT_TYPE_HASH`); ends at 0x2f38 = file size |
| Hash segment | header version 7 (words: 0, 7, 0x18, 0, 0xe0, 0x90, 0, 0, 0x68, 0xd20); certificate chain at the end (0xd20 bytes): leaf `CASS - SBL4`, issuer chain `QMC Attestation Root CA 6 SubCA 1` and `QMC Attestation Root CA 6` (Qualcomm). Signature validity is not checked here |

Loader walk (Linux 7.3):

- `adreno_gpu.c:31-174` `zap_shader_load_mdt()` (`:156` auth call) and `a6xx_gpu.c:17,1137` (`GPU_PAS_ID 13`, `adreno_zap_shader_load(gpu, GPU_PAS_ID)`).
- Needs a `zap-shader` child (`hamoa.dtsi:4018`), `qcom_pas_is_available()` (`adreno_gpu.c:56`, else `-EPROBE_DEFER`), a `memory-region` (`:61`), and `firmware-name` (`adreno_gpu.c:82-88`). The Denali DT sets `firmware-name = "qcom/x1e80100/microsoft/qcdxkmsuc8380.mbn"` at `L/arch/arm64/boot/dts/qcom/x1-microsoft-denali.dtsi:723-725`, read with `request_firmware_direct()`, so the file must exist at `/lib/firmware/qcom/x1e80100/microsoft/qcdxkmsuc8380.mbn` (the firmware worker's part).
- Memory region: `hamoa.dtsi:598-601`, `gpu_microcode_mem: gpu-microcode@8d9fe000`, `reg = <0x0 0x8d9fe000 0x0 0x2000>`, `no-map` (8 KiB).
- `mdt_loader.c:22-53` `mdt_header_valid()`: ELF magic ok, `e_phentsize` 32 ok, phdr table ends at 148 <= 12088, no section headers: valid.
- `mdt_loader.c:110-139` `qcom_mdt_get_size()`: loadable = `PT_LOAD`, not hash type, `memsz` != 0 (`:55-65`): only phdr 1. min 0x1000, max `ALIGN(0x1430, 4K)` = 0x2000, so the size is 0x1000. `adreno_gpu.c:111-123`: 0x1000 <= 0x2000, fits.
- `mdt_loader.c:161-228` `qcom_mdt_read_metadata()`: `e_phnum` 3 >= 2 (`:180`); phdr 0 is not `PT_LOAD` (`:183`); hash segment found at index 2; metadata = 0x94 + 0xf38 = 0xfcc bytes. `0xfcc != 12088`, and `p_offset + hash_size` = 0x2f38 <= file size, so the "hash in its own segment, within the loaded file" branch (`:213`) is used. No split `.b%02d` files are needed (`qcom_mdt_bins_are_split()`, `:296-322`, returns false: every segment ends within the file).
- `mdt_loader.c:231-294` `__qcom_mdt_pas_init()`: `qcom_pas_init_image(13, metadata, 0xfcc)`, then, because phdr 1 is relocatable, `qcom_pas_mem_setup(13, 0x8d9fe000, 0x1000)` (`:283`).
- `mdt_loader.c:336-438` `qcom_mdt_load_no_init()`: relocatable, so `mem_reloc = min_addr = 0x1000` (`:376-381`); phdr 1 goes to offset 0 of the region, `filesz == memsz`, copied from file offset 0x1000. Then `qcom_pas_auth_and_reset(13)` (`adreno_gpu.c:156`).

Conclusion: format, size and region fit. Same loader path as the other X1E80100 laptops that point `firmware-name` at their own `qcdxkmsuc8380.mbn` (for example `x1e80100-asus-vivobook-s15.dts:19`). The Windows driver lists this name (UTF-16 `qcdxkmsuc8380.mbn` at `qcdxkm8380.sys` offset 0x474360, next to `qcdxkmsucpurwa.mbn` at 0x474388, SoC-specific names), and the INF copies both (`qcdx8380.inf` lines 58-59, 620-621); the Purwa one has `memsz` 0x3f4 and belongs to `DEV_0D17`, not to this unit.

Not answerable from the files:

- PAS ID: the 13 is hard-coded in Linux (`a6xx_gpu.c:17`). The MBN has no PAS ID field; its hash header has image ID 0 (word 0 of the hash segment). Whether TZ accepts PAS 13 for this image on this device is TBD. Evidence: `dmesg` lines `error %d initializing firmware`, `error %d setting up firmware`, `Unable to authorize the image`, `PAS is not available` (`adreno_gpu.c:57,165`, `mdt_loader.c:279,287`).
- Windows side of the PAS ID and the memory region: not in `dsdt.dsl` (SHA-256 `8a7b849b9ac2148a9806d967612eb0d5195020c3e29ffd834b837767256a8ede`: no zap or `0x8D9FE000` string) and not found as a string in `qcdxkm8380.sys`; a REA pass on the `.sys` would be needed (language `AARCH64:LE:64:v8A`, with the section 9 settings and the Ghidra lock). Not done.
- TZ signature acceptance: the image is Qualcomm-signed (chain above); whether this exact image is accepted on a retail Surface Pro 11 is TBD (device test).

## 3. Method and limits

- All Windows firmware decoding used a throw-away parser written in the scratchpad (not committed): no disassembly, no REA. The container layout is my own reading of the bytes; it is consistent (section sizes add up to the file size 125782; ACD words equal the Linux DT values; GMEM equals the Linux catalog).
- Not done: REA on `qcdxkm8380.sys` (the question allowed it only if needed; the INF and the data file answer the selection and the Fmax); any device-side check.
- Line numbers of `qcdx8380.inf` are those of the file converted from UTF-16 to UTF-8 with CRLF removed from the count.
