# Closed-loop speaker audit, 2026-11-03

Scope: offline audit and host tests only. No device action, audible output, kernel/image/ISO build, or git write. S1/D26 and the speaker-off fallback remain in force. The observations below do not establish closed-loop protection.

## Priority defect: calibration can outlive an unstarted VI graph

**Verified in the composed series source** (`out/rev21-apply`): `sp11_apply_r0t0()` sets the global calibration mask immediately after a successful DSP SET_CFG (`sound/soc/qcom/qdsp6/audioreach-sp11.c:391-401`), before graph prepare and start (`qdsp6/q6apm-lpass-dais.c:256-265,210-218`). If prepare or start then fails, or the application closes after prepare without starting, `is_port_started` is false: shutdown closes the graph without a stop (`q6apm-lpass-dais.c:185-200`), and `q6apm_graph_close()` does not invalidate calibration (`qdsp6/q6apm.c:787-796`). The guard clears the mask only when the last *started* VI stream stops (`sp11-guard.c:218-237`).

On a subsequent VI graph, a missing calibration file returns success without clearing that old mask (`audioreach-sp11.c:351-355`). **Conditional consequence:** if that new VI graph starts, and SP graph/enable, caps, mode, fault and nominal/degraded policy checks also pass, the guard can report `allowed: yes` based on calibration from the earlier graph. The ADSP may reject the later graph, and no such hardware event or actual unmute has been observed. With degraded diagnostics, a stale nominal mask still fails; a stale non-nominal mask can satisfy that particular check. A positive `cal_mask` alone is therefore not proof for the current graph. Do not retry failed VI preparations or exchange calibration files in the same boot while this defect is present.

The host scenario in `userspace/build-topology/harness/check_guard_lifetime.py` compiles the actual guard, R0/T0 missing-file, graph-close and DAI shutdown functions from that composed source with host stubs. It simulates an acknowledged calibration, closes before start, takes the real missing-file branch, then simulates successful VI and SP start. It reproduces the two failures; stopping a started VI stream is a positive control. It does not model DSP behavior, parallel streams, kernel locking or a physical amplifier.

**Single priority request to kernel:** bind the calibration state to the VI graph/attempt that actually received it. At minimum invalidate it under the guard lock before every new VI preparation and on every failure or close, including an unstarted graph; a calibration marker must become current only after that graph's successful SET_CFG. If an already allowed graph loses calibration, schedule the existing mute. Preserve all mode, fault, caps, nominal/degraded, VI/CPS and kill-switch gates. Review shared-graph/refcount and concurrent retry behavior rather than assuming one PCM is the only caller. Add tests for successful SET_CFG followed by prepare failure, start failure, and close before start; retry with missing, invalid and rejected files; normal stop/restart; measured versus nominal; degraded diagnostics; active-stream mute; kill/fault/caps; and concurrent/shared graphs. Each retry without a newly accepted calibration must leave `allowed: no`. No guard change is implemented here.

## Other concrete integration findings

1. **Private supplement names do not follow the selected model.** `kernel/dtb-variants/x1p64100-microsoft-denali-m15-spk.dts:37-38` selects card name `X1E80100-Microsoft-Surface-Pro-11-CL`; `out/rev21-apply/sound/soc/qcom/common.c:189` reads the `model`, and `qdsp6/topology.c:1475-1478,1499-1504` passes that name to both loaders. Patch 0014's loader constructs `<card>-sp11cl.bin` and `<card>-sp11cal.bin` (`patches/0014-ASoC-qcom-audioreach-add-closed-loop-speaker-protect.patch:279-280,306`; final composed `audioreach-sp11.c:199-209,231-234`). Thus it requests `X1E80100-Microsoft-Surface-Pro-11-CL-sp11cl.bin` and `...-CL-sp11cal.bin`. `image/tools/private-m14.py:40-46,138-148` renames only the topology and installs both supplements with the unsuffixed card name. The private build record `out/image-work/20261103T213714Z/private-m14-record.json` and the already-extracted L0 root `out/image-work/l0-sp11-fedora44-aarch64-kiwi-20261103T213714Z-private/root/` confirm these three destination names and hashes and the absence of the CL-named supplements. Missing `sp11cl` is silently optional at the loader but leaves `loaded: 0`, so the closed-loop open gate refuses (`sp11-guard.c:116-129`). Fixing the supplement name alone would still leave the calibration name wrong. The image owner must eventually stage both supplements under the **CL** model names, preserve private-only handling, and check those exact names and hashes, initramfs where applicable, and absence of both old and new names in public images. No image file was changed here.

2. **Supervisor requests unsupported front-end parameters.** The actual generated configuration has MultiMedia5 capture S16_LE, 48 kHz, one or two channels (`out/firmware-private/audio/qcom/x1e80100/X1E80100-Microsoft-Surface-Pro-11-closedloop.conf:1583-1605`; source `userspace/build-topology/m4/X1E80100-Microsoft-Surface-Pro-11-closedloop.m4:42-45`). `image/overlay/usr/libexec/sp11/speaker-supervisor:14-35` opens `hw:0,4` and calls `snd_pcm_set_params` with S32_LE, 8 kHz, four channels and software resampling disabled. With those advertised constraints the direct hardware PCM cannot negotiate the request. The image-owner follow-up is to use supported **front-end** parameters, preserve the separate backend fixup and no-playback behavior, and test errors and XRUN/liveness. Do not treat changing the capture format as proof of feedback.

3. **The configured TX channel counts need investigation.** For WSA TX_0, `out/rev21-apply/sound/soc/qcom/x1e80100.c:155-174` fixes two channels. `qdsp6/q6apm-lpass-dais.c:170-180` copies this count and the default channel map to `cfg`; `qdsp6/q6apm.c:443-460` passes that same configuration to every graph module. `qdsp6/audioreach.c:760-762,782-788` therefore constructs a two-channel codec DMA endpoint and normally mask `0x3`, while `:1520-1541,1559-1581` constructs a four-entry VI map for two speakers. This is a **verified configuration mismatch**, not proof that the ADSP rejects it or that changing the count is safe: the VI helper explicitly rejects `num_channels > 2`. The actual codec-DMA convention, on-wire samples and intended mapping need independent evidence before proposing a functional change.

The current `m15-safe` source still includes the speaker fragments (`kernel/dtb-variants/x1p64100-microsoft-denali-m15-safe.dts:3-14`); its name is not evidence of a speaker-off fallback. `m15-nosnd` describes sound and swr0 off and can be checked as the speaker-off fallback, although it also disables the sound card. The retained and canonical D28 Speaker sequences now have identical SHA-256 `163cd2d165fb3a0e7003f7ec8b7e7801f5f23737e4274ef9efb1cf091478c179`; `image/tools/check-m11-payload.py:92-98` checks both physical PA writes and rejects an alias cset. Runtime UCM behavior is still untraced.
