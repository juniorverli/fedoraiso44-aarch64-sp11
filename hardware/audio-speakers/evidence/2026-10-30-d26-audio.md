## 2. The APM_CMD_GET_SPF_STATE timeout (the "blocker")

Verified, `sources/linux` v7.3:

- `drivers/soc/qcom/apr.c:365-374` `apr_device_probe()` runs `adrv->probe(adev)` and assigns `adev->svc.callback = adrv->gpr_callback` only afterwards.
- `sound/soc/qcom/qdsp6/q6apm.c:886` `apm_probe()` calls `q6apm_get_apm_state()` (a synchronous command, 5 s wait, `audioreach.c:593-637`) before it returns.
- `apr.c:309` `gpr_do_rx_callback()` does `if (svc->callback) svc->callback(...)`. During the probe the callback is NULL, so the answer is dropped silently. This is deterministic, not a rare race.

Verified, M12 log (`out/device-logs/m12-20261030/19f802...`, `dmesg.txt.gz`):

- `Adding APR/GPR dev gprsvc:service:2:1` at 21:31:58, `CMD timeout for [1001021] opcode` at 21:32:27.26 (opcode 0x1001021 is `APM_CMD_GET_SPF_STATE`; the 33 s is the late module load, then exactly the 5 s wait).
- The probe continues after the timeout (the return value is ignored): `q6apm-dai`, `q6apm-lpass-dais`, `q6prm-lpass-clock` are loaded and `q6prm_clocks` has 32 users in `lsmod`.
- `q6prm` `prm_probe()` returns `-EPROBE_DEFER` unless `q6apm_is_adsp_ready()` (a second GET_SPF_STATE, sent after the callback exists) returns a non-zero state. `q6prm_clocks` exists, so that second request was answered.

Inference (strong): the ADSP audio PD and SPF are alive; the timeout is only the dropped probe-time answer. H1 to H4 in the earlier plan are not needed to explain it. The reason there is no card in M12 is the DT (`/sound` and `swr0` disabled, `sound.txt`: no soundcards), not the timeout. Unknown until a device log: that a card registers on `m13`; the collector must show it.

Fix: patches 0006 and 0007. Without 0006 the new early callback could dereference NULL driver data, so 0006 precedes 0007.

## 3. Safety layering for speakers (D26 / S1)

Layers, outermost first:

1. Packaged default DTB: unchanged, `/sound` and `swr0` disabled (kernel patch 0001). `kernel-dtb-safety.py` default profile rejects any speaker path and also rejects the marker.
2. `m13-spk` DTB (marker, `swr0` on, both WSA8845 enumerated) is checked with `--profile d26`. Verified on compiled output: `m12` and `m13` pass the default profile; `m13-spk` fails the default profile and passes `d26` with the marker.
3. Kernel gate (patch 0009): `x1e80100_snd_startup()` returns `-EOPNOTSUPP` for `WSA_CODEC_DMA_RX_0/1` on `microsoft,denali` before `qcom_snd_sdw_startup()`. No module parameter, control or sysfs override. Microphone and DP links unchanged.
4. Existing open-loop caps (0001, 0002, 0004, 0005): PA gain reset to 0 dB, `PA Volume` max 6 (0 dB), WSA digital and MIX max 81 (-3 dB).
5. User space: UCM boot value 72 (-12 dB) and PA 0, speakers muted at start; dconf lock on above-100 %; WirePlumber default 5 %.

Is the gate implementable and robust? Yes for what it does today: a failing `startup` on a DPCM back end makes the front-end PCM open fail, and no SoundWire stream or DAPM power-up happens. It is not a "gate until validated" state machine: it is an unconditional refusal, because the condition (closed-loop graph up and fault free) cannot exist until the Stage 3 work below is done. So with 0009 `m13-spk` enumerates the amplifiers but cannot play. That is the honest state; D26's open-loop sound cannot be switched on from user space on purpose.

Residual risk that the kernel gate does not cover: the amplifier is enumerated and programmed at probe (reset GPIO release, register defaults, PA gain 0 dB via 0001/0004) with no stream running; a SoundWire register write from user space is not possible without a debug interface. Unknown, to check in the first test: that no amplifier output is enabled by the probe alone (read `PA Volume`, DAC/COMP switches, dmesg).

Series dependency: a kernel that boots `m13-spk` MUST contain 0001, 0002, 0004, 0005 and 0009. The kernel worker adds 0006 to 0009 together; 0008 without 0009 would be a speaker-enabled DTB with only gain caps.

## 6. User space (done)

- `userspace/overlay/` (mics, unchanged, installed everywhere).
- `userspace/overlay-speakers/` (renamed from `stage-b-speakers-HOLD`, referenced names updated): speaker UCM, `WsaInit` boot value for the four digital volumes changed from 78 (-6 dB) to 72 (-12 dB); PA stays 0.
- Ceiling reasoning (Verified numbers from the Argon report, one Windows default value cross-checked is Unknown, see 8): Windows default -12 dBFS with PA +16.5 dB and closed loop. The kernel cap (-3 dB, PA 0) remains the hard limit if someone writes the controls with `amixer`; the desktop does not write them (no hardware mixer element; verify in the first test that WirePlumber uses software volume).
- Unknown: whether the installed WirePlumber exposes a hard per-node volume limit key; none is claimed. The WirePlumber file keeps the 5 % default only.
- Fallback entry `SP11 debug, no speakers`: M12 DTB (`/sound` and `swr0` off, S1 baseline), `overlay/` not needed (no card). Microphone-only entry: `m13` with `overlay/`.

## 8. Closed-loop V/I protection: design from the ACDB and what is verified

Method: `acdb_inspect.py` on `surface_acsp8380.inf_arm64_f6524e4db745e12a/REV_0D/acdb_cal_0D.acdb` (sha256 `a0a8635b...8decde`, catalog-confirmed) as data; direct decode of selected parameters by this worker. The earlier Argon REA report remains the only source for driver-side semantics; spot-check below.

### 8.1 Graph (Verified from the ACDB)

15 graph key sets contain `SPEAKER_PROTECTION` (module `0x070010e2`, instance `0x4027`); the full speaker subgraph is `0xb0000001`, its main variant has 4 containers (`0xe0000001`, `5`, `6`, `7`):

- forward: `SAL 0x4001` -> `DATA_LOGGING 0x402c` -> `SPEAKER_PROTECTION 0x4027` -> `SPLITTER 0x4002` -> `MFC 0x4003` -> `CODEC_DMA_SINK 0x4157` (WSA RX). Splitter has extra legs to `0x47c9`, `0x4747`, `0x4730` (other graphs, Unknown purpose).
- V/I feedback: `CODEC_DMA_SOURCE 0x4026` -> `MFC 0x4025` -> `SPEAKER_PROTECTION_VI 0x4024` (module `0x070010e3`).
- CPS feedback: `CODEC_DMA_SOURCE 0x402b` (sample rate 24000, from parameter `0x08001017` words `[24000, 0x20020, 1]`) -> `MFC 0x402a` -> `0x4029` (module `0x07001098`) -> `CPS_DATA_ROUTER 0x4028` (module `0x070010e4`).
- IMCL control links (param `0x08001061`): `0x4024:0x80000000 <-> 0x4027:0x80000000` (intent id `0x08001204` = 134222340), `0x4028:0x80000000 <-> 0x4027:0x80000001` (intent `0x08001537`), `0x4157:0x80000007 <-> 0x40df:0xc0000001` (intent `0x080010c2`, peer outside this subgraph).
- Other subgraphs of the same keys (`0xb0000011`, `0xb0000028`, and the numbered variants) are the stream/loopback side and the mic/VI-adjacent processing; not needed for protection.

### 8.3 What Linux 7.3 lacks (Verified in the series tree)

- `wsa884x.c`: VISENSE and CPS are only in `wsa884x_sink_dpn_prop` (RX); the DAI has no capture stream; the SoundWire direction is RX; VSENSE is hardcoded to `VSENSE_M24_DB` with `ISENSE_12_DB`; reset default `OCP_CTL` is 0xc6; `CURRENT_LIMIT` is rewritten. The Windows values (`OCP_CTL 0xf6`, `VSENSE_M21_DB` at +16.5 dB, 2S boost registers) are from Argon only: Unknown here.
- `x1-microsoft-denali.dtsi:1094,1106`: left `qcom,port-mapping = <1 2 3 7 10 13>`, right `<4 5 6 7 11 13>`: the CPS master port 13 is shared. The same values are used by upstream X1E boards; Argon says Windows uses 14 for the right one. Unknown which is right for this unit.
- `x1-microsoft-denali.dtsi:1089,1101`: both amplifiers use `lpass_tlmm 12` as reset (Verified); the second reset line is not described.
- `x1e80100.c`: no VI/CPS DAI links (no `WSA_CODEC_DMA_TX_0`/`TX_2` link in the DT).
- `qdsp6/audioreach.c`: no IMCL (`0x08001061`) emission, `audioreach_set_module_config()` never called for `0x070010e2/e3`, no handling of the SPv5 diagnostics event `0x0800138c`.
