In `audioreach.c:1520-1581` the VI operation count is interpreted by that implementation as two speakers and expands to four map entries `[1,2,3,4]`, which its header calls V/I pairs (`audioreach.h:737-754`). This proves what Linux constructs, not how the DMA or physical SoundWire samples are packed.
- **Verified, ACDB as catalogued data:** `sources/windows/DriverStore/surface_acsp8380.inf_arm64_f6524e4db745e12a/REV_0D/acdb_cal_0D.acdb`, catalog SHA-256 `a0a8635ba65127180a1caef46af61c00171c9a93cbf8b5f5650709b4638decde`, keyless VI instance `0x4024`, parameter `0x08001203`, payload offset `0x3a502`, 20 bytes, SHA-256 `dd2b45e6dd3aad74c1e776b5f131ab27324b7633f423e1667ec02ac8175194d7`. The four-byte words decode using the Linux map structure as count **4** and entries `[1,2,3,4]`. The independent file observation agrees with Linux's generated logical map; it does not establish physical order or DMA packing. No calibration values or samples are logged by the new instrumentation.
- **Windows lead, not a newly verified runtime fact:** the previous REA survey reports two-speaker tag and SP/VI `num_speaker` matching strings, but does not establish the language was forced for every result or decode the actual SP value. The catalog requires `AARCH64:LE:64:v8A`; see [prior audit](2026-11-03-closed-loop-audit.md). The logged ACDB map, Linux VI count and two amplifiers support the two-speaker/four-map interpretation, not a conclusion that two DMA channels are correct. SP record count, Windows DMA config, slot packing, sense scale and left/right mapping remain unknown. No undocumented port, gain or DMA count was changed.
- **Smallest topology correction:** the VI top-level m4 arguments formerly said four, but `subgraph-sp11-vi-capture.m4` never references `DEVICE_MIN_CHANNELS`, `DEVICE_MAX_CHANNELS`, `DEVICE_FORMAT` or `DEVICE_*_RATE`; these arguments did not configure the DMA. They now say two and explicitly document that they are unused. This is a source-consistency fix, not a functional DMA fix. A regenerated topology has not been built or compared in this session.
- **Verified topology shape, device operation unknown:** codec DMA source `0x4026` -> logger `0x4025` -> VI `0x4024`; VI has no output. MultiMedia5 connects by a DAPM edge only. It is a trigger, not a host V/I tap. The ACDB also contains CPS `0x4028` and its `0x402b -> 0x402a -> 0x4029 -> 0x4028` chain and CPS-to-SP link. The current topology implements none of that CPS chain. It is unknown whether CPS is mandatory for this hardware's protection.

## CPS policy for this experiment

CPS is **not needed to ask whether the isolated VI trigger opens and reports its configuration**, but it is required as a conservative unmute gate because its role is unresolved. The generator now refuses implicit omission; `--vi-only-diagnostic` generates one VI link and sets the existing CPS-required flag even though the topology lacks a CPS stream. It refuses `--with-cps` until a complete CPS topology exists and refuses `--measured` until a supported measurement workflow exists. The explicit nominal file is test-only. Generation without a calibration refuses an existing stale calibration file before writing. The previous private f44ef supplement had flags 0: it must not be reused as this diagnostic's input.

The existing guard populates `cps_required` when the SP graph starts, and reports 0 while the SP graph is down; therefore `cps_required: 0` on the capture-only test does not imply CPS is optional. With an SP graph running and this diagnostic supplement, the guard must require a CPS stream. The host guard test verifies that gate, but no live CPS stream exists. The mandatory boot-time `sp11.nospk=1` and absent `sp11.allow_nominal` are additional independent *software decisions*, not a hardware interlock. Never use this diagnostic as evidence that a closed loop is complete or sound is safe.

## Calibration and instrumentation candidates

The 36-byte `SP11CA01` envelope, two-channel limit, CRC, 80–125% R0 bounds and -10–60 C T0 bounds remain unchanged. Candidate [0024](../patches/0024-ASoC-qcom-validate-calibration-flags-report-VI-identity.patch), applied after the kernel owner's 0011, rejects unknown envelope flags and reserved words and reports `cal_graph_matches_vi` and `vi_ambiguous`; calibration identity and `cal_mask` must both be examined. An unset nominal flag is now logged as `non-nominal`, not as a measurement claim. The nominal source values and assumed 25 C remain assumptions; the 20-byte DSP SET_CFG is not a verified Windows ABI. No cooldown, automatic recalibration or measurement policy is implemented because its semantics are not established.

Candidate [0026](../patches/0026-ASoC-qcom-propagate-graph-open-errors.patch) fixes another confirmed issue in the composed source: `q6apm_get_audioreach_graph()` ignored the synchronous APM GRAPH_OPEN result (`out/rev21-apply/sound/soc/qcom/qdsp6/q6apm.c:88-92`). Thus rejection or timeout could masquerade as host graph-open success. It propagates that result, serializes shared graph lookup/open/final release with a separate graph mutex, and logs the result. A timeout can leave DSP state uncertain; stop and reboot rather than retrying the diagnostic. The candidate affects all AudioReach graphs. Host concurrency stubs are not proof of kernel lock ordering, start-count safety, DSP cleanup after partial OPEN, or all graph users: kernel review and tests are required.

Candidate [0027](../patches/0027-ASoC-qcom-report-muted-speaker-graph-metadata.patch) logs graph IDs and command return codes; for each supplement SET_CFG it logs only graph/instance/parameter IDs, size and return status. It logs VI DMA rate, width, channel count and requested mask, VI operation speaker count and its map, and each feedback slave's requested port/mask/count. `rc=0` for `0x080011f5` means this Linux command received a successful APM response, not that the DSP interpreted the payload correctly or produced correct protection. Existing transport error logs include the DSP error code. The maps and port masks are requested settings, not observed on-wire slot assignments.

For each guarded amplifier, 0027 also attempts an uncached `WSA884X_PA_FSM_EN` read before feedback add and free, only when the device is already attached and in runtime use. It logs the global PA-enable register bit or explicit unknown/read failure; it does not resume an idle device or write a register. A direct register bit is a separate observation from the guard but is **not** proof of actual acoustic silence, analog output state, or continuous inhibition. Missing/error/unknown is not off. Its runtime and SoundWire read behavior need kernel/device verification; the existing mute/write paths ignore some register errors and are not independently proven.

The read-only [guard report](../userspace/closed-loop/guard-report) labels absent fields unknown, treats `cps_required: 0` as merely not reported required, and does not authorize unmute. The [supervisor](../userspace/closed-loop/speaker-supervisor) verifies MultiMedia5 and the negotiated S16_LE/48 kHz/stereo parameters, starts capture only, checks RUNNING and exits on XRUN, state loss, I/O error or two seconds without frame-pointer progress. It advances the ALSA application pointer via `snd_pcm_forward()` instead of reading a sample buffer. ALSA documents this operation as moving the application frame position forward ([ALSA PCM reference](https://www.alsa-project.org/alsa-doc/alsa-lib/group___p_c_m.html)); Linux `sources/linux/sound/core/pcm_native.c:3020-3041,3082-3100` implements it by moving the application pointer. Whether the unconnected trigger produces frames at all, and whether forwarding keeps this particular PCM running, remain device questions. A stall ends the diagnostic; neither progress nor its absence proves VI samples.
