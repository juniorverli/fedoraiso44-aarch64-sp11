## Speaker path and protection

Both runtime device-tree dumps show `swr0` at `soundwire@6b10000` as `status = "disabled"`; the left and right WSA884x child descriptions remain in the base tree but are under that disabled controller. The live `sound {}` node contains the VA and DisplayPort links, with no WSA playback link. `lsmod` lists the WSA macro codec but not the WSA884x slaves. The D26 speaker UCM service explicitly skips because `ConditionKernelCommandLine=sp11.entry=spk` is false, and `/run/sp11-speaker-ucm` is absent.

The read-only guard snapshot is the same in both captures: `open_allowed: yes`, `allowed: no`, reason `the closed-loop graph is not up`, `loaded: 1`, `graph_up: 0`, `vi_streams: 0`, `cal_mask: 0x0`, no fault. The kernel logs `closed-loop speaker protection data loaded: 1 links, 28 records` after the ASoC card's initial deferred widget binding. This proves the guard data was parsed and the card registered; it does not prove the ADSP accepted or started a speaker/VI graph. With `swr0` disabled, no WSA link, no V/I stream and no speaker entry, `graph_up=0` and `allowed=no` are expected fail-closed state. These safe/Spectra captures do not demonstrate a speaker graph failure or a playback defect.

The card enumerates `MultiMedia1 Playback`, `MultiMedia2 Capture`, `MultiMedia3 Playback` and `MultiMedia4 Playback`; this does not mean a WSA speaker backend is present. The `no backend DAIs enabled for MultiMedia4 Playback` warning is for the DP path and cannot be attributed to the speaker graph. Likewise `ASoC: Parent card not yet available, widget card binding deferred` is followed by card/device enumeration and is not a failed card probe in these captures.

## Repeatable WSA macro cache warning

Both boots log the following for `wsa_macro 6b00000.codec` shortly after card registration:

- `Driver needs fixing: Unsorted reg_defaults, sorting the copy` (11:31:24.403478 UTC / 11:26:40.368498 UTC)
- `using zero-initialized flat cache, this may cause unexpected behavior` (11:31:26.542844 UTC / 11:26:42.504440 UTC)

The first message is emitted by regmap while it sorts the provided defaults. The second is emitted by Linux 7.3 `drivers/base/regmap/regcache-flat.c:111` when a flat-cache read addresses an entry whose valid bit is clear; the flat-cache path returns its zero-initialized value. The WSA macro uses `REGCACHE_FLAT`, installs codec-version-specific defaults in `sound/soc/codecs/lpass-wsa-macro.c:1107-1117,2722-2772`, and reads the SoundWire control register from `swclk_gate_is_enabled()` at `:2618-2627`. The warning does not log the register address or caller, so the source of this cache miss is unknown. It is a reproducible diagnostic lead for a future controlled speaker-entry capture, not sufficient evidence that speaker protection or WSA playback failed here. Do not replace the cache type, invent a default, or change speaker guards on this evidence. Ask the kernel owner to capture the missing register/caller in a diagnostic build if it also occurs in an entry with the WSA path enabled.

## Microphone observations from the same captures (read-only)

Both entries expose `MultiMedia2 Capture` as ALSA PCM device 1 (`pcmC0D1c`), with the UCM `Mic` device mapped to `hw:${CardId},1` and described as internal microphones. The VA DMIC muxes are reported as `VA_DMIC`; the sound card and LPASS VA macro drivers are present. No recording or measured input level was captured, and the Spectra snapshot says no user PipeWire session was available when `wpctl status` was sampled. Thus capture endpoint enumeration is verified, but the microphones' signal path and audible/recorded operation remain unverified; these logs do not establish microphone failure.
