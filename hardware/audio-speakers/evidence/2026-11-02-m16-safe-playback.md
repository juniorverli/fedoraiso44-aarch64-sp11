## RX failure

**Verified:** `sources/linux/sound/soc/qcom/qdsp6/audioreach.h:67` defines `0x0100100e` as `APM_CMD_REGISTER_MODULE_EVENTS`; `APM_CMD_SET_CFG` is `0x01001006` (`:63`). The M16 closed-loop patch 0014 calls `audioreach_sp11_register_events()` after SP parameter configuration, operation mode and enable; its registration targets the SP module instance with event `0x0800138c`, no event payload, then returns failure to `audioreach_set_media_format()`. That error propagates through `q6apm_graph_media_format_pcm()` (`sources/linux/sound/soc/qcom/qdsp6/q6apm.c:443`) to the generic `Failed to set media format` message (`q6apm-lpass-dais.c:257`). Inference, revised below: the backend call path supports a rejected SP diagnostics subscription; the opcode alone does not distinguish it from other registrations, and the log does not contain a target or event ID. Status 3 means `ADSP_EUNSUPPORTED` (`sources/linux/sound/soc/qcom/qdsp6/q6dsp-errno.h:14`); the exact rejected operation or field and graph state remain **TBD**. The prior report cites event occurrence in ACDB but does not independently establish registration ABI; see `2026-10-30-argon-rea-report.md` and `2026-10-30-closed-loop.md` H7. Status 3 alone does not identify which field is wrong.

**Verified source / Inference for runtime:** topology source `userspace/build-topology/m4/X1E80100-Microsoft-Surface-Pro-11-closedloop.m4:22-83` declares MultiMedia1 S16_LE, 48 kHz, stereo and WSA RX graph 105 with the same format, WSA interface RX0; SP is in graph 105, VI in graph 106. Public topology `out/ref/srini-art/X1E80100-Microsoft-Surface-Pro-11.m4` SHA-256 `41b658e92860b52646f05fdc3f9b2ae4737b790c90515c40ce8595b9e05b3728` agrees on RX format and routing but has no SP. Patch 0015 forces 48 kHz on RX, leaves channels and format from FE, and forces TX_0 to 8 kHz, S32_LE, two logical speakers; the VI code expands their mapping. `q6dma_hw_params` uses the channel interval **maximum**, `params_width()` and `params_rate()` (`q6apm-lpass-dais.c:169-180`), and `audioreach_codec_dma_set_media_format()` sends those values (`audioreach.c:705-765`). Exact negotiated RX values were not logged; if the FE constraints are honored they should be 2/48000/16. A channel/rate/format fix is not supported by this error, and the TX change does not establish an RX defect. Furthermore the failure at the SP module can precede the codec DMA configuration; the log does not prove that the DSP ever received the RX endpoint format. Request read-only parameter and module/command tracing if a safe diagnostic becomes available.

Patch 0019 only identifies failed SP diagnostics registration; it retains the error and guard behavior. It is not a functional fix. `checkpatch --strict`: 1 error for missing Signed-off-by, 0 warnings or checks; with `--no-signoff`, 0 errors, warnings or checks. No sign-off was fabricated. Apply checked against the relevant source after patches 0014 and 0018. No build or device test.

## Firmware byte analysis and candidate fix

**Verified:** byte scan of `out/firmware-root/lib/firmware/qcom/x1e80100/microsoft/Denali/qcadsp8380.mbn`, SHA-256 `921870a839ee2aba647b04598d62ed96f3d2d5dfbb2499fc842f9a6ff0e0da13`, found one little-endian occurrence each of SP `0x070010e2`, VI `0x070010e3`, CPS router `0x070010e4` at byte offsets `0x12c6034`, `0x12c6024`, `0x12c6014`, respectively. Their table records start four bytes earlier at `0x12c6030`, `0x12c6020`, `0x12c6010`. No occurrence of event ID `0x0800138c` (`8c 13 00 08`) exists anywhere in the 22,092,168-byte file. The Windows miniport `sources/windows/DriverStore/qcaudminiport_base8380.inf_arm64_738ad101f903ae9b/qcaudminiport8380.sys`, SHA-256 `79b26804d05332304c736c4e03e942db6a07ea886a2b07f3a4ff5947d1d05531`, contains none of these four little-endian constants. Catalog: `sources/binary-catalog.tsv` rows for both binaries; this was a byte search, not disassembly.

**Inference, leading candidate:** the firmware table supports the presence of SP/VI/CPS modules, and the absent event literal supports an unsupported reference diagnostics event as the reason for the M16 registration failure. Absence of a literal cannot prove the firmware cannot synthesize or support an ID, nor prove which command/field produced the logged response; a correlated device test is still needed. Firmware module presence does not prove the topology, control links, feedback, calibration, or protection work.

**Verified source / candidate:** patch 0020 maps DSP `ADSP_EUNSUPPORTED` to `-EOPNOTSUPP` in the synchronous response path (previously all positive statuses became `-EINVAL`), while reserving that return for a DSP response on event registration by treating a transport `-EOPNOTSUPP` as fatal `-EIO`. Only SP diagnostics registration accepts the mapped error; all other failures remain fatal. It logs once and latches `sp-diagnostics` in the guard. Other commands retain fatal error handling. Patch applies after 0019 and passes `checkpatch --strict`; no kernel build or device test.

**Protection limitation:** patch 0014 treats every diagnostics event as a DSP fault because its payload is undecoded. Missing the subscription therefore removes a fault observation channel. Patch 0020 keeps that decision fail-closed by latching a fault, so graph preparation may proceed but unmute is refused, including on later opens. Patch 0013 independently latches enabled WSA interrupt status after initialization. Patch 0012 requires loaded data, no fault or kill switch, running SP and VI graphs, CPS when required, and both calibration channels before unmute; these are graph-state counts, not proof of live sample flow or working protection. Patch 0013 asks this guard on each unmute and keeps the PA muted when refused. At the time of this M16 evidence, the D26 marker was only an offline DT validation contract. Follow-up patch 0022 also reads it at runtime: exact marker plus no SP selects capped open loop; an SP topology remains on closed-loop gates. The speaker-off fallback remains required. Proving a safe substitute for the missing DSP fault channel and validating actual VI/CPS data and protection on-device are separate open work; no audible test follows from this patch.

## Follow-up: shared-memory hypothesis

**Verified:** the M16 private ISO manifest `out/iso/sp11-fedora44-aarch64-kiwi-20261101T232050Z-private.json` records topology SHA-256 `000b6d720640225657cdb08d26db738962bca7d5961a4be01c34c5a7778b6272`; the L0-extracted ISO root, current private generated binary and `out/build/tplg-harness-e2e/fw/qcom/x1e80100/hcl-tplg.bin` all hash to that value. L0 6.4 also reports the staged hash matches. This establishes the ISO artifact, not the hash actually loaded on the device. The generated `.conf` has SHA-256 `2267887225dbc1544ba53c00fe81d6df8e6d74f36882ae4a28cc98991a310340`.

**Verified:** the MultiMedia1 frontend source selects `subgraph-stream-vol-playback.m4` with first IID `0x6001` (`userspace/build-topology/m4/X1E80100-Microsoft-Surface-Pro-11-closedloop.m4:22-25`); the pinned base template `out/ref/srini-art/audioreach/subgraph-stream-vol-playback.m4:38,70` declares WRSH, not pull mode. The generated config `stream0.wrsh_ep1` says module ID `0x07001000`, IID `0x6001`, i.e. `MODULE_ID_WR_SHARED_MEM_EP` (`sources/linux/sound/soc/qcom/qdsp6/audioreach.h:13`), not `MODULE_ID_SH_MEM_PULL_MODE` (`:19`, `0x07001006`). The prior real-parser harness log `out/build/tplg-harness-e2e/q-hcl.log` (SHA-256 `24a5a1a1c786ba84a641fae030efa785621536432c31322accf836c475f15d24`) confirms graph 0 IID `0x6001` / MID `0x07001000`; graph 105 contains MFC, SP, logger and codec DMA, and no shared-memory module. The same log confirms the SP IID is `0x4027`. Harness firmware hash matches the ISO artifact. It does not exercise `q6apm_graph_open()` or the ADSP.

**Verified:** parser `sources/linux/sound/soc/qcom/qdsp6/topology.c:464-470,572` records the module ID and instance token, with the allocator storing the instance at `:165-199`. `q6apm_graph_open()` zero-allocates each graph and searches within that graph for pull, then WRSH, on playback (`q6apm.c:711-762`). Hence graph 0 should get `shm_iid=0x6001`, with `is_push_pull_mode` false; graph 105 has neither endpoint and its own `shm_iid` stays zero. Zero is therefore expected for the backend, not evidence of a parser defect. An absent endpoint or a nonpositive returned IID leaves the field zero; the zero-token dynamic allocator path also needs care because `idr_alloc_cyclic()` returns the allocated ID but the code stores the unchanged `module_id` (`topology.c:184-199`). This topology supplies explicit nonzero IIDs, so that separate edge case does not establish the observed failure.

**Verified:** watermark registration uses `graph->shm_iid` and watermark event `0x0800101c` (`audioreach.c:1226-1260`), but its only in-tree caller is the frontend `q6apm-dai.c:247-264`, inside the push/pull branch; failure there logs `WaterMark event config failed`, before media-format calls. The reported `Failed to set media format` at `q6apm-lpass-dais.c:257-259` is the separate backend path, whose `q6apm_graph_media_format_pcm()` skips all four shared-memory module types (`q6apm.c:443-465`). Patch 0014 adds a different registration using the same opcode, SP module IID and `EVENT_ID_SP_DIAGNOSTICS`, in that backend media-format path. No component patch changes the watermark call. The adjacent opcode error and backend error therefore support SP registration as the leading explanation, but without a transaction/target trace they do not prove the two messages belong to the same command; concurrent activity remain unproven; status 3 identifies an unsupported operation but not the target field.

**Decision:** neither adding SH_MEM to the backend nor skipping a watermark registration addresses the evidenced path. No functional topology or kernel patch is justified by this hypothesis; skipping a required watermark on a real push/pull stream could break it, while returning an error for an invalid IID would not fix this backend. Keep patch 0019 as a diagnostic and apply candidate 0020 after it; retain the D26 guard and fault latch. On a future device boot, verify the loaded topology hash and use the diagnostic to distinguish SP registration, with event/IID and command correlation if safely available. Do not infer protection or permission to unmute from this offline analysis.

## 2026-11-02 Windows subscription scan and candidate 0021 gate

**Windows evidence supplied for this review:** a byte scan of `qcaudminiport8380.sys` and its DLLs found no `APM_CMD_REGISTER_MODULE_EVENTS` (`0x0100100e`, in either byte order), no SP diagnostics event ID `0x0800138c`, and no SP module IDs `0x070010e2`/`0x070010e3`. The two SP module IDs occur in `qcadsp8380.mbn`. This supports the inference that the Windows miniport does not subscribe to the SP diagnostics event and that the subscription is not required by that vendor audio path. The firmware IDs alone do not prove enabled state, calibration acceptance, live VI/CPS data, or equivalent protection. The scan provenance, file hashes and exact scanned DLL list were not included in the supplied result; treat the finding as operator-provided pending those details.

**Candidate 0021:** for only the DSP `ADSP_EUNSUPPORTED` response to SP diagnostics registration, replace the sticky `sp-diagnostics` protection fault with a one-time degraded-diagnostics state. The guard reports a derived `degraded_fault: 1` and refuses unmute while any prerequisite is missing; this derived condition is distinct from a latched hardware/protection fault and does not block graph preparation. Once all prerequisites pass, `degraded_fault` becomes 0 and unmute may proceed if every other existing guard passes. Do not clear or relax actual faults, the kill switch, loaded-data check, graph state, VI stream check, required CPS stream check, calibration mask, amplifier gate, D26 DT profile/volume ceilings, or any unrelated error path. In degraded mode require non-nominal closed-loop calibration. The candidate records SP module enable success and requires it in the guard. This change does not validate sample quality or restore the lost DSP fault-event channel; hardware protection remains unproven until device evidence and further safe validation.

**Revision-17 merge evidence must all be present in the same muted-boot capture:**

1. Exact loader message `closed-loop speaker protection data loaded: 1 links, 28 records` (or the actual revision-17 link/record counts, with the private topology hash recorded) proves only that the kernel parsed the supplement.
2. Exact warning `SP diagnostics unavailable; speakers remain muted` from the 0020 path, with DSP status `ADSP_EUNSUPPORTED` attributable to the registration command. In this source path that warning is reachable only after SP graph parameters, normal operation mode and `audioreach_module_enable()` all returned success, followed by the targeted diagnostics registration returning unsupported. This is indirect but valid control-flow evidence that the module-enable command succeeded; it does not prove that the DSP actually ran the protection algorithm or that the feedback is effective. The current code emits no separate module-enable success line or instance ID. A generic status 3 or `-EOPNOTSUPP` alone does not identify the rejected operation. The Windows scan is supporting context only; it cannot substitute for this device result.
3. The calibration log `speaker calibration applied (measured)` and a contemporaneous `/sys/kernel/debug/sp11/guard` snapshot showing `loaded: 1`, `graph_up: 1`, `vi_streams` at least 1, `cal_mask: 0x3`, `cal_nominal: 0`, and `cps_streams` at least 1 whenever `cps_required: 1`. `graph_up: 1` is required alongside the targeted warning to establish the SP graph reached start. Before 0021, the guard has no `sp_enabled`, `diagnostics_degraded`, or `degraded_fault` fields; the targeted warning plus its source control flow serves as the module-enable result evidence for revision 17. Also capture its existing fault and reason: under 0020, expected `fault: 1 (sp-diagnostics, 0x00000003)` prevents unmute.

The evidence can justify considering 0021 only if all the above appear together in the same muted revision-17 run, with the selected D26 entry and unchanged amplifier/volume limits confirmed. The graph/VI/calibration producers can update while the sticky 0020 fault is set, so the guard snapshot can show whether those callbacks ran, but `allowed` must remain `no` solely because of `sp-diagnostics`. The warning's control-flow position establishes the successful enable response without an explicit log; it does not prove DSP efficacy. Candidate 0021 adds a separate success line, `sp_enabled`, `diagnostics_degraded`, and derived `degraded_fault` state for later runs. In a later run with a missing prerequisite, `degraded_fault: 1` and `allowed: no` must appear; with all protection prerequisites present, `degraded_fault: 0` is required before unmute. Do not treat absence of an error as success evidence.

**Reject merge** if the data-loaded line is absent or reports failed/empty data; the targeted warning does not appear; registration returns anything other than DSP `ADSP_EUNSUPPORTED`; any unrelated configuration, graph, amplifier, limits, or transport error occurs; the guard has `loaded: 0`, `graph_up: 0`, `vi_streams: 0`, incomplete calibration (`cal_mask` other than `0x3`), nominal calibration, missing required CPS, `nospk: 1`, or any real protection/amplifier fault; or the D26 ceilings/profile are absent. A generic status 3, `-EOPNOTSUPP`, or absence of `Failed to set media format` does not replace the targeted warning. Do not treat a `fault` latch caused solely by the known 0020 diagnostics response as independent evidence for or against the underlying protection path; it is the state 0021 proposes to replace and remains sticky in the revision-17 image. That image stays muted.

For later runs, the candidate adds a success log after the SP module-enable response and exposes `sp_enabled` and `diagnostics_degraded` in the read-only guard. This helps attribute the command result and state, while still not proving DSP algorithm efficacy. No kernel/ISO build or device test was run for this candidate.
