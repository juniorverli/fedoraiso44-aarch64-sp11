## RX failure

**Verified:** `sources/linux/sound/soc/qcom/qdsp6/audioreach.h:67` defines `0x0100100e` as `APM_CMD_REGISTER_MODULE_EVENTS`; `APM_CMD_SET_CFG` is `0x01001006` (`:63`). The M16 closed-loop patch 0014 calls `audioreach_sp11_register_events()` after SP parameter configuration, operation mode and enable; its registration targets the SP module instance with event `0x0800138c`, no event payload, then returns failure to `audioreach_set_media_format()`. That error propagates through `q6apm_graph_media_format_pcm()` (`sources/linux/sound/soc/qcom/qdsp6/q6apm.c:443`) to the generic `Failed to set media format` message (`q6apm-lpass-dais.c:257`). Inference, revised below: the backend call path supports a rejected SP diagnostics subscription; the opcode alone does not distinguish it from other registrations, and the log does not contain a target or event ID. Exact DSP reason, target validity, required payload, and graph state at registration are **TBD**. The prior report cites event occurrence in ACDB but does not independently establish registration ABI; see `2026-10-30-argon-rea-report.md` and `2026-10-30-closed-loop.md` H7. Do not treat error code 3 as identifying which field is wrong.

**Verified source / Inference for runtime:** topology source `userspace/build-topology/m4/X1E80100-Microsoft-Surface-Pro-11-closedloop.m4:22-83` declares MultiMedia1 S16_LE, 48 kHz, stereo and WSA RX graph 105 with the same format, WSA interface RX0; SP is in graph 105, VI in graph 106. Public topology `out/ref/srini-art/X1E80100-Microsoft-Surface-Pro-11.m4` SHA-256 `41b658e92860b52646f05fdc3f9b2ae4737b790c90515c40ce8595b9e05b3728` agrees on RX format and routing but has no SP. Patch 0015 forces 48 kHz on RX, leaves channels and format from FE, and forces TX_0 to 8 kHz, S32_LE, two logical speakers; the VI code expands their mapping. `q6dma_hw_params` uses the channel interval **maximum**, `params_width()` and `params_rate()` (`q6apm-lpass-dais.c:169-180`), and `audioreach_codec_dma_set_media_format()` sends those values (`audioreach.c:705-765`). Exact negotiated RX values were not logged; if the FE constraints are honored they should be 2/48000/16. A channel/rate/format fix is not supported by this error, and the TX change does not establish an RX defect. Furthermore the failure at the SP module can precede the codec DMA configuration; the log does not prove that the DSP ever received the RX endpoint format. Request read-only parameter and module/command tracing if a safe diagnostic becomes available.

Patch 0019 only identifies failed SP diagnostics registration; it retains the error and guard behavior. It is not a functional fix. `checkpatch --strict`: 1 error for missing Signed-off-by, 0 warnings or checks; with `--no-signoff`, 0 errors, warnings or checks. No sign-off was fabricated. ## Follow-up: shared-memory hypothesis

**Verified:** the M16 private ISO manifest `out/iso/sp11-fedora44-aarch64-kiwi-20261101T232050Z-private.json` records topology SHA-256 `000b6d720640225657cdb08d26db738962bca7d5961a4be01c34c5a7778b6272`; the L0-extracted ISO root, current private generated binary and `out/build/tplg-harness-e2e/fw/qcom/x1e80100/hcl-tplg.bin` all hash to that value. L0 6.4 also reports the staged hash matches. This establishes the ISO artifact, not the hash actually loaded on the device. The generated `.conf` has SHA-256 `2267887225dbc1544ba53c00fe81d6df8e6d74f36882ae4a28cc98991a310340`.

**Verified:** the MultiMedia1 frontend source selects `subgraph-stream-vol-playback.m4` with first IID `0x6001` (`userspace/build-topology/m4/X1E80100-Microsoft-Surface-Pro-11-closedloop.m4:22-25`); the pinned base template `out/ref/srini-art/audioreach/subgraph-stream-vol-playback.m4:38,70` declares WRSH, not pull mode. The generated config `stream0.wrsh_ep1` says module ID `0x07001000`, IID `0x6001`, i.e. `MODULE_ID_WR_SHARED_MEM_EP` (`sources/linux/sound/soc/qcom/qdsp6/audioreach.h:13`), not `MODULE_ID_SH_MEM_PULL_MODE` (`:19`, `0x07001006`). The prior real-parser harness log `out/build/tplg-harness-e2e/q-hcl.log` (SHA-256 `24a5a1a1c786ba84a641fae030efa785621536432c31322accf836c475f15d24`) confirms graph 0 IID `0x6001` / MID `0x07001000`; graph 105 contains MFC, SP, logger and codec DMA, and no shared-memory module. The same log confirms the SP IID is `0x4027`. Harness firmware hash matches the ISO artifact. It does not exercise `q6apm_graph_open()` or the ADSP.

**Verified:** parser `sources/linux/sound/soc/qcom/qdsp6/topology.c:464-470,572` records the module ID and instance token, with the allocator storing the instance at `:165-199`. `q6apm_graph_open()` zero-allocates each graph and searches within that graph for pull, then WRSH, on playback (`q6apm.c:711-762`). Hence graph 0 should get `shm_iid=0x6001`, with `is_push_pull_mode` false; graph 105 has neither endpoint and its own `shm_iid` stays zero. Zero is therefore expected for the backend, not evidence of a parser defect. An absent endpoint or a nonpositive returned IID leaves the field zero; the zero-token dynamic allocator path also needs care because `idr_alloc_cyclic()` returns the allocated ID but the code stores the unchanged `module_id` (`topology.c:184-199`). This topology supplies explicit nonzero IIDs, so that separate edge case does not establish the observed failure.

**Verified:** watermark registration uses `graph->shm_iid` and watermark event `0x0800101c` (`audioreach.c:1226-1260`), but its only in-tree caller is the frontend `q6apm-dai.c:247-264`, inside the push/pull branch; failure there logs `WaterMark event config failed`, before media-format calls. The reported `Failed to set media format` at `q6apm-lpass-dais.c:257-259` is the separate backend path, whose `q6apm_graph_media_format_pcm()` skips all four shared-memory module types (`q6apm.c:443-465`). Patch 0014 adds a different registration using the same opcode, SP module IID and `EVENT_ID_SP_DIAGNOSTICS`, in that backend media-format path. No component patch changes the watermark call. The adjacent opcode error and backend error therefore support SP registration as the leading explanation, but without a transaction/target trace they do not prove the two messages belong to the same command; concurrent activity and the DSP's reason remain unknown.

**Decision:** neither adding SH_MEM to the backend nor skipping a watermark registration addresses the evidenced path. No functional topology or kernel patch is justified by this hypothesis; skipping a required watermark on a real push/pull stream could break it, while returning an error for an invalid IID would not fix this backend. Keep patch 0019 as a diagnostic and retain its error and D26 guard. On a future device boot, verify the loaded topology hash and use the diagnostic to distinguish SP registration, with event/IID and command correlation if safely available. Do not infer protection or permission to unmute from this offline analysis.
